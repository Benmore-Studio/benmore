End-user search boxes, filter UI, anything where the query text comes from a request body / URL param. For those, use `run: sql` with `:name` placeholders + `with.params:` - that path is parametrized and safe by construction. The runtime refuses a request-sourced value in sql_dynamic text for synchronous and `mode: async` flows alike. In a data-event flow (on_insert / on_update / on_delete) the triggering row's columns are request input too, since the caller wrote them; its id, user_id, tenant key, timestamps, session keys and their old_* copies are not. So are the signed-in caller's profile values under `user`, which the caller writes at signup and through PATCH /api/_auth/profile: every `user.<col>` except the account columns the framework owns (user.id, user.email, user.role, user.verified, user.group_id, timestamps, the groups: tenant columns), refused when written, by benmore check and at run time; see api({at:'flows'}) → identity_binding. The caller's email (`${{ user.email }}`, `{{user_email}}`, `:user_email`) is never sql_dynamic text either: signup accepts quotes and SQL comment characters in an address. It stays trusted identity everywhere else; bind it with `:user_email` in `run: sql`. Taint follows copies: a `run: set` output computed from request input, a `for_each` loop variable over request data, a parsed request body, a value reached through an `||` fallback, an `on_error:` handler, and an `enqueue` payload value (in the job flow that receives it) are all still request input. So is the output of any named `run: sql`, `compute`, `api` (or other) step whose own templates read request input, e.g. `SELECT :q AS c` then `'{{pick.c}}'` in sql_dynamic text; a lookup keyed only by literals or the session stays untainted. Fix a refusal by binding the value with `:name` in a `run: sql` step, never `{{ref}}` in sql_dynamic. `run: enqueue` also refuses a request-controlled `flow:` name.
