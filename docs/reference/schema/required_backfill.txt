Adding a required field without @default to a model whose table already exists adds the column NOT NULL with a backfill default chosen by type: Int, BigInt, Float and Decimal get 0, Boolean 0 (false), String and Bytes '' (an empty string), DateTime the time the migration ran (by a table rebuild, see time_defaults). A required foreign key is never backfilled (relation_migrations) and an @updatedAt field fills with the write time. Every existing row gets that value and the live column keeps it as its DEFAULT, so a SQL insert (flow, hook, import) that leaves the field out stores it while the API refuses a create without the field (`<field> is required`); a new database (a reset dev, a first promote) creates the table without that default. The write (write_file, edit_file, `benmore push`, `benmore deploy`) lists each such field under `schema_not_applied` with the value, `benmore check` reports it until the app reloads, and the reload logs it (`SCHEMA BACKFILL`). To choose the value, add the field with `@default(<value>)`; to set existing rows, ship a migrations/ file (`UPDATE t SET c = <value>;`). Changing @default later does not change the live default (unapplied_changes).
