Adding @relation to an existing Prisma table installs a physical SQLite foreign key, so native includes and parent-reference authorization see the same relationship as a fresh table. New nullable reference columns use ALTER ADD COLUMN REFERENCES and preserve existing rows as null. A new required reference without an explicit default is never backfilled with an invented id: populated tables must first add a nullable column, backfill valid parent ids in an explicit migration, then apply the intended constraint. Missing constraints on existing columns, including relations older runtimes recorded without installing, are reconciled even when schema source is unchanged. Safe leaf-table repairs preserve rows, hidden rowids, original constraints/options, indexes, triggers and AUTOINCREMENT sequence in the schema migration transaction. Invalid existing references, conflicting physical FKs, or a repair that would rebuild a table referenced by another table fail without committing schema/data/ledger changes; fix them with an explicit migration that preserves related rows. These refusals can block startup or reload. The platform upgrade-check command compares declared relations with physical FKs and uses the same read-only repair checks for retained-column orphan references (including soft-deleted rows), conflicting constraints and incoming-FK rebuild refusals before startup; it does not repair data or write migrations. Parent targets without an eligible single-column primary/full unique key are refused; composite, partial and expression indexes do not qualify. Ordinary INTEGER rowid keys and BINARY keys with no declared COLLATE are verified from SQLite metadata. Other collation cases remain explicitly unverified warnings that also block upgrade-check until reconciled; no DDL collation matching is guessed. Runtime repair retains atomic native FK validation as the final authority. New columns and other pending schema changes still require their normal migration validation. Inventory and resolve legacy drift before upgrading. No rows, including soft-deleted rows, are discarded or rewritten to invent a parent. Repair journals retain the executed SQL; automatic rollback of a relation rebuild is refused because removing its constraint requires another reviewed migration. Native schema.sql constraints and custom FK actions remain authoritative.
