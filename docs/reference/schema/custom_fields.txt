Admins (an unscoped admin session or token) can add columns at runtime: GET /api/_schema/<table>/fields lists the table's columns (custom ones flagged), POST /api/_schema/<table>/fields {name, type: TEXT|INTEGER|REAL|DATETIME, description?} adds one (201; reserved names and over 50 custom fields per table are 400, an existing column 409), DELETE /api/_schema/<table>/fields/<name> removes a custom field. A versioned table's <table>_history gains the column in the same transaction. POST takes only the app's own model tables, the ones auto-CRUD serves. A version-history table, a full-text index or its shadow tables and SQLite's own tables answer 400 `<table> is not an app table: ...`, a missing table 404, a _benmore_ table 403. GET and DELETE still accept such a table, so a field added there before can be found and removed. The CustomFields component (api(at:'components')) uses these routes. A custom field named with an SQL reserved word (order, group, select) is a working column: after the 201 it filters, sorts, counts and projects like any other. See reserved_word_names for the two things to know.
