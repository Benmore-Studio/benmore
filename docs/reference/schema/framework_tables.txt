Four pieces of config take only the app's own tables: app.yaml `versioned:`, encrypted fields (encrypted.yaml and app.yaml `encrypted:`), workflows.yaml (`table:`) and computed.yaml (a field's table and each table under its `triggers:`). A framework table (`_benmore_*`) or one of SQLite's own (`sqlite_*`) in any of them is refused by the write gate (write_file, edit_file, `benmore push`, `benmore deploy`) and is an error in `benmore check`. An app that was deployed with such an entry keeps loading and the entry does nothing: no history table, no encrypted column, no transition route, no trigger. Its log names the entry at every start, as `VERSIONING NOT RUNNING`, `ENCRYPTION NOT RUNNING`, `COMPUTED NOT RUNNING` or a `WARNING: workflows.yaml ...` line. A computed field that loses one trigger this way is still recalculated on its other triggers. retention.yaml follows the same rule (api({at:'retention'}) keys). What an app does configure on a framework table: `access: _benmore_users: read:` for the user directory (api({at:'access'})), hooks on `_benmore_users` for sign-up and sign-in (api({at:'hooks'})), extra profile columns through `auth.signup_fields` and `auth.profile_fields`, and SQL in a flow that reads it. Keep a per-user state, secret or derived value in a table of the app with a `user_id` column.
