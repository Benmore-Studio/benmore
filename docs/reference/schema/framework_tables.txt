Four pieces of config take only the app's own tables: app.yaml `versioned:`, encrypted fields (encrypted.yaml and app.yaml `encrypted:`), workflows.yaml (`table:`) and computed.yaml (a field's table and each table under its `triggers:`). A framework table (`_benmore_*`) or one of SQLite's own (`sqlite_*`) in any of them is refused by the write gate (write_file, edit_file, `benmore push`, `benmore deploy`) and is an error in `benmore check`. An app that was deployed with such an entry keeps loading and the entry does nothing: no history table, no encrypted column, no transition route, no trigger. Its log names the entry at every start, as `VERSIONING NOT RUNNING`, `ENCRYPTION NOT RUNNING`, `COMPUTED NOT RUNNING` or a `WARNING: workflows.yaml ...` line. A computed field that loses one trigger this way is still recalculated on its other triggers. retention.yaml follows the same rule (api({at:'retention'}) keys). What an app does configure on a framework table: `access: _benmore_users: read:` for the user directory (api({at:'access'})), hooks on `_benmore_users` for sign-up and sign-in (api({at:'hooks'})), extra profile columns through `auth.signup_fields` and `auth.profile_fields`, and SQL in a flow that reads it. The app's own SQL (a flow's `run: sql` or `run: sql_dynamic` step, a hooks.yaml `sql:`, a page `<query>`) reads and writes ROWS of framework tables and may create, alter and drop the app's own tables, indexes, triggers and views, but it cannot change the framework's objects. Refused when the statement runs, however it is spelled (quoted names, a `main.` prefix, comments, text built by sql_dynamic): CREATE or DROP of a table, view, index or trigger whose name starts with `_benmore_` (a TEMP one included); CREATE or DROP of an index or trigger on a `_benmore_*` table; ALTER TABLE of one, and ALTER TABLE ... RENAME TO a `_benmore_` name; and `PRAGMA writable_schema = ...`. The step fails with a message that starts `app SQL may not` and names the object (a flow answers 500, a before-hook refuses the write), and the statement changes nothing. Dropping one of the app's own tables still takes the framework's triggers on it along. The write gate and `benmore check` refuse a flow file or hooks.yaml whose SQL text is such a statement; a deployed file keeps loading and the step fails when it runs. Under `compliance: hipaa` the same SQL also cannot UPDATE or DELETE audit rows (api(at:"audit.append_only")). Add a column to `_benmore_users` with `auth.signup_fields` / `auth.profile_fields`, not with ALTER TABLE in a flow. A file in migrations/ is the app's schema tool and may do more: add a column or an index to a framework table, put a trigger with a name of the app's own on one, write its rows, and drop a `_benmore_*` trigger from one of the app's own tables (the next load installs it again while the config asks for it). It cannot set `PRAGMA writable_schema`, create a trigger whose name starts with `_benmore_`, drop a `_benmore_*` trigger from a `_benmore_*` table (nor drop a framework table that carries one), or create a TEMP table or view with a `_benmore_` name. Such a statement fails with a message that starts `a migration may not`, however it is spelled; the file is rolled back and set aside as failed like any failing migration, and a push that adds the file is refused by its dry run with the same message. Under `compliance: hipaa` a migration cannot change the audit tables or their rows either (api(at:"audit.append_only")). Keep a per-user state, secret or derived value in a table of the app with a `user_id` column.
