A migrations/*.sql write (write_file, edit_file, `benmore push`, `benmore deploy`, the save hook; dev or `--env prod`) that deletes a table's rows or a column's values on the target instance by dropping, renaming or rebuilding the table is refused, naming what is lost and the counts; the app applies every migration file its ledger lacks when it reloads. The check runs the file in the reload's dry run (one transaction, always rolled back; see failed_migration_push in api(at:"recovery")) and compares before and after: every table the file drops or alters (however the statement is spelled) and every table whose foreign keys reference one of those (a DROP TABLE with foreign keys on deletes its ON DELETE CASCADE children) must afterwards hold at least as many rows, under the same name or renamed, and every column holding non-NULL values must still exist, under its name or the name the file renames it to, with at least as many. Lines read `DROP TABLE t (2 rows)`, `t: 2 rows, by RENAME TO t_retired + DROP TABLE t_retired`, `t: 2 rows before the file, 0 after it (the file rebuilds the table)`, `t.c: 2 rows with a value before the file, the column is gone after it (the file rebuilds the table)` and `DROP COLUMN t.c (2 rows with a value)`. A rebuild that copies every row and every populated column passes: `CREATE TABLE t_new (...); INSERT INTO t_new (...) SELECT ... FROM t; DROP TABLE t; ALTER TABLE t_new RENAME TO t;`, or rename t to t_old, create t, copy, drop t_old. Take the statements out to keep the data, or write the file again with allow_table_drop (`benmore push migrations/<file>.sql --allow-table-drop`) to drop it - a backup is taken before the migration runs and `benmore restore` lists it. Not checked: a DELETE or UPDATE in a table the file does not drop, rename or alter (the file's stated intent, such as a dedupe before @unique; in a table it does restructure the comparison counts them), an ADD COLUMN-only file, empty tables, all-NULL columns, the DOWN section, a file the instance already applied, files the runner never applies (subdirectories, *.failed.sql), instances without data, and virtual (full-text) tables. When the dry run reaches no verdict (its 8 s bound, the write lock held by another writer, a trigger needing the encryption key) or the file itself fails, the file is read instead with the SQLite lexer (a drop behind a /* comment */, on a line with another statement, with quoted or main-qualified names or in another case is the same drop; temp and attached schemas are not the app's data): the reading follows renames and passes a rebuild only when the file inserts into the replacement, but it cannot see a column a rebuild leaves out. Promote's gate (force) and dry run run the same comparison for every copied file on prod, and restore's code-mismatch check on the snapshot (api(at:"recovery") restore_code_mismatch); the runner logs `DESTRUCTIVE MIGRATION <file>: ...` from the reading when it applies such a file.
