A schema.prisma change SQLite cannot make in place - a field's type, nullability or @default, a removed field, a removed @unique - is not applied to the live database (nor on prod after promote, so both keep the same columns). The write (write_file, edit_file, `benmore push`, `benmore deploy`) answers `schema_not_applied` with one line per change naming the column and what the live database does instead: Int -> String keeps an INTEGER column that stores "007" as 7; a field made required keeps accepting NULL in SQL writes and keeps existing NULL rows; a new @default leaves rows created without a value on the old default; a removed field keeps its column and data, and API reads keep returning it. `benmore push` prints the lines, `benmore check` lists them as `schema_not_applied` warnings until the app reloads, the reload logs them (`SCHEMA CHANGE NOT APPLIED`), and promote's preview lists the prod side under `schema_not_applied`. A live column the schema no longer declares is logged by the start that first finds it (`schema kept as it is: <table>.<column>: in the database but not in the schema - kept with its data ...`) and again only when that list changes, not on every start. To make such a change, ship a migrations/ file: `ALTER TABLE t DROP COLUMN c;` for a removed field (promote asks for force before it runs on prod), an UPDATE backfill for a newly required field, and for a type change a new field first and then, in the push that removes the old field from the schema, a file that copies the values and drops the old column: `ALTER TABLE t ADD COLUMN new INTEGER; UPDATE t SET new = CAST(old AS INTEGER); ALTER TABLE t DROP COLUMN old;` (the ADD COLUMN is skipped where the new field already made the column). Benmore does not rebuild the table with a cast: SQLite's conversion is lossy. Keep such a file in the source: it serves every database of the app. A database created after the field left the schema (the copy `benmore test` runs on, a new instance, a dev database built again from the schema) never had the column: there the file's `DROP COLUMN` has nothing to do, is skipped with a log line and the file is recorded as applied. A database that is new in the load that runs the file (it held no application table and no applied migration before that load built it from the current schema) also skips every other statement that fails only because it names a table or column the current schema does not have: the copy of a type change, a backfill of a removed column, an index or trigger on a removed table. The rest of the file runs there, so its triggers, indexes and seed rows land, and the file is recorded as applied (api(at:"recovery") startup_migrations). A statement that names a framework table (`_benmore_*`) or a SQLite one (`sqlite_*`) is never skipped: it fails the file on a new database as on any other. A misspelt name is skipped the same way, and what the statement was meant to do is then not done. So whoever can be told is told: the write that brings the file (write_file, edit_file and their dry run, `benmore push`, `benmore deploy`), a promote and its preview, and a restore answer `migration_skipped_drops`, one line per skipped statement, with this key's address in `migration_skipped_drops_docs`; `benmore push` prints the lines. A drop's line names the file and the column as table.column (a table or an index by its name) and says this database does not have it. The line of any other statement names the file, the statement's number in it with its leading keyword (`statement 2 (UPDATE)`) and the missing table or table.column, and says the current schema does not have it; the load that skips it logs the same line as a `WARNING`, which `benmore test` prints above its results. A write lists the statements of the file it brings, a promote those of the files prod has not applied, a restore those the restored database skips. The write is not refused. Read each line: a name this database never had is expected on a database built after the field left the schema, and a mistake anywhere else. On a database that already holds the app's tables only the drop is skipped: any other statement that names a missing table or column fails the file there, and a write that brings it is refused.
