A schema.prisma change SQLite cannot make in place - a field's type, nullability or @default, a removed field, a removed @unique - is not applied to the live database (nor on prod after promote, so both keep the same columns). The write (write_file, edit_file, `benmore push`, `benmore deploy`) answers `schema_not_applied` with one line per change naming the column and what the live database does instead: Int -> String keeps an INTEGER column that stores "007" as 7; a field made required keeps accepting NULL in SQL writes and keeps existing NULL rows; a new @default leaves rows created without a value on the old default; a removed field keeps its column and data, and API reads keep returning it. `benmore push` prints the lines, `benmore check` lists them as `schema_not_applied` warnings until the app reloads, the reload logs them (`SCHEMA CHANGE NOT APPLIED`), and promote's preview lists the prod side under `schema_not_applied`. A live column the schema no longer declares is logged by the start that first finds it (`schema kept as it is: <table>.<column>: in the database but not in the schema - kept with its data ...`) and again only when that list changes, not on every start. To make such a change, ship a migrations/ file: `ALTER TABLE t DROP COLUMN c;` for a removed field (promote asks for force before it runs on prod), an UPDATE backfill for a newly required field, or a new field, a copy of the values and then removal of the old field for a type change. Benmore does not rebuild the table with a cast: SQLite's conversion is lossy. A database created after the field left the schema (the copy `benmore test` runs on, a new instance, a dev database built again from the schema) never had the column: there the file's `DROP COLUMN` has nothing to do, is skipped with a log line and the file is recorded as applied, so the same file serves both databases (api(at:"recovery") startup_migrations). A drop whose name is misspelt is skipped the same way, and the column it was meant to drop is then still there. So whoever can be told is told: the write that brings the file (write_file, edit_file and their dry run, `benmore push`, `benmore deploy`), a promote and its preview, and a restore answer `migration_skipped_drops`, one line per skipped statement that names the file and the column as table.column (a table or an index by its name) and says this database does not have it, with this key's address in `migration_skipped_drops_docs`; `benmore push` prints the lines. A write lists the drops of the file it brings, a promote those of the files prod has not applied, a restore those the restored database skips. The write is not refused. Read each line: a name this database never had is expected on a database built after the field left the schema, and a mistake anywhere else. Only the drop is skipped: a statement that reads the removed column first (the copy in a type change) fails on such a database with `no such column`, so delete that file from the source once dev and prod have applied it.
