A schema.prisma change SQLite cannot make in place - a field's type, nullability or @default, a removed field, a removed @unique - is not applied to the live database (nor on prod after promote, so both keep the same columns). The write (write_file, edit_file, `benmore push`, `benmore deploy`) answers `schema_not_applied` with one line per change naming the column and what the live database does instead: Int -> String keeps an INTEGER column that stores "007" as 7; a field made required keeps accepting NULL in SQL writes and keeps existing NULL rows; a new @default leaves rows created without a value on the old default; a removed field keeps its column and data, and API reads keep returning it. `benmore push` prints the lines, `benmore check` lists them as `schema_not_applied` warnings until the app reloads, the reload logs them (`SCHEMA CHANGE NOT APPLIED`), and promote's preview lists the prod side under `schema_not_applied`. A live column the schema no longer declares is logged by the start that first finds it (`schema kept as it is: <table>.<column>: in the database but not in the schema - kept with its data ...`) and again only when that list changes, not on every start. To make such a change, ship a migrations/ file: `ALTER TABLE t DROP COLUMN c;` for a removed field (promote asks for force before it runs on prod), an UPDATE backfill for a newly required field, or a new field, a copy of the values and then removal of the old field for a type change. Benmore does not rebuild the table with a cast: SQLite's conversion is lossy.
