An on_error handler can respond, redirect or serve a file to finish a synchronous HTTP request. The original failure remains recorded for diagnostics and internal callers. A transactional flow rolls back before starting its on_error handler, so the handler's own database writes are independent of the failed transaction. The outputs of the writes that rollback undid are removed before the handler starts: `${{ steps.<id>.outputs.* }}` of every INSERT, UPDATE, DELETE or REPLACE step (`run: sql` or `sql_dynamic`) that ran in the transaction, the failed step included, has no value in the handler, so a reference to one fails the handler step as template_unresolved unless it has a fallback (`${{ steps.w1.outputs.id || '' }}`). Reads (SELECT) keep their outputs, and a flow without `transaction: true` keeps every output (its writes are committed). Use `${{ error }}` (error_value) for what failed. The handler response is released only after that rollback; a failed parent write is never committed to let its handler run. Once a nested handler rolls back the parent transaction, enclosing retries stop; an enclosing handler may still run once, and a later whole-job attempt starts a fresh transaction. A handler that only records failure does not automatically return success: add an explicit respond when the request was accepted despite a notification failure. Failed connector reads remain failures even if a handler produces output.
