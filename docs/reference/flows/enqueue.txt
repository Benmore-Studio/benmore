`run: enqueue` uses `with: {flow: worker, unique_key: 'work-${{ params.id }}', with: {id: '${{ params.id }}'}}` to queue an existing flow through the native durable queue. `flow` is a non-empty string; payload `with` is a map of text bindings (quote scalars or serialize JSON with the json filter). Optional `run_at` is an RFC3339 timestamp: left out or written empty, the job runs now; a `${{ }}` value that renders anything else, empty included, fails the step. Optional `unique_key` deduplicates pending/running jobs only; completed/failed jobs can be queued again. Enqueue participates in the current SQL transaction and exposes `job_id`, `flow`, `status_token` under its step id. Explicit enqueue is sessionless; the destination's HTTP auth gate does not authorize the queued work, and the job has no `:user_id` or other identity name. A payload key named `user_id`, `user_email`, `user_role`, `user`, `user_group_id`, `_group_id` or `_group_key` (or `user.<column>`) is refused when the file is written and is never queued: those names are the runtime's in every flow. Pass the value under a name of your own, `with: {target_user_id: '${{ user.id }}'}`, from a signed-in producer, never a request field, and read `:target_user_id` in the queued flow. A reference with no value anywhere in the step fails it and no job is queued. Authorize the producer and independently recheck stored authority/state in the worker. A request-controlled flow name is refused when the step runs; request/secret taint is preserved. Legacy enqueue also preserves `unique_key`. Queue deduplication does not replace worker idempotency. The job runs once unless the target flow declares `on.request.max_attempts` (see api(at:"async-flows") → retries).
