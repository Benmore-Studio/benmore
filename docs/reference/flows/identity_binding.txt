user_id, user_email, user_role, user, _group_id and _group_key are server-owned in every flow: request input can never set them, a step whose id is one of them does not replace them (identity_step_ids), and a `for_each` loop variable cannot take their names (checked_values → loop_variable). auth: required flows bind them from the session. Public flows bind them from the caller's session when signed in, otherwise they bind SQL NULL (a public flow cannot be handed a caller-chosen user id or tenant). That is who the caller is, not what their profile says: most columns of the `user` object are text the caller wrote (first_name, last_name, auth.signup_fields and auth.profile_fields through PATCH /api/_auth/profile or an anonymous /signup). Every `user.<col>` (and the whole `${{ user }}` object) counts as request input for `run: sql_dynamic` text and for the scheme or host of a credentialed `run: api` call, and so does any set, loop, enqueue or step output built from it, exactly like a request field. Only the account columns the framework owns stay trusted: user.id, user.email, user.role, user.verified, user.group_id/user.org_id (the session tenant), created_at, updated_at, last_login_at, deactivated_at, password_change_required, email_grandfathered and the groups: tenant key, role and active columns. Bind profile values with `:name` in a `run: sql` step; they stay ordinary data in respond, SQL params and JSON bodies. The email is identity everywhere else, but its text is the caller's choice at signup and may hold quotes and SQL comment characters, so `${{ user.email }}`, `{{user_email}}` and any value built from them are never written into `run: sql_dynamic` text; bind them with `:user_email` in `run: sql`.
