A synchronous HTTP flow has a time limit: 30 s by default, or `on.request.timeout:` (a Go duration such as `45s` or whole seconds, at least 1 s, at most 95 s on the hosted platform because Cloudflare ends a request whose answer has not started after about 100 s; self-hosted the maximum is 95 s unless the server sets `BENMORE_FLOW_TIMEOUT_MAX`). A value out of range, unreadable, or on a `mode: async` flow is refused at write time and by benmore check. Past the limit a `transaction: true` flow rolls back and answers 503 JSON `{error: "flow_timeout", outcome: "rolled_back", rolled_back: true, timeout_seconds, steps_run, failed_step, request_id, message, hint}` with header `X-Benmore-Outcome: rolled_back`: the writes made in the transaction were not kept, and a statement still running is interrupted. A flow without a transaction stops before its next step and answers 500 with `outcome: stopped` and `rolled_back: false`: statements that already ran stay committed and the remaining steps did not run, so check before sending the request again. Outbound calls already made are not undone in either case. `run: sql`, `run: sql_dynamic`, `run: api`, `run: webhook`, `run: compute` and `run: transcribe` are cut at the limit (a step `timeout:` longer than the time left has no effect); other steps finish the call they are in. An on_error handler does not run for a flow its time limit stopped. The status is not 504 because on the hosted platform Cloudflare replaces a 502 or 504 body with its own text (edge_error_status). For work that needs longer than the default, declare a longer `timeout:`, or use `mode: async` for work that can take more than a few seconds. The limit applies only to synchronous requests: async jobs, cron, data-event flows, scheduled tasks and connector reads are not bound by it. A client that disconnects does not roll back a flow. A transaction also stays under `BENMORE_DB_WRITE_TX_LIMIT` (60 s by default, api(at:"recovery") → write_lock), so a `transaction: true` flow with `timeout:` above 60 s also needs that per-app env value raised; a rollback by that limit gets the same 503 `rolled_back` answer. benmore check and the write response warn on such a flow, naming the app's current limit. On the hosted platform, when the app received a request but gave no complete answer (it closed the connection, a request other than a flow ran past the app's 30 s response limit, or the request body could not be read completely), the caller gets 500 JSON `{code: "outcome_unknown", outcome: "unknown", reason}` with header `X-Benmore-Outcome: unknown` (an HTML page without auto-refresh for a browser navigation): the request may have completed, so check its effect before sending it again. reason is `connection_closed`, `timeout`, `request_body` or `client_closed`. A 503 with `outcome: not_delivered` means the app was not reached and a retry is safe. A call the time limit cuts does not count against the host's circuit breaker (see `circuit_breaker`).
