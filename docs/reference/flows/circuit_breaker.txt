`run: api`, `run: webhook` and `run: proxy` share a circuit breaker per app and host: after 5 failures in a row the host is not called for 60 s (the step fails with `circuit open for <host>`), then one probe call decides whether it closes. What counts as a failure: a transport error (connection refused or reset, DNS, TLS), a 5xx answer, and the step's own allowance running out (`timeout:` on api and proxy steps, 30 s by default; 10 s for a webhook delivery), since a host that does not answer within what the step gives it is slow for every flow. A call cut by the flow's time limit (`on.request.timeout`, when the run had less time left than the step allows) or by the caller disconnecting (run: api and run: proxy end with the caller's request; run: webhook delivers regardless) counts neither as a failure nor as a success. In a synchronous flow the flow's limit (30 s by default) usually ends a hung call before an api step's 30 s default, so give a step that calls a host prone to hanging a `timeout:` shorter than the flow's limit if you want the breaker to stop calling it. A 4xx is the host answering and resets the count.
