A step that fails before any respond step answers 500 with one JSON object, the flow_no_response diagnostic: `message` (`Internal error (request id: <id>)`), `failed_step`, `failed_type`, `request_id` and `reason`, a fixed phrase for the kind of failure that never quotes the error (`the statement names a table that does not exist`, `a record with the same unique value already exists`, `the statement returned or changed a different number of rows than expect_rows allows`, `the upstream service answered with an error status`, ...). A step that fails inside an `if:` block or a `for_each:` loop is named itself, with its own type, reason and hint. The step's own error (`step_error`, one line with credential-shaped text redacted) and the step `hint` are in the answer only for a caller signed in to the app as an admin on a full-access credential, who then also gets the error in `message`; anyone else gets `error_detail` saying where it is. The full error is always kept under the request id: the request log row (MCP get_request_logs with request_id, benmore requests <app>) and two journal lines, `FLOW ERROR [<flow>] <error> (request <id>)` and `FLOW ERROR DETAIL [...] failed_step=... error=... hint=... request=<id>` (benmore tail <app> --grep <id>). A step that fails because the request body is over its limit answers 413 instead (request_body). A SQL step, or the transaction's begin or commit, that could not get the database's write lock in time answers 503 `database_busy` with a `Retry-After` header instead when nothing the run wrote is kept (a `transaction: true` flow, which is rolled back, or a flow in which no earlier statement wrote): send the request again (outbound calls and sends the run already made are not undone). A flow without a transaction that had already written keeps the flow_no_response answer, with `reason: the database was busy` (see api({at:'errors'}) common_envelopes). A refused `run: purge_current_user` (wrong or missing confirmation, a credential that may not erase the account) answers 400 or 403 with its reason instead (see api({at:'auth'}) → account_erasure). Every value the flow can read from the app's env, and every value derived from one, is replaced by [redacted] in step_error, `message`, the request log, the journal and an on_error handler's `${{ error }}` (error_value) (as written and URL-escaped), so a secret inside an api URL path (a bot token, a webhook path) is not shown to an app admin.
