A `${{ }}` value can be an expression in the `if:` grammar anywhere a flow writes a value (respond bodies, headers and status, SQL binds, api URL/query/headers/body, set, enqueue, email, sms, compute args, for_each): compare with == != > < >= <=, join with && || ! and parentheses, quote text literals. `&&` and `||` return an operand and comparisons a boolean, as in JavaScript and as in `if:`: `${{ params.id && 'yes' || 'no' }}` is 'yes' when id is set, `${{ params.n > 3 }}` is true. Truthiness is `if:`'s (empty, 0, false, no, null and a missing ref are falsy). A whole JSON value (`ok: "${{ params.n > 3 }}"`) is emitted as its native result (a boolean, or the operand's own value); inside text it renders as text. A whole SQL bind (with.params or inline) binds that result too: a boolean as 1/0 (see sql_boolean_params). A ref with pipes and a lone `||` fallback are not expressions (`${{ x || none }}` is the text 'none' when x is missing). Your template is parsed before any value is substituted, and a request value is only ever an operand. An expression that doesn't parse fails its step with template_unresolved, and the write gate and `benmore check` refuse it, naming the step. Request input behind `&&` or a comparison counts as request input everywhere it is checked (sql_dynamic, an api or webhook URL that carries credentials, email html escaping). Functions, arithmetic and `in` are not supported: compute those in SQL (CASE WHEN) or a compute step.
