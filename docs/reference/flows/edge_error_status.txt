On the hosted platform Cloudflare replaces a 502, 504 or 520-530 response from the app with its own text page (`error code: 502`), so a flow that answers one of them with a JSON error loses the body and its request id; the same body with 503 arrives intact. Answer 503 for an unavailable upstream, 500 for an unexpected failure, 4xx when the request is at fault. benmore check and the write response warn on a `run: respond` with a literal 502, 504 or 520-530 (520-530 are Cloudflare's own error codes), and on one whose status passes a `run: api` step's `outputs.status` through, since the upstream's 502 or 504 then reaches the caller as that page: answer 503 for those (an `if:` on the status) or a fixed status. The warning also covers a status expression that can answer one (`${{ params.code == 418 && 202 || 502 }}` in an on_error handler, `${{ params.st || 504 }}`); a number the expression only compares against (`params.code == 502`) is not warned. Respond steps inside on_error handlers are checked like any other. The framework's own upstream failures (billing portal, `<fetch>`, broadcast, email change) answer 503 and an OAuth provider pointing at a private address 500. When the platform cannot reach an app, a browser navigation gets the self-refreshing App restarting page with status 503 and any other caller 503 JSON with `outcome: not_delivered`; an app that received the request and then failed to answer gets 500 `outcome: unknown` (see `time_limits`). While the platform restarts an app (`benmore restart`, an env change) requests wait for the new process. Open SSE streams end as soon as an app process starts shutting down (EventSource reconnects to the new process).
