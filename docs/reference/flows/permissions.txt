on.request.permissions: [projects:read, tasks:read] requires authentication and every declared scope before any flow step. Scoped administrators do not bypass scopes; unrestricted direct logins retain access subject to role checks (a global admin holds every permission unless roles: declares `admin` with narrower scopes). Permission declarations use distinct explicit resource:action scopes, without wildcards. Discovery and scheduling apply the same constraint. permissions: is also how a scoped credential (an API token or Bearer session minted with explicit scopes, a connector grant) reaches a flow as its user. Where the rule is not enforced yet, it is advisory: a scoped credential calling a flow without permissions: runs it as the full account, and the app log names the flow (once per app and flow every 10 minutes) with the fix. Where the platform enforces it, an `auth: required` or `role:` flow without permissions: answers it 403 before any step, and a public or `auth: optional` flow runs for it as for an anonymous caller. An app whose integrations call flows with scoped tokens declares the scopes each flow needs (e.g. `permissions: [shifts:read]` on a read flow, `[time_off:write]` on one that writes time_off), or a capability scope (`permissions: [partner:import]`) that the integration's role grants and its tokens carry: with roles: declared a token's scopes are intersected with its roles' before the check. Unscoped credentials and ordinary sign-ins are unaffected. This does not itself enable application MCP or approve writes.
