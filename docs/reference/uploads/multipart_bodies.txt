Three routes read a multipart/form-data body: POST /api/_upload and POST /api/_files (one file part named `file`), and the auto-CRUD create POST /api/<table>, where each text part is a field and each file part is stored and its reference written to the column the part is named after. A create stores a file part only when its reference goes into the row. A file part whose field is no column of the table (a typo in the input's `name`) is not stored and is listed in the `X-Ignored-Fields` response header; one named after a column a create never takes from the request (`id`, `user_id`, the tenant key, another protected column, a workflow's state column) is not stored either and is listed in `X-Stripped-Fields`. The create itself still answers 200 with the row, so read those headers when a row comes back without its file. A file the create does store is refused like any upload: 415 for a refused type, 413 over the per-file cap, and then no row is created. An update never stores a file: PATCH /api/<table>/<id> takes JSON or a URL-encoded form. Sent as multipart with a session cookie (a browser `FormData`), its text fields are applied and its file parts are dropped; sent with an API token or a Bearer session, none of its fields are read. When no field was read it answers 400 `{"error":"No fields to update","hint":"this PATCH has a multipart/form-data body, ...","docs":"uploads.multipart_bodies"}`. To change a file column, upload the file first (POST /api/_upload) and PATCH the returned reference as the column's value in JSON. Batch, ingest and /api/_transaction take JSON or NDJSON only. A flow never receives a file: no flow step reads a file part, and the fields of a multipart body are not bound as flow params either (api({at:'parse'}) → summary). Upload the file first, then call the flow with the returned reference in a JSON body, and let the flow check that reference against a row the caller owns before it uses it.
