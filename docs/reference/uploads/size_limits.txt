Each file is capped at 50 MB. File parts over 4 MB spill to a temporary file instead of memory, and each app parses at most 8 uploads at once, at most 3 of them for one client (the signed-in user, else the client address): further uploads queue for a free slot for up to 30 s, and only then get 503 with Retry-After, so retry after the indicated seconds. A batch of more than 3 parallel uploads from one user (Promise.all) still works; the rest queue behind the user's own uploads. A file over the cap answers 413 on every upload path. A zero-byte file is accepted and stored (`size: 0`). A file whose (lowercased) filename extension is longer than 10 characters or holds anything but letters and digits is refused (415). A file with no extension is refused on the hosted platform's media storage, on every upload path, with 415 `file type not allowed: the file name has no extension, ...`, because that storage decides the served content type from the extension; send it under a name that has one (`bm.upload(file, { filename })`). An app on local disk (self-hosted) or on its own bucket (S3_BUCKET) accepts it and stores it as `<id>.`. Files sent as multipart to POST /api/<table> are stored PUBLIC (in a folder named after the table; private under compliance: hipaa, see hipaa), and a public upload cannot be deleted by the app (public_vs_private); for a private file use POST /api/_upload with kind=private and store the returned reference. A multipart request body is capped in total too: by default one full-size file plus form fields (51 MB), so a POST /api/<table> carrying several large files at once gets 413 unless the app sets MAX_UPLOAD_BODY_BYTES (bytes, at most 1 GB). POST /api/_upload and /api/_files (and bulk-import chunk PUTs) may take up to 5 minutes to send the body once the request holds an upload slot, plus 30 s for the answer. On the hosted platform Cloudflare's own limits still apply in front of the app.
