A multipart auto-CRUD create stores its files before the access, NOT NULL, member-of, idempotency, foreign-key, validator and before-hook gates run, so a create that is refused (or fails to commit) deletes the bytes it stored from the active storage backend (on the hosted platform only under the app's own prefix) and their `_benmore_upload_owners` rows before the answer returns. Deletion is best effort and logged (`discard refused upload`); the ownership row is removed only after the bytes are, so a backend that cannot delete leaves the object with its row kept (never a row-less, legacy-looking private file). Multipart is accepted on create only (PATCH takes no files). The two-step `/api/_upload` and `/api/_files` routes still store first and leave the file if the later create is refused.
