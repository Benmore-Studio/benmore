`run: delete_upload` deletes a PUBLIC upload of this app when the step proves whose file it is: `with: { path: '${{ steps.post.outputs.image_url }}', record: { table: posts, id: '${{ steps.post.outputs.id }}' } }` (the flow in deletion_example, with a public column). `record:` is required for a public file. A public URL is known to everyone who can see the file, so the flow's SQL alone does not show whose it is: without `record:` the step fails (`delete_upload refused`) and nothing is deleted. `benmore check`, and the check a file write runs, warn about a delete_upload step with no `record:` whose path names a public folder, or whose templated path may resolve to a public file in a signed-in flow. The proof is the one a private file gets with `record:` (private_ownership): `table` is a literal table of this app, the row references the file in one of its columns, and the row belongs to the uploader (`user_id`) or, on a tenant-keyed table, to the uploader's tenant. So a URL another user copied into a row of their own is refused. A file an app admin uploaded passes with any row that references it. Every public upload records its uploader (table `_benmore_public_upload_owners`: path under uploads/, user_id, group_id, uploader_admin; private uploads stay in `_benmore_upload_owners`). Two cases follow from the record: a file with no uploader record (stored by an earlier runtime, or written by a flow step instead of uploaded) passes on the row reference alone, so scope the lookup that selects the row; and a file uploaded with no signed-in user (an anonymous multipart create) has a record no row matches, so delete_upload refuses it. Accepted references: the canonical `uploads/<folder>/<file>` path (optional leading slash), this instance's exact media-CDN public URL (`https://<media CDN>/public/<sub>/uploads/...`; a dev instance's is under `<sub>-dev`, see storage_backends), or this app's exact configured-S3 URL. Everything else fails before the proof is checked and before any storage call: another app's prefix (from a dev instance, production's too), another host or port, a query or fragment, percent-encoding, dot segments, backslashes, a doubled slash, an uppercase scheme, a folder named private in another letter case, and on local disk any spelling other than the one the file is stored under. A missing object succeeds (safe retries); a storage failure fails the flow, and the ordering advice for `transaction: true` in private_deletion applies. Caches outlive the delete. Deleting removes the stored object; it does not purge copies already cached, and there is no purge step. On the hosted media CDN a public file is stored with `Cache-Control: public, max-age=31536000, immutable`, so the CDN and any browser that already fetched it may keep serving their copy for up to one year; only a request that reaches storage finds it gone. On local disk a public file is served with `Cache-Control: public, max-age=86400` outside dev mode (up to one day in a browser or proxy cache). With your own bucket (S3_BUCKET) the framework sets no Cache-Control; the bucket or the CDN in front of it decides. A file that must stop being readable the moment it is deleted belongs in the private tier (public_vs_private).
