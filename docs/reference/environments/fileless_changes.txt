A schema change that writes no migration file (a @default, type or nullability change, a removed field or @unique; see api(at:"schema") `unapplied_changes`) does not split dev's and prod's migration numbering. A generated file starts from the schema the last migration file produced, and an instance chains pending files from the same point, so both instances keep one file per change. Files generated by an older runtime keep their headers; where they break the chain, the instance generates its own file.
