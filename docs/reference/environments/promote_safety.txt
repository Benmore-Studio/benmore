A promote's preview and its destructive-change gate also read the UP section of every migrations/*.sql file the promote would copy that prod has not applied (prod's user-migration runner applies each one): a DROP TABLE of a table holding rows or an ALTER TABLE ... DROP COLUMN of a column holding values is listed under `destructive` and refused without force, like a removed model. A table the same file drops and re-creates by renaming onto its name (the generator's rebuild) is not counted. A table whose model was removed and which a copied file also drops is one entry naming both causes. Exit codes: `benmore promote <app> --dry-run` exits 0 whenever the preview itself ran, also when the promote would be refused (`would_block: true`, with `destructive` or `would_fail` saying why); it then prints a last line on stderr saying the real promote would be refused. A script reads `would_block` from the JSON. The promote itself exits 1 when it is refused. After a promote, the tool waits for prod to answer /health as healthy: a promote whose prod did not come back healthy, or whose migration is not verified, answers ok:false with `error`, `prod_healthy:false` and where to look (`benmore logs <app> --env prod`, `benmore restore <app> --env prod`), and `benmore promote` exits 1. A failed migration rolls back its own transaction, so prod data is unchanged; the promoted code stays on prod. The dashboard's publish reports verification pending in the same cases.
