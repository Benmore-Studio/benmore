A promote's preview and its destructive-change gate also read the UP section of every migrations/*.sql file the promote would copy that prod has not applied (prod's user-migration runner applies each one): a DROP TABLE of a table holding rows or an ALTER TABLE ... DROP COLUMN of a column holding values is listed under `destructive` and refused without force, like a removed model. A table the same file drops and re-creates by renaming onto its name (the generator's rebuild) is not counted. After a promote, the tool waits for prod to answer /health as healthy: a promote whose prod did not come back healthy, or whose migration is not verified, answers ok:false with `error`, `prod_healthy:false` and where to look (`benmore logs <app> --env prod`, `benmore restore <app> --env prod`), and `benmore promote` exits 1. A failed migration rolls back its own transaction, so prod data is unchanged; the promoted code stays on prod. The dashboard's publish reports verification pending in the same cases.
