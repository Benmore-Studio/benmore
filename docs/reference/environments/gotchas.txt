Custom domains are PROD-ONLY - they map to <sub>, never <sub>-dev - so never move a custom-domain (or real-user) app's data to dev; use `seed-dev` so prod + the domain keep serving and dev is a fresh copy. promote is CODE-ONLY: the first promote starts prod with an EMPTY data.db. Its schema preflight (dry_run `destructive`) refuses without force both a dropped column and a model removed from schema.prisma whose prod table still holds rows - prod's next start would drop that table (pre-migrate backup only). Renaming a model while `@@map` keeps the table is not a drop. A field that gains `@unique` gets a `uniq_<table>_<column>` index on the live table (the migration fails and retries on the next start while duplicates exist). Build-loop ops (push/sql/logs) default to the DEV instance for apps that have one - pass `--env prod` to act on production. `benmore push <file> --env prod` (or a `benmore use prod` pin) writes code DIRECTLY to prod, bypassing promote: a hotfix path that diverges prod from dev (the CLI prints a PROD warning), so run `refresh-dev` before the next promote or it overwrites the hotfix. promote is the normal path to prod.
