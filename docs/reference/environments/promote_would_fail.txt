Promote refuses code whose migration fails on prod's data. The dry run (MCP `promote` dry_run, `benmore promote --dry-run`, the dashboard publish preview) answers `would_fail: {step, error, statement}` with `would_block: true`, `benmore doctor` lists it under drift, and promote (tool, CLI, dashboard with 409) refuses before prod's code changes unless forced. Fix prod's data first (`benmore sql <app> "..." --write --confirm --env prod`, or a migrations/ file that runs before the failing step; the schema's own migration runs before every migrations/ file, so for a failing schema step promote that file on its own first), or change the schema or file on dev, then run the dry run again. The run replays a start, not a reload: what a start installs between its schema step and its migration files is in place when the files run (computed triggers, the `<column>_blind` columns of encrypted fields, the `<table>_history` tables of versioned tables), so a file promoted together with the app.yaml or encrypted.yaml that creates such a column or table is judged as prod's start will run it. It holds no encryption key: a statement that fires a trigger needing one, a run over its bound or a held write lock give no verdict and refuse nothing, and so does a file that fails after that set-up could not be replayed. Not replayed: the encryption and blind-index triggers of fields the same promote encrypts (the run has no key), deferred foreign keys checked at commit, and framework tables a start creates for the first time. Because no replay can be proven complete, `force` overrides the refusal (the same flag that accepts destructive changes): the answer then carries `warning` and `forced_would_fail`, and if the dry run was right prod fails to start or skips that file. The dashboard dialogs show the step and offer no publish button for it; `benmore promote <app> --force` is the override. After every restart the answer lists `set_aside_migrations`: the `migrations/*.failed.sql` files prod holds, which its migration runner renamed after they failed and which it runs without (one copied from dev counts too). With any, `migration_verified` is false, ok is false and `set_aside_note` says what to do; the dashboard shows verification pending and names them. A promote that would skip a failing file is refused until the file or prod's data is fixed, or forced.
