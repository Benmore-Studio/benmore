`benmore remove-production <app>` (MCP remove_production, POST /platform/apps/{name}/remove-production?confirm=<app>, the dashboard's Remove from Live button) takes an app out of production: the production instance stops and the app no longer holds a live-app slot, so another app can be published in its place. The app stays as a dev-only app. What stops: <sub>.benmore.ai and every custom domain of the app answer the 404 "App not found" page, and production's cron schedules, scheduled tasks, job workers and inbound webhooks stop with it (a provider that keeps calling a webhook gets 404). What stays: nothing is deleted. A final backup of the production database is taken first (the action fails with nothing changed when that backup fails), and the production database, uploads and environment are kept. The dev instance, source and history, the GitHub link, collaborators, env vars in every scope, custom-domain claims and their verification, managed DNS zones and records, a dedicated SMS number, Stripe Connect keys and stored backups are untouched. A managed DNS zone and a dedicated SMS number keep being billed while they exist, and the subscription and add-on quantities do not change; the kept production data still counts toward storage. Publishing again: `benmore promote <app>` brings production back on the kept data (the promote preview and its destructive-change gate judge the migration against it) and needs a free live-app slot like a first publish; see `publishing`. Who: the app owner only, from the CLI, MCP or their own dashboard sign-in; collaborators and delegated dashboard sessions are refused (403). Confirmation: the CLI asks you to type the app name (`--yes`, short `-y`, skips the prompt), MCP and HTTP take confirm=<app subdomain or display name>; without it the answer (400 over HTTP) says what would stop, what stays and what keeps being billed, and nothing changes. Answers: `{ok:true, status:'removed', production_removed_at, final_backup, final_backup_note, data_kept:true, live_apps_used, still_billed, dev_url}`; an app with no production instance answers `status:'not_published'` without error (the action is safe to repeat). An app that has only a production instance (no dev instance) is refused with 409: give it one with `benmore seed-dev <app>` first. While a promote, restore, refresh, deploy or delete of the same app runs the answer is 409; retry after it. If a step fails the answer says which state the app is in: either production was started again and the app is still published, or (rare) production is stopped while the app still counts as published, in which case the same command finishes the removal and `benmore promote <app>` brings production back. Afterwards `benmore status <app>` and GET /platform/app-status report `production: 'removed'`, `prod_published: false`, `prod_exists: false` and `production_removed_at`; `benmore apps --json` omits `url` and carries `production_removed_at`; `final_backup_note` says where the final backup is kept (on the hosted platform a stored snapshot, which `benmore restore <app> --env prod` lists under `stored_snapshots` marked `final_backup: true`); commands without --env target the dev instance, and commands aimed at production with --env prod are refused with `no_production_instance` until the app is published again (`restart`, `restore --from`, `sql` and the other commands that need a running instance; `restore --env prod` without --from still lists the kept backup files): see `no_production_instance`. `benmore publish` / `benmore unpublish` are a different thing: they only switch `features.testing` in app.yaml and never start or stop an instance.
