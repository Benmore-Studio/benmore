promote's `destructive` list and its force gate cover only what prod's start-up really deletes: the table of a removed model, and the rows or populated columns a copied migration file deletes, measured by running the file on prod in a rolled-back transaction (a drop, a rename then a drop, or a rebuild that leaves rows or a column out; api(at:"schema") migration_file_drops). Prod carries those out when it restarts, so after a forced promote the gate clears, and verification waits for the drop instead of reporting the promote unverified. Differences prod's migration never applies (a prod column dev's schema does not declare, a nullability or type change) are listed under `schema_not_applied` (dry run, promote answer, dashboard preview, `benmore status`, refresh-dev --data-only) and never block; `forced_destructive` is true only when force allowed a real drop. To remove such a prod column, ship a migrations/ file with `ALTER TABLE t DROP COLUMN c;` and promote with force. A column such a promoted migration file drops is not listed under `schema_not_applied`, and the answer of a promote lists what prod keeps as read from prod after its migration ran, so a forced promote does not list the column it just dropped.
