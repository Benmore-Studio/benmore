refresh-dev / refresh_dev require editor access and hold the app's lifecycle lock until the refreshed dev is verified. Dry runs apply nothing; full mirrors require force when they would overwrite/delete dev work, including same-size/same-time edits. Code copies require a recoverable git snapshot first. Refresh retains mandatory gitignore exclusions and refuses history that already tracks runtime data. A `files:` selection gets the same excludes as a full mirror inside a selected directory (nested *.pem, *.key, .env*, data.db, ... stay in prod). Code copies (promote, seed_dev, refresh_dev) carry regular files only: symlinks are skipped, and a selected path that is or passes through a symlink in prod or dev is refused before dev is stopped. With --data-only/--with-data, a consistent snapshot of prod's database is taken and its encrypted values are checked against prod's key before dev is stopped. A prod key that is inconsistent or cannot be read fails the refresh. Dev is taken offline and must stop cleanly before its data is replaced. Dev's database and key are preserved under .benmore/backups/before-refresh-*/ first. Prod's key is saved as dev's (dev scope) before the data is installed; a failure before installation puts dev's key back. Dev is never started automatically after an error, except after a code-only refresh that failed with dev's source unchanged (see the end of this entry). Success means dev answered healthy after the refresh. Errors set MCP isError (CLI exits nonzero) and include refresh.stage, code_state, database_applied, key_applied and recovery paths. Source may already have changed when a later step fails. code_state:partial_rollback means tracked source was restored but newly copied untracked files may remain. After installation, failure can leave the new pair installed and dev stopped, or running but unverified; inspect the stage before retrying. Restoring an old encrypted database requires its matching key; on dev, restore_db installs a preserved key record with its backup (see api(at:"recovery") restore_encryption_key), and a refresh of a dev database its key cannot read is refused with that way out. Prod data/code are not changed; real production data and its encryption key are copied into dev. Unrelated dev secrets remain scoped. A refresh is not atomic across a power loss; do not run direct writes or a key rotation on the app while one is in progress. Stopping and starting dev each have a bounded wait; copying a large database takes additional time. Production's queued work stays production's: in the copy, pending and running jobs are marked failed and pending/blocked scheduled tasks cancelled before it is installed (the response's `queue_held` counts them), so dev never re-sends production's queued email, SMS or webhook deliveries. Production's sign-in state stays production's too. Before the copy reaches dev it gets a restore's no-live-database treatment (api(at:"recovery") database_restore): every session and bearer token, API (`bmr_`) token, passkey, OAuth provider token, OAuth code and client, sign-in challenge, email-change, reset/verification and one-time-code grant is deleted, every MCP connector grant is marked revoked and its access/refresh credentials, pending authorizations and sealed upstream credentials deleted, and one `refresh_credentials` audit row in the copy records the counts; production's connector file-processing records and artifact manifests are dropped from the copy too, as on a restore with no live database. The response's `credentials_revoked` counts them per table. Accounts keep the password hashes, MFA and verification they had on prod when the copy was taken, so after a refresh nobody is signed in to dev and users sign in again with their prod password (a password changed on prod later reaches dev only with the next refresh). Dev's own credentials are not carried into the copy either: dev's accounts are different accounts, matched to prod's only by id or email, so nothing on dev can vouch for a prod credential. A dry run that copies data says so: `database` (dev's database would be replaced), `encryption_key` (swapped for production's, or unchanged when production has none) and `credentials`. The CLI's refusal names `--force` and `--dry-run` (the MCP arguments are force:true and dry_run:true). Everything dev does after that is live, though: its cron jobs, hooks, flows and webhook subscriptions run against the copied data, and platform email and SMS reach the real addresses in it. A promote's schema check reads the schema and migration files it would ship, 12 MiB at most. The copy works whether or not production is running. A `files:` selection is checked before dev is stopped, on a dry run too. A path production does not have (`selected path "x" does not exist in production`) and a list naming only protected or never-copied paths (`no valid files to copy`) are refused with `(refused before dev was touched; nothing was copied)`. A selected path whose own name the copy never carries (.DS_Store, *.failed) is skipped like a protected one. A code-only refresh (no with_data/data_only) that fails after the stop with dev's source exactly as it was (dev's database connections did not drain, the refresh was refused before copying, or git shows the rollback restored the snapshot and nothing was added) starts dev again, since no database or key was touched: the error ends `dev's code, database and key are unchanged and dev was started again` and `refresh.dev_restarted` is true. When files the copy had already added remain, or the rollback or that restart fails, dev stays stopped and the error says `dev is stopped`, names the leftover files and how to start it (restart_app with env "dev", `benmore restart <app> --env dev`). A refresh that copies data never starts dev after an error.
