Unknown/malformed recipe configuration is rejected by the write gate and when the app loads. A `verify:` map takes only recipe, header, timestamp_header, secret, previous_secret, prefix, path_param, context and skew_seconds; any other key (a misspelled `skew:`, an invented `algorithm:`) is refused by the write gate and `benmore check`, because the runtime would ignore it. Request verification failure returns 401 `Invalid signature`, with the granular reason logged server-side (`FLOW VERIFY REJECT [<flow>]: <reason>`). The granular reason is NEVER returned in the response body - that would make the endpoint an oracle. A body over 1 MiB returns 413 before any flow step runs, for both the recipe form and the `verify: stripe|github|shopify|slack|<header>` string form. A string `verify:` that is neither a provider nor a hyphen-joined header name is refused at write time and by `benmore check` (api({at:'webhooks'}) → inbound_verify); the header form reads only the header it names. The string form's sibling `secret:` takes `${{ env.NAME }}` or `{{env.NAME}}`, like the map form's secret (api({at:'webhooks'}) → inbound_verify); a secret that does not resolve rejects every request. The write gate and `benmore check` refuse on.request `secret:` without `verify:` (the route would check nothing and answer unsigned requests with 200), a string `verify:` without `secret:` (every request would get 401; the map form requires its own `secret`), and on.request `secret:` beside a map-form `verify:` (it is not read); a deployed file still loads and logs the problem.
