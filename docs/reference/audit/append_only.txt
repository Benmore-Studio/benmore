Under `compliance: hipaa` _benmore_audit_log and _benmore_read_audit are append-only: BEFORE UPDATE and BEFORE DELETE triggers abort with `<table> is append-only`, so an editor's SQL, a bulk import (Mode B restore DML) or a bug cannot rewrite history. Inserts are allowed. Framework maintenance is the one exception: the retention sweep and account erasure (it blanks the erased account's address in audit rows) still change rows. `sql(write:true)` refuses any statement naming `_benmore_audit*` or `_benmore_read_audit`, and BENMORE_AUDIT_RETENTION shorter than 6 years is ignored (logged). A BEFORE INSERT trigger refuses an insert that names an existing id, so `REPLACE INTO` / `INSERT OR REPLACE` cannot overwrite a row. At every start and reload the triggers are compared with their exact text: a missing or changed one (a migration that dropped it and created a no-op under the same name) is recreated, and any other trigger on an audit table is dropped (both logged as SECURITY). Once the triggers exist, a user migration statement or seeds.sql statement naming an audit table is refused. Not covered: authored flow/hook SQL (it ships with the app and is reviewable), a restore that swaps the database file (the triggers return at the next start), a migration that runs before the app's first hipaa start (its effect is repaired at that start), and Mode B restore INSERTs, which can still add rows. Removing `compliance: hipaa` leaves the triggers in place; drop them by hand if intended.
