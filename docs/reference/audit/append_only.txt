Under `compliance: hipaa` _benmore_audit_log and _benmore_read_audit are append-only: BEFORE UPDATE and BEFORE DELETE triggers abort with `<table> is append-only`, so an editor's SQL, a bulk import (Mode B restore DML) or a bug cannot rewrite history. Inserts are allowed, and that includes the audit rows of an approved connector command (`mcp_command_prepare`, `mcp_command_approve`, `mcp_command_commit`). Framework maintenance is the one exception: the retention sweep and account erasure (it blanks the erased account's address in audit rows) still change rows. `sql(write:true)` refuses any statement naming `_benmore_audit*` or `_benmore_read_audit`, and BENMORE_AUDIT_RETENTION shorter than 6 years is ignored (logged). A BEFORE INSERT trigger refuses an insert that names an existing id, so `REPLACE INTO` / `INSERT OR REPLACE` cannot overwrite a row. At every start and reload the triggers are compared with their exact text: a missing or changed one (a migration that dropped it and created a no-op under the same name) is recreated, and any other trigger on an audit table is dropped (both logged as SECURITY). A missing trigger is logged as `SECURITY: audit trigger <name> was missing; restoring it` (the first install of an app logs nothing). A user migration of a hipaa app cannot UPDATE, DELETE or replace audit rows, alter or drop an audit table, add or drop a trigger or an index on one, or set `PRAGMA writable_schema`, whether or not the triggers are in place: the file fails with `<table> is append-only under compliance: hipaa: a migration may not ...` (or `a migration may not set PRAGMA writable_schema ...`, which holds for every app). Whether the app is hipaa is decided before the file's first statement, from its app.yaml or from the installed triggers. Once the triggers exist, a user migration statement or seeds.sql statement naming an audit table is refused whatever it does. The app's own SQL (a flow's `run: sql` or `run: sql_dynamic` step, a hooks.yaml `sql:`, a page `<query>`) may INSERT audit rows and nothing else: an UPDATE or DELETE on an audit table, and a `REPLACE INTO` / `INSERT OR REPLACE` into one, is refused before it runs, whether or not a trigger is in place, and the step fails with a message that starts `<table> is append-only under compliance: hipaa`. Neither that SQL nor a migration can create a trigger, on any table, whose body would update, delete or replace audit rows when it fires (a trigger that INSERTs one is fine). The app's SQL also cannot drop, replace or add a trigger on an audit table, or drop, alter or shadow the tables: that holds for every app and every framework table (api(at:"schema.framework_tables")). Not covered: a restore that swaps the database file (the triggers return at the next start), a migration that ran before the app's app.yaml said `compliance: hipaa` (the triggers are installed at the first hipaa start), and Mode B restore INSERTs, which can still add rows. Removing `compliance: hipaa` leaves the triggers in place; drop them by hand if intended. On every app, with or without `compliance: hipaa`, the /_admin panel shows _benmore_audit_log and _benmore_read_audit and never writes them: their pages have no Create, Edit or Delete control, and POST /_admin/api/<audit table>/create, /update/<id> and /delete/<id> answer 403 {error:"admin_table_read_only", table, message, docs}.
