`auth.sign_in_audit: true` in app.yaml turns on the sign-in trail (yes/on/1 mean the same; any other value, and a misspelt key, is refused when app.yaml is written). It is off unless set, for every app, with or without `compliance: hipaa`; a hipaa app that must show who signed in and who was turned away should set it. With it on, _benmore_audit_log gets one `sign_in` row for every session a sign-in issues and one `sign_in_refused` row for every attempt turned away; table_name is `_benmore_users` and row_id the account's id.

`sign_in`: new_values `{"method": ...}` with `password` (the sign-in form), `token_exchange` (POST /api/_auth/token), `otp` (the emailed or texted code that completes a sign-in), `totp` (the authenticator or backup code that completes one), `mfa_enrollment` (the session issued when a required enrollment is completed), `passkey`, `oauth` (a social sign-in) or `signup` (the session a sign-up issues). The row is written in the transaction that creates the session: when it cannot be written no session is issued and the sign-in fails. A step that issues no session (a password accepted before a code is asked for) writes no row.

`sign_in_refused`: new_values `{"method": ..., "reason": ...}` with reason `invalid_credentials` (no such account, a wrong password, or a deactivated account), `invalid_code` (a wrong emailed, authenticator or backup code), `invalid_passkey`, `locked` (the account is locked after failed attempts) or `network_locked` (the client address is). user_id and user_email name the account when one matched. When none did, user_id is 0, row_id is empty and user_email holds what was typed only if it is shaped like an email address (a password typed into the wrong field is not kept). A failed write of this row is logged and does not change the answer: the attempt is refused either way.

Not recorded even with the trail on: a refusal that is not a failed credential check (an address outside `auth.domain` / `auth.allow_emails`, an unverified account, a required password change, a refused social sign-in, an expired code or link), sign-outs, and sessions that are not a person's sign-in (support sessions and act-as have their own rows: account_events; API tokens: `api_token_created`). No row holds a password, a code, a token or a session id. Addresses are stored as in every other row and blanked by account erasure (api(at:"auth.account_erasure")); a database restore copies the rows written since its snapshot (api(at:"recovery.restore_audit_rows")). Every row adds to the audit log, and refused attempts are bounded only by the lockout and the rate limits; retention is `BENMORE_AUDIT_RETENTION` (at least 6 years under hipaa).
