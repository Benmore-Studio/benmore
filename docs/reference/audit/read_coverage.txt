Read-audit events (tables in auth.read_audit, or every table under compliance: hipaa) are also recorded for flow `run: sql` / `sql_dynamic` statements that produce a result set (any SELECT, also one that matches no row, and a write with RETURNING; query_type `flow_sql`, one event per audited table the statement names; a view over an audited table is not seen), /_admin table and record pages (`admin_list`, `admin_read`), GET /api/_audit (`audit_log`: one event per audited table whose audit rows the answer returned, since they carry that table's old and new values; row_id is the request's `row_id` filter, else empty), and PDF exports (/pdf/<page> renders through the page query path, `page_query`). A read with no request (cron, background jobs, data events) records user_id 0 and `system:<query_type>` (e.g. `system:flow_sql`). An anonymous HTTP read is recorded (user_id 0, user_email `anonymous`) only under compliance: hipaa, and never for a table whose read mode is anon/everyone (public data); other apps skip anonymous reads. The client_ip column holds the reader's address (resolved like the request log; NULL on rows written by an older runtime and for system reads; account erasure clears it with user_email); GET /api/_audit/reads and get_read_audit (editors) return it. The impersonator_user_id and impersonator_email columns name the admin behind a read made through a support session (POST /api/_auth/impersonate); they are 0 and '' for every other reader, and both endpoints return them (impersonation, read_history). A failed audit write is logged (`READ AUDIT write failed` / `READ AUDIT flush failed, N read events not recorded`); under compliance: hipaa writes are synchronous and a failed one fails the read with 500. A `transaction: true` flow's events are written right after its transaction ends, committed or rolled back (the read happened either way), and a failure there is logged. Under compliance: hipaa a run that succeeds writes them inside its transaction instead, so its writes and its read events commit together: when they cannot be written the transaction is rolled back, a request flow answers 500 and keeps nothing (the request can be sent again), and a cron, queued or data-event run fails like any failed step. A hipaa run that rolls back for another reason still records its reads afterwards; a failure of that write is logged as `READ AUDIT LOST`. Not recorded: SSE/WebSocket payloads, approved connector commands (their sealed operation and audit rows record them), and dashboard backup downloads (owner-only under hipaa, api(at:"compliance") -> workforce_reads).
