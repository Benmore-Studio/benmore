Read-audit events (tables in auth.read_audit, or every table under compliance: hipaa) are also recorded for flow `run: sql` / `sql_dynamic` statements that produce a result set (any SELECT, also one that matches no row, and a write with RETURNING; query_type `flow_sql`, one event per audited table the statement names; a view over an audited table is not seen), /_admin table and record pages (`admin_list`, `admin_read`), and PDF exports (/pdf/<page> renders through the page query path, `page_query`). A read with no request (cron, background jobs, data events) records user_id 0 and `system:<query_type>` (e.g. `system:flow_sql`). An anonymous HTTP read is recorded (user_id 0, user_email `anonymous`) only under compliance: hipaa, and never for a table whose read mode is anon/everyone (public data); other apps skip anonymous reads. The client_ip column holds the reader's address (resolved like the request log; NULL on rows written by an older runtime and for system reads; account erasure clears it with user_email); GET /api/_audit/reads and get_read_audit (editors) return it. A failed audit write is logged (`READ AUDIT write failed` / `READ AUDIT flush failed, N read events not recorded`); under compliance: hipaa writes are synchronous and a failed one fails the read with 500. A `transaction: true` flow's events are written right after its transaction ends, committed or rolled back (the read happened either way); such a write cannot refuse rows already used, so under hipaa a failure there is logged as `READ AUDIT LOST`. Not recorded: SSE/WebSocket payloads, approved connector commands (their sealed operation and audit rows record them), and dashboard backup downloads (owner-only under hipaa, api(at:"compliance") -> workforce_reads).
