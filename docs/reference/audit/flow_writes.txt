The audit log records the writes the framework makes for a caller: POST/PATCH/DELETE /api/<table> (single, batch and NDJSON ingest), /api/_transaction, POST /api/_groups/create, workflow transitions, version reverts, record shares and bulk imports. A write the app makes with its own SQL is not recorded: a flow's `run: sql` or `run: sql_dynamic` step, a hooks.yaml `sql:` and a cron.yaml `sql:` job leave no row in _benmore_audit_log, with or without `compliance: hipaa`. A flow that books an appointment or signs a note is invisible in GET /api/_audit unless it writes the row itself, in the same flow as the write: an INSERT INTO _benmore_audit_log step (flow_writes_example is a whole flow file). Columns: `action` (any text; `insert`, `update` and `delete` keep the row next to the API's own under GET /api/_audit?action=), `table_name`, `row_id` (text), `user_id` and `user_email` (bind `:user_id` and `:user_email`, which a flow takes from the caller's session; a flow that runs with no signed-in caller, such as a schedule, writes its actor as a literal, e.g. 'system:nightly-close'), `old_values` and `new_values` (JSON text or NULL, see values_format). Write ids and the fields that changed, never the value of an encrypted column: the API seals those in its own audit rows, and your INSERT stores what it is given. With `transaction: true` the write and its audit row commit or roll back together. Under `compliance: hipaa` the app's SQL may INSERT audit rows and can never UPDATE or DELETE them (append_only). A hook records its write with a second `sql:` entry under the same event and table; hook SQL runs after the triggering write commits and each entry is its own statement (api(at:"hooks.durable_effects")). A cron.yaml job records its write with a second `sql:` step: a job written as one `sql:` line becomes `run:` with the write and the INSERT INTO _benmore_audit_log as two `sql:` steps. Under `compliance: hipaa`, `benmore check` and the check after a push or file write warn about a flow job whose SQL writes a table of the app when no step of that job inserts into _benmore_audit_log, about a hooks.yaml event and table whose hooks write a table when none of them does, and about a cron.yaml job whose own SQL (its `sql:` line, or the `sql:` steps of its `run:` or `steps:` list at any depth) writes a table when none of it does. It is a warning: the file is accepted. Writes to framework tables (`_benmore_*`) are not counted, a cron.yaml job that names a `flow:` is reported through that flow's file, and an app without `compliance: hipaa` gets no warning. Reads a flow's SQL makes are covered by the read audit (read_coverage).
