Hosted: accounts created, promoted or reset through the platform's create_superuser tool (and `benmore users` set-password / create, which call it) are audited in the app as superuser_created, superuser_promoted or superuser_password_reset on table _benmore_users, with user_email = the platform account that made the change and user_id 0; values carry the email and role, never the password. Setting the password of an existing account this way ends that account's sessions, API tokens, OAuth codes, MCP connector grants, passkeys and pending reset links, and clears the TOTP factor of an account that was never verified, as a reset link does, and makes the new password temporary (password_change_required: the user chooses their own at next sign-in) unless the caller passes require_password_change:false (CLI: set-password --no-change-required) for an account it controls. New accounts keep the password unless require_password_change:true. State-changing MCP tool calls (file writes, env changes, restores, reset_and_seed, promote/refresh_dev, key rotation, write SQL, create_superuser, collaborator and ownership changes, GitHub pushes) also appear in the dashboard Activity feed of the app the caller reached, as do calls that act as an app user or publish content: probe_route with `as` or a non-GET method, browser_check/browser_batch with `as`, and generate_upload_url. The app's own audit log names the user a probe acted as, so this feed is where the collaborator behind it appears.
