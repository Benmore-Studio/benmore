role:<X>, role:<a>,<b> and perm:<res>.<action> decide WHO may call an operation; the rows it reaches still follow the table's columns. On a table with a user_id column and no groups: key (the tenant root aside) a holder reaches only the rows they own (user_id = them) plus rows shared with them through record-level grants; another user's row answers 404 on read, update and delete, which reads like a missing row. So `time_off: {update: role:manager}` does NOT let a manager approve someone else's request, and `team_notes: {all: role:manager}` shows each manager only their own notes. Use `owner_or_role:manager` when holders should reach every row (owners keep their own; on a group-keyed table holders reach their tenant's rows). On a table with the groups: key, role:/perm: holders reach every row of their tenant (with no tenant, only their own rows that carry none, see scoping.missing_group); on a table with neither user_id nor the key they reach every row. Global admins (not stepped into a tenant) bypass row scope under every mode. `benmore check` and the push write gate warn on a role:/perm: read, update or delete over such a table, naming the owner_or_role: mode to use (advisory, the declaration stays legal; `role:admin` is not flagged, since only a global admin passes it there and admins bypass rows), and `benmore describe <app> table <t>` (MCP describe_table) / api(at:'table:<t>') report rows `owner` with a `hint` for that op.
