Reverts use the CRUD transaction pipeline: current update policy, write scopes, edit ACLs, locks, validation and before/after hooks apply. Protected ownership, tenant and identity fields are not restored from history, nor are command-owned columns, a workflow's state column (it moves only through its transitions) or hidden credential columns (revert_hidden). See revert_kept. A revert writes only the columns it changes: a column whose value in the version is the row's current value is left alone. Its before_update hooks get those columns as {{_submitted}} and in their SQL placeholders (api(at:'hooks') → submitted_fields), so a hook that refuses a client-set column (`when: "instr(_submitted, ',escalation_count,') > 0"`) refuses a revert only when the version holds another escalation_count than the row does. When the version differs from the row in no column a revert writes, the revert writes every column the version holds again, and all of them are in {{_submitted}}.
