A versioned table's stored versions live in `<table>_history`: the table's columns plus _version, _valid_from, _valid_to, _changed_by and _change_type, one row per replaced state. It is written only by the framework, as rows of the table are updated and deleted (and by a retention policy that removes a row's versions with the row). Nothing else writes it: there is no /api/<table>_history route, and the /_admin panel shows it with no Create, Edit or Delete control (a row opens with View). POST /_admin/api/<table>_history/create, /update/<id> and /delete/<id> answer 403 {error:"admin_table_read_only", table, message, docs} and change nothing, so the versions the endpoints list and what a revert restores are the states the rows really had. The same holds for history kept from a table that is no longer in versioned: (it is used again if the table returns to the list). Read versions with GET /api/<table>/<id>/versions and /versions/<version>, restore one with POST /api/<table>/<id>/revert/<version>. A table of your own whose name only ends in _history is not a history table: it gets its /api route and is created, edited and deleted in the panel like any other.
