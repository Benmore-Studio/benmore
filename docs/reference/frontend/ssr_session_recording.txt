Server-rendered pages carry the session recorder when app.yaml `recording:` allows it (on in dev mode, production needs `recording.production: "true"`). Its keys are `enabled`, `production` and `mask_inputs`; any other key under `recording:` is not read, and a write of app.yaml and `benmore check` warn about it. Each of the three takes true or false, and yes/no, on/off and 1/0 mean the same, quoted or not: `recording.enabled: no` turns the recorder off in dev mode and in production (pages carry no recorder and the beacon route does not exist). A value that is neither is not read, which leaves the recorder not turned off (`enabled`), production not recorded (`production`) and typed values masked (`mask_inputs`), and the same two checks warn about it. App admins read recordings at GET /_internal/recordings, so secrets are masked: anything inside a `[data-bm-mask]` element (or sdui's `[data-bm-sensitive]`) is recorded as `***` in DOM snapshots, input, click and attribute events; password inputs, inputs named (or with an id) like password/token/secret/card/cvv/ssn/otp/totp/mfa/passcode/2fa, and inputs whose `autocomplete` is one-time-code, a password or a `cc-` field lose their value attribute in snapshots and mutations as well as typed values (`recording.mask_inputs: "false"` turns that name rule off, not data-bm-mask); URL parameters with those names (a reset link's `token=`) and otpauth: URIs are masked. Put `data-bm-mask` on any element that shows a credential: an API token, a TOTP secret or QR code, backup codes. sdui MfaSetup and ApiTokenManager already do. Pages without such elements record unchanged. The beacon (POST /_internal/recording) is anonymous: each client address may send 240 batches a minute (429 past that) and an app decodes at most 4 at once (503 while busy); the recorder sends about 12 a minute per open page.
