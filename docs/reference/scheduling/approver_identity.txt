Who an approval is assigned to. approver_email is an email-keyed grant (api({at:'auth'}) email_keyed_grants): the request belongs to the account whose verified or grandfathered address is that address, in any letter case. POST /api/_approvals trims and lower-cases approver_email before it looks the account up and stores the row, so `Bob@Example.com` reaches bob; the request is bound to an account (approver_id) and notifies it only when that account has already proven the address. An account that registered the address without proving it is not bound or notified, does not get the request from GET /api/_approvals (with or without mine=1) and gets 403 `not the assigned approver` from /decide. Once the address is proven (verification link, emailed code, confirmed email change to it, provider-verified OAuth sign-in) the request is that account's to list and decide; no notification is sent for a request made earlier. A stored approver_id next to an approver_email counts only while that account holds the address in proven form: the request follows its address, so an approver who changes their email no longer lists or decides requests addressed to the old one (an admin still can). A row with an empty approver_email and an approver_id names its approver by id (only SQL writes such a row; the API never does) and is unchanged: that account decides it, verified or not. The account purge blanks approver_email on requests addressed to the erased address and clears an approver_id there that belongs to another account. In an app that never proves addresses (no auth.verify_email, auth.otp or OAuth sign-in), an account that is not grandfathered (api({at:'auth'}) email_keyed_grants) is unproven and cannot be an approver by email until it verifies.
