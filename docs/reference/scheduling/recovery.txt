A reminder left `running` by a worker that died (its claim not refreshed for 5 minutes) is put back and fires again. A kind:'flow' task left `running` is put back only when its flow declares `idempotent: true` at the top of its flow file (as for async flow jobs); any other flow task becomes `failed` with last_error `worker died while running this flow task; not run again because the flow is not marked idempotent (it may already have run some steps)`, because the table cannot tell which steps already ran. A running task refreshes its claim every minute, so a slow flow is never fired twice by the sweeper a hot reload starts, and a restart of the app process gives the sweep in progress up to 8 seconds to finish. A task orphaned more than 3 times is marked failed with last_error instead of fired again. Claim identity: a task is stamped (`claimed_at`) when it is claimed, and a run records done/failed/blocked only while the task is still `running` under its own stamp (a recovered, re-claimed run logs `SCHEDULE lost claim` and writes nothing). Transitions: pending|blocked -> running (claim); running -> done|failed|blocked (owning run only); running -> pending (orphan, recoveries+1) | failed (orphaned more than 3 times); pending|blocked -> cancelled (owner DELETE).
