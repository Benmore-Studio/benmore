POST /api/_approvals { table, row_id, approver_email, title } (row_id a string or an integer) notifies the approver. When table names an app table the requester must be able to read that row, or the request is 404: the request joins the record's approval history that every reader of the record sees. Any other table value is a free-form label. Repeating a request that is still pending (same record, approver and title) returns that approval without a second notification; one account may make 30 approval requests per 10 minutes (then 429 with Retry-After). GET /api/_approvals?table=&row_id=&mine=1 lists the approvals you requested or are asked to decide, plus every approval on table/row_id when you can read that record (an admin sees all). POST /api/_approvals/{id}/decide { decision:'approved'|'rejected', note? } - only the assigned approver or an admin on an unscoped credential (see decide_authority); notifies the requester once. The answer names what is stored. Repeating the same decision (same note, or none) answers 200 with that status and sends nothing; the opposite decision, or the same decision with a different note, on a decided approval answers 409 `{error, status:<stored>}` and changes nothing; an unknown id answers 404 (admin) or 403 (anyone else). Nobody approves their own request. POST /api/_approvals with approver_email naming the requester (same account, or the same address in any case) answers 403 and stores nothing; /decide by the account that requested the approval answers 403 even for an admin, and so do create and decide from a support-impersonation or delegated session (otherwise one admin could request as a user and approve as themselves). The check is the same account or the same address only: a second account the same person controls is not detected, and an approval already stored as self-approved keeps status='approved'. Transitions: pending -> approved | rejected; no other transition.
