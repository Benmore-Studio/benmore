Which accounts can approve a tenant's record. In an app with groups:, a request whose table is an app table that carries the groups key, on a record whose key holds a tenant, is assigned only to an approver inside that tenant: an account with a live membership in the record's tenant (api({at:'scoping'}) live_membership), or an account that can read the record anyway (a global admin, for example). The approver does not need read access to the record: on an owner-only table (access `self`) another member of the requester's tenant approves. POST /api/_approvals naming an account outside the tenant (a member of another tenant, or of none) answers 200 `{id, status:'pending'}` and stores the request, exactly as for an address no account holds, so the answer does not say whether the address has an account; that account gets no notification, does not get the request from GET /api/_approvals (with or without mine=1) and gets 403 `not the assigned approver` from /decide. The tenant is checked on every list and every decide, against the tenant the approver's session is in. An approver removed from the tenant stops listing and deciding the request; the requester and the record's readers still see it, and an admin on an unscoped credential still decides it. An account that joins the tenant afterwards lists and decides the requests addressed to it (no notification is sent for a request made earlier). A member of several tenants lists and decides a request while their session is in the record's tenant (POST /api/_switch_group). When the record has been removed from its table, only an admin decides the request; a soft-deleted record keeps its tenant. Not bound to a tenant, so any account with a proven address (see approver_identity) can be named: a record whose groups key is empty, a table without the groups key (such as the groups.bootstrap org_table or a groups.shared table), a free-form label, and every table of an app without groups:.
