Which accounts an approval reaches. An approval stays inside the tenant, or the membership, of what it is about. Table carrying the groups key, record whose key holds a tenant: the approver is an account with a live membership in the record's tenant (api({at:'scoping'}) live_membership). The groups.bootstrap org_table: the row is the tenant, so the approver is a member of that tenant. Table whose read rule is `member-of:` and that has no groups key: the approver is a member of what the record belongs to (the rule's own membership). In all three a global admin can also be named, and so can an account that the record's own row rule lets read it (its owner, a record share); an org_table every signed-in account may read is still bounded to the tenant's members. The approver does not need read access to a tenant's record: on an owner-only table (access `self`) another member of the requester's tenant approves. Free-form label (a table value that names no app table) in an app with groups:: the approver is in a tenant the requester is a live member of, or is a global admin; a requester with no tenant can name only a global admin, and a global admin's request reaches any account. POST /api/_approvals naming an account outside these bounds answers 200 `{id, status:'pending'}` and stores the request, exactly as for an address no account holds, so the answer does not say whether the address has an account; that account gets no notification, does not get the request from GET /api/_approvals (with or without mine=1) and gets 403 `not the assigned approver` from /decide. The bound is checked on every list and every decide, against the tenant the approver's session is in and the live membership rows. An approver removed from the tenant or the membership stops listing and deciding the request; an admin on an unscoped credential still decides it. An account that joins afterwards lists and decides the requests addressed to it (no notification is sent for a request made earlier). A member of several tenants lists and decides a request while their session is in the record's tenant (POST /api/_switch_group). A label request follows its requester: once the requester leaves the tenant they shared with the approver, only a global admin decides it. The requester is bounded the same way on a record: they list their own request, and are notified of its decision, only while they are in the record's tenant (or membership) or can read the record; after leaving they get neither, and get both back on rejoining. A requester always lists their own label requests. When the record has been removed from its table, only an admin decides the request and its requester still lists it; a soft-deleted record keeps its tenant. Not bound, so any account with a proven address (see approver_identity) can be named: a record whose groups key is empty, any other table without the groups key (a groups.shared table, for example), and every table and label of an app without groups: (apart from its `member-of:` tables).
