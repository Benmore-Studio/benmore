Before-hooks (before_insert/before_update, CRUD, batch, NDJSON /ingest and /api/_transaction) get {{_submitted}}: the columns the request is writing, as ",a,b," - known, non-protected columns it sent a value for. Keys the write drops (_csrf, query parameters, unknown or protected names) and the user_id / tenant key the framework fills in are not listed. Test a field with instr('{{_submitted}}', ',weight,') > 0 - e.g. to allow a client to change status and nothing else. An unsubmitted {{field}} renders as its own literal text, but a caller can send that text as a value, so don't rely on comparing against the placeholder. On an update, hook SQL placeholders are the request's values (id, the submitted columns, {{_submitted}} and the session keys) plus {{old_<column>}}, the value stored before the change, for every column: `'{{status}}' = 'approved'` asks whether this request sets status, and `{{old_status}}` is the status the row has now (a subquery such as `(SELECT status FROM orders WHERE id = {{id}})` reads it too). `when:` is different: it is judged over the row as it will be, stored columns included. A workflow transition submits no fields, so its hook SQL sees the whole row with the target state, and `old_<column>` for every column (`old_status` is the state it leaves). A version revert (POST /api/<table>/<id>/revert/<version>) submits the columns it changes: those whose value in the version differs from the row's current value, never a column the revert keeps (api(at:'versioning') → revert_kept). A guard on a submitted column therefore refuses a revert only when the revert would change that column; a revert to a version that changes nothing submits every column the version holds.
