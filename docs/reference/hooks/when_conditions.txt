`when:` on a hooks.yaml entry, a workflows.yaml transition or an on_transition entry is a SQLite condition over the event row: `when: "status = 'paid' AND old_status != 'paid'"`, `status IN ('approved','denied')`, `assignee_id IS NOT NULL`, `hold_until <= datetime('now') AND NOT EXISTS (SELECT 1 FROM exceptions x WHERE x.booking_id = bookings.id)`. The row is a one-row table named after the hook's table with every column, `old_<column>` (the value stored before the change in a before_update or on_update hook, an on_transition entry and everything a workflow transition evaluates; NULL in insert and delete hooks), the caller's user_id, user_email, user_role, user_roles and user_group_id (NULL without a session), `_submitted` on before-hooks, and the other submitted fields. The caller's keys replace same-named columns: on a table with a user_id column, `user_id` is the caller and the row's own is `old_user_id` where old_<column> is filled. Name columns directly; `<table>.<column>` is the event row and `main.<table>` the stored table. Values are bound, never pasted into the SQL, and carry their column's declared type as in a query on the table: numeric text in an Int column compares as a number, a String column compares as text (`'10' > '9'` is false there). The condition is one read-only expression (it may read other tables; no `;`, and no `?`/`:name` parameters) and is stopped after 2 seconds. NULLs follow SQL with one exception: outside subqueries `!=`/`<>` is NULL-safe (`IS NOT`), so `status != 'paid'` holds for a NULL status and `old_x != x` holds when x is first set or cleared, while next to the empty string NULL counts as empty, so `phone != ''` means "has a value". Other comparisons with NULL are false: `x = ''` is false for NULL (write `coalesce(x, '') = ''`) and so are `x < 5` / `x <= 5`. Quote text: an unquoted word is a column (`status = paid` fails). A `when:` is not a template: `{{status}} = 'paid'` is refused at write time and never matches. A condition that can't be evaluated (a template, an unknown column, a syntax error, the time limit) fails closed and is logged once: a before-hook refuses the write (422, as for hook SQL that fails), an after-hook or on_transition hook doesn't fire, a transition answers 422 `condition not met` and GET /api/<table>/<id>/transitions does not list it. For a transition the row is the stored row before the change, with the caller's keys: the state column still holds the current state, old_<column> holds the same stored values, and user_id is who makes the transition, so `when: "old_user_id != user_id"` refuses the row's owner (a requester cannot approve their own request) and `when: "old_user_id = user_id"` admits only the owner; `(SELECT user_id FROM main.<table> t WHERE t.id = <table>.id)` reads the stored owner too. The before_update, on_update and on_transition hooks that transition fires see the same keys with the state column set to the new state. An approved MCP command that moves the state is judged over the same row, with the user the command runs as for the caller. A timeout has no caller and evaluates no transition `when:`; in the hooks it fires, user_id is the row's own column and the other caller keys are NULL. The write gate and `benmore check` prepare every `when:` against schema.prisma (old_* and the session keys included) and refuse one that can't be evaluated, naming the entry (`on_update.orders[0]`, `orders.transitions.pending -> shipped`); an existing file still loads, with a warning in the app log.
