A `webhook:` entry without `body:` posts the event row as JSON: on insert and update the row as stored (typed values and the columns the database filled in, such as a `status` default and created_at), with `old_<col>` values on update. That default row leaves out hidden columns (api(at:'scoping') → hidden_columns: `api_key`, `*_token`, `*_secret` ... and their `old_` values), like a webhook subscription delivery, and the internal flags `user_admin_bypass` and `user_act_as_group_id`. Unlike a subscription's `data`, it carries the actor under the session names, as hook SQL reads them: `user_id`, `user_email`, `user_role`, `user_roles` and `user_group_id` are the signed-in caller's, even where the table has a column of that name. So when an admin edits alice's row the default body says `user_id` = the admin's id next to `old_user_id` = alice's; a subscription delivery says alice's id for both and names the admin in `triggered_by_user_id` (api(at:'webhooks') → outbound_payload). To send the row's owner from an update hook, name `{{old_user_id}}` (the stored value before the change) in `body:`, or use a webhook subscription. To send such a value on purpose, name it in `body:` (`{"key":"{{api_key}}"}`). A declared blind-index column (`<col>_blind` and its `old_` value) is the exception: no hook delivery reads it, named or not, and a `{{<col>_blind}}` placeholder is left as written (api(at:'encryption') → flow_results). A `ws:` entry without `payload:` broadcasts only `{"table":"<table>"}`, never the row: name the columns the client reads in `payload:` (`{"id":{{id}},"title":"{{title}}"}`).
