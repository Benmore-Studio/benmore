An update that sends back the mask its caller reads is not a new value. On PATCH /api/<table>/<id> (and the singleton PATCH /api/<table>), PATCH /api/<table>/batch and /api/_transaction updates, an encrypted field whose submitted value is exactly `****` is left out of the write when the caller reads that field masked on that row, and the answer names it in X-Ignored-Fields (`diagnosis,salary`; `/api/_transaction` names `table.column`, since one transaction can span tables). The usual edit form - GET the row, change a field, PATCH the whole row back - keeps the stored values. An update whose only fields are such echoes writes nothing: PATCH answers 200 `{"status":"updated"}`, batch skips the row (not counted in `updated`), and a transaction operation answers 400 `No fields to update` like any update with nothing to write. The connector's native table update (which checks value types first) drops a text echo the same way. Whether a field is dropped depends only on the caller's own masking of the row (its unmask roles and the row's owner and tenant), never on the stored value: a masked caller who sends `****` gets the same answer whether the field holds a value or is NULL (a NULL stays NULL), so the answer reveals nothing. A masked caller can still write any other value. A caller who reads the field unmasked (an unmask role, the row's owner under `self`/`owner`, an admin, or a field with no unmask_roles) writes `****` as text. `[unavailable: decryption failed]` sent to an encrypted field is dropped and named the same way for every caller, since it is never a value. A create stores what it is sent.
