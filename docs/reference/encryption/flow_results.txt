A flow's SQL step reads the table directly. Encrypted columns arrive decrypted and nothing is masked for the caller, so what a `respond` step returns is what every caller the flow admits receives: a role that reads `****` through the API reads the value through the flow. `SELECT *`, `t.*` and `RETURNING *` on a table with encrypted fields return every encrypted column in clear and, for a blind-indexed column, its `<col>_blind` value as well (blind_index: an HMAC that is equal for equal plaintexts, which every framework response strips). Select the columns the response needs by name (`SELECT id, name, dob FROM patients ...`), leave an encrypted column out unless every caller of the flow may read it, and put the flow's own authorization in its WHERE clause. An expression over an encrypted column inside SQL (`substr(ssn, -4)`) works on the stored ciphertext, not the value. Under `compliance: hipaa`, `benmore check` and the check after a push or file write warn when a `respond` step returns a SQL step's rows whole (`steps.<id>.outputs.first`, `.rows`, `.rows[0]` or `.outputs`) and that step's query selects `*` from a table with encrypted fields; the message names the columns. It is a warning: the file is accepted. A response that reads single columns (`steps.<id>.outputs.first.name`), a query that names its columns, and a row handed on through `run: set`, a loop variable or another step are not reported, and an app without `compliance: hipaa` gets no warning.
