A flow's SQL step reads the table directly. Encrypted columns arrive decrypted and nothing is masked for the caller, so what a `respond` step returns is what every caller the flow admits receives: a role that reads `****` through the API reads the value through the flow. `SELECT *`, `t.*` and `RETURNING *` on a table with encrypted fields return every encrypted column in clear. For a blind-indexed column the step's rows also hold its `<col>_blind` value (blind_index: an HMAC that is equal for equal plaintexts), which the steps of the flow can read and bind (`steps.<id>.outputs.first.<col>_blind`) and which a `respond` step leaves out of what it sends: a key named like a blind column the app declares in `blind_index:` (on any table) is dropped at every depth of the response, in a `json` body, a body that is one reference, a list or object rendered into a text body or a header (`| json` included), and a key written in the step's own `json:`. Every other column of the row is sent as before. A column that only ends in `_blind` and is declared nowhere is an ordinary column and stays. To return the value on purpose, select it under another name (`SELECT ssn_blind AS match_key`) or reference the single value under another key (`match_key: ${{ steps.p.outputs.first.ssn_blind }}`). The steps that send flow data out of the app follow the same rule: `run: webhook` (a `payload:`, a text `body:`, and the whole flow context it posts when it has no body), `run: api` (`json:`, `body:`, `form:`, `query:`, the URL and headers), `run: proxy` (the URL, `json:`, `body:`, headers and `filename:`), `run: email` (recipients, subject, `html:`, `text:`, a `template:`, attachments), `run: sms`, `run: broadcast`, `run: notify` and a `ws:` step (room and payload) leave every declared `<col>_blind` key out of a list or object they send or render, at any depth, and do not send a payload key, form field or query parameter named like one. They send every other column as before, and a single value the step references under another key (`match_key: ${{ steps.p.outputs.first.ssn_blind }}`) or the query selects under another name is sent. `run: enqueue` queues a job of the same app and passes its `with:` values on unchanged, blind value included. A `redirect` target that takes step values follows the rule too: a list or object rendered into it loses the key, and a query parameter named like a declared blind column (`?ssn_blind=...`) is left out of the address, the rest of which is sent as rendered; a target written out with no reference is sent as written. The steps of a cron.yaml job are flow steps and behave the same. A hooks.yaml delivery (`webhook:` with or without `body:`, `email:`, `sms:`, `notify:`, `ws:`) reads the event row without the declared `<col>_blind` columns and their `old_<col>_blind` values, so a `{{ssn_blind}}` placeholder in one is left as written, like a name the row does not have; hook `sql:` and `when:` read the column. To send the value on purpose, send it from a flow that selects it under another name. Select the columns the response needs by name (`SELECT id, name, dob FROM patients ...`), leave an encrypted column out unless every caller of the flow may read it, and put the flow's own authorization in its WHERE clause. An expression over an encrypted column inside SQL (`substr(ssn, -4)`) works on the stored ciphertext, not the value. In every app with encrypted fields, with or without `compliance: hipaa`, `benmore check` and the check after a push of the flow file, of app.yaml or of the schema warn when a `respond` step returns a SQL step's rows whole (`steps.<id>.outputs.first`, `.rows`, `.rows[0]` or `.outputs`) and that step's query selects `*` from a table with encrypted fields; the message names the encrypted columns the response carries in clear. It is a warning: the file is accepted. A response that reads single columns (`steps.<id>.outputs.first.name`), a query that names its columns, and a row handed on through `run: set`, a loop variable or another step are not reported.
