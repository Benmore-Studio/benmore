A computed.yaml `expr:` or `sql:` field, or an app.yaml `aggregates:` sql, that reads an encrypted column is refused when written (write_file, edit_file, `benmore push`, `benmore deploy`) and is an error in `benmore check`, on the file that holds it. They run in SQLite on the stored ciphertext: `substr(ssn, -4)` stored hex from the ciphertext (a new value on every write and key rotation, readable by viewers who see ssn masked), `length(col)` the plaintext's length, and `SUM(salary)` a silent 0 (/api/_query refuses SUM/AVG/MIN/MAX over an encrypted column for the same reason). A write of encrypted.yaml (or app.yaml `encrypted:`) that newly encrypts a column such a field reads is refused naming the field, unless `benmore deploy` writes the fixed computed.yaml or app.yaml in the same batch. The columns a field reads are resolved by SQLite against the schema, so `patients.ssn`, `NEW.ssn`, aliases, joins and subqueries count and a same-named column of an unencrypted table does not. A null test (`col IS NULL`, `col IS NOT NULL`) and `COUNT(col)` work on ciphertext and stay allowed; `benmore_decrypt(col)` does not, since it would copy plaintext into a column every reader sees unmasked. Keep the derived value in its own plain column written where the plaintext is: from the client with the record, or in the flow that writes the record (`substr(:ssn, -4)` in its `run: sql` step). An app that already has such a field keeps loading and computing what it did; the next write of computed.yaml or app.yaml is refused until it is changed.
