fields: works on ANY declared column type, not just TEXT. An INTEGER/REAL column gets the same trigger machinery - the value is stringified deterministically (50000 → "50000", 1.5 → "1.5" via shortest round-trip), encrypted, ciphertext lands in the column. On read the framework consults the column's declared schema type and coerces the decrypted string back to int64/float64, so GET /api/paychecks/15 returns "wages_cents": 50000 (number), not "50000" (string). blind_index: works the same (HMAC of the stringified plaintext). Filters follow blind_index above: only = and __in, and only on a blind-indexed column; `?wages_cents__gt=10000`, `__lt`, `__ne`, `__like`, `sort=`/`orderBy=` on it, or equality on a column without a blind index answer 400 naming the column. /api/_query refuses value aggregates (sum/avg/min/max) and group_by on encrypted columns too. Range/sort/aggregate on encrypted ciphertext is genuinely unsupported; keep a non-sensitive derived column (band/bucket) in plaintext if you need it.
