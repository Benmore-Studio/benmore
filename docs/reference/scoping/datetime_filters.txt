A list filter or sort on a DateTime column (declared DATETIME, DATE or TIMESTAMP, which reads return as RFC 3339 UTC) compares instants when the value is an ISO-8601 date or date-time (`2026-01-15`, `2026-01-15T00:00:00Z`, `2026-01-15T05:00:00+05:00`, `2026-01-15 00:00:00`; without a zone it is UTC): `?created_at__gte=` with `new Date().toISOString()`, `?due=` with the value a read returned, `__gt`, `__gte`, `__lt`, `__lte`, `__ne`, `__in` (when every value of the list is one), `?count=true`, `?page=` totals and `?cursor=` pages alike; `?sort=` / `?orderBy=` on a DateTime column order by instant too (created_at and updated_at are the exception, below). A column holds whatever spelling its writer sent (CURRENT_TIMESTAMP writes `2026-01-15 10:00:00`, a browser `...T...Z`, some clients an offset or a bare date); the comparison is by instant whatever the spelling. Instants compare to the millisecond. A value that is no date (`?due=2026`, `?due=someday`) and `__like` compare the stored text; a stored value SQLite cannot read as a date (free text, or a number such as a Unix timestamp) is compared as text and sorts before every date when ascending; encrypted columns keep their own rules. Cost: equality and range filters use an index on the column. A sort on `created_at` or `updated_at` stays the plain ORDER BY an index on the column serves: no request can write either column, and the framework writes them only as CURRENT_TIMESTAMP (`2026-01-15 10:00:00`: the column default and the @updatedAt trigger) and, for updated_at on an update, the same form with fractional seconds (`2026-01-15 10:00:00.123456789`); that text already orders as its instants. This applies when the column's default is CURRENT_TIMESTAMP (Prisma `@default(now())`) or datetime('now'), and to an updated_at with no default; a value put there in another spelling by SQL you wrote (a flow, a hook, a trigger, a migration, a SQL restore) sorts by its text, while filters on it compare instants. A sort on any other DateTime column orders by instant and reads every row the filters match instead of walking an index on that column: on a large table narrow it with a range filter, or page by id with `?cursor=`. URL-encode the `+` of an offset as %2B. POST /api/_query does the same (api({at:'query'}) datetime_filters).
