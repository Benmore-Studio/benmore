A membership row grants access only while it is live. Rows with deleted_at set (when the membership table has that column) never count, and `groups.active_field: <column>` (optional, app.yaml) additionally requires that column to be truthy on the groups membership table (NULL, '', 0, '0', 'false', 'no', 'off' are inactive). This applies everywhere membership is checked: tenant resolution, groups.role_field, POST /api/_switch_group (403 for an inactive membership; 400 for an API token, which has no session row to hold the tenant), the group user directory, tenant bootstrap, scheduled-flow execution, member-of: EXISTS guards and ws_rooms: joins (active_field applies to those only when their table is the groups table). A session's cached tenant is re-checked on every request, so deactivating or soft-deleting a member takes effect on their next request; admins keep the tenant they switched into. An active_field that is not a column name is rejected at load; one naming a column the table lacks grants no membership (fail closed). Generic CRUD (update, batch, /api/_transaction, revert, admin panel) changes active_field on the groups table only for a caller acting inside the row's own tenant (effective group = the row's key) or an admin who bypasses row scope; anyone else gets 403. A deactivated member has no tenant, so owning the row (user_id) or a share on it does not let them switch it back on. Without a declared rule on the table, switching another member on or off takes a tenant admin (see membership_management). Example: `groups: { table: company_members, key: company_id, user_field: email, active_field: active }`.
