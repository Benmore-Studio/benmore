A row of a table with the groups: key belongs to the tenant in its key column. The rule in one line: rows meant to stay with their owner whatever tenant they name: declare `self`; everything else needs the tenant. A signed-in user with no tenant (never joined one, removed from it, or holding only a membership that is not live) reaches no row that carries a tenant under `group`, the implicit default (no access: rule for the table), `owner_or_role:`, `role:`/`perm:` or `member-of:`: owning the row (user_id), a role or a membership row is not enough. This holds on every per-row surface: list, read by id, ?include=, /api/_query (rows and aggregates), ?count=true, ?q= search, /api/_my-data, versions and revert, locks, signed URLs for the row's files, sharing, update and delete, and the row's realtime events. A member removed from a tenant therefore loses the rows they created there on their next request, and reaches them again when the membership is restored. The exception is an action whose rule you DECLARE as `self` (the table's `read:`/`update:`/`delete:` key, its `all:`, the `<table>: self` shorthand, or the global `default:`): there the owner reaches their own row with or without a tenant, action by action. A global `access.default` of `self` counts as declared for every table and action it applies to (those with no rule of their own); only a table with no rule and no `default:` is on the implicit default. Use it for rows a non-member owns on purpose, such as a request to join a tenant that carries the tenant's key and that its requester lists and withdraws (`join_requests: { read: self, write: off, update: off, delete: self }`, written by a flow). A removed member keeps reading exactly the rows whose user_id is theirs on a table declared `self`, so do not declare it for tenant content. On a table that is not declared `self`, a user with no tenant reaches only: rows explicitly shared with them (permissions.tenant_boundary), and their own rows whose tenant key is NULL, empty or 0, which is what a create by a user with no tenant stores (the key is filled only from the caller's tenant). Those rows stay outside the tenant the user joins later: its tenant clause matches only rows that carry its key. On the groups membership table itself a user with no tenant also READS the rows that name them as the member (groups.user_field is them: their user id, or for an email-keyed table an address their account has proven), in whichever tenant, active or not, whoever wrote the row and whether or not the table has a user_id column: a member whose only membership is switched off through groups.active_field lists it with GET /api/<membership table>, so a pending-invitation or access-switched-off screen can show it. This holds where a live member reads the roster through the tenant: no rule on the table, `read: group`, `role:`/`perm:` the caller passes, or `member-of:`; under a declared `self` or `owner_or_role:` the owner rule decides as it does for a live member, and `admin`, `off` or a role the caller does not hold close the table to them. It is a read of those rows and nothing more. Such a row gives no tenant and no tenant role, so every other tenant table stays closed and ?include= expands no tenant row from it; the roster's realtime events do not reach them; a soft-deleted row is not listed; another member's row answers 404, the rows they created about other members included. A user who has a tenant (a live member, an admin who stepped into one) reads that tenant's roster as before, without their switched-off rows elsewhere. Under `read: group` the answer is the list, the single read, ?count=true, ?q= and /api/_query; the row's versions, lock state and signed file URLs answer only where the table's read rule lets a user with no tenant call them (`member-of:`, or no rule on a membership table that has user_id). Changing the row is a separate decision: when its user_id is also theirs they may leave by deleting it (unless the table's delete rule is `group`, which needs a tenant); every other change, switching it back on included, is refused (live_membership, membership_management). A list answers 200 with what is in scope (an empty page during onboarding) rather than 404; under `group` mode a create, update or delete by a user with no tenant answers 403 with a hint to join or create a tenant. `read: anon` and `read: everyone` are not row-scoped and read every row whatever its tenant. Admins who bypass row scope are unaffected, and so are tables without the groups: key.
