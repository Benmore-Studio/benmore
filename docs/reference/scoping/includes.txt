?include=<relation> expands related rows through the same row scope as a direct read of the related table. A relation is named by a related table name or by the model's Prisma relation field name: `notes CaseNote[]` on Patient → GET /api/patients?include=notes, a pointer `referredBy Patient? @relation(fields: [referredById], references: [id])` → include=referredBy; each expands under the name you asked for. Table names resolve first (a `<name>_id` FK or an FK to table `name` gives the parent; a table `name`/`name`+s with an FK to this table gives children), then the relation field; a back-relation uses the other model's pointer with the same @relation label, else its only pointer to this model. When a table has two FKs to the same table, a table-name include takes the conventional `<singular>_id` column - name the relation field to pick the other. Parents come back as an object, children (any back-relation, list or not) as an array. An include entry that names no relation, or nests past 4 levels, is listed in the X-Ignored-Params response header as `include=<entry>` (an entry that resolves but finds no readable row is applied, children as []). A point-in-time read (?as_of=) applies no include and lists every entry there. A has-many include returns at most 100 children per parent row, lowest ids first; when a list was cut, the parent row carries `_include_truncated: ['<relation>', ...]` - page the children through GET /api/<child>?<fk>=<id> instead. Includes nest at most 4 levels. Repeated entries resolve once, and one request may name at most 32 distinct include entries (400 beyond that). One request's includes fetch at most 10000 related rows in total, across every entry and level. Parents are expanded in answer order until the budget is spent; a row the budget did not reach gets no expansion and carries the relation in `_include_truncated`, like a cut child list, so page those rows or narrow per_page. Entries sharing a first segment (include=tasks,tasks.comments) fetch that relation once.
