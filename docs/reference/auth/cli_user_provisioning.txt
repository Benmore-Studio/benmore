Create a hosted app user with `benmore users <app> create <email> --password-stdin [--role <role>] [--first-name <name>] [--env dev|prod]`; standard input is bounded to 64 KiB and strips only terminal CR/LF, and empty input or combining `--password-stdin` with `--password` is refused. Existing `--password <pw>` remains compatible but warns that the secret is exposed in argv and shell history. `create` has no flag for a temporary password: the account keeps the password it is created with. To have the user choose their own at first sign-in, create the account, then run `benmore users <app> set-password <email> --password-stdin`, which marks the password temporary unless `--no-change-required` is passed. CLI calls the separate `create_app_user` tool, which is create-only and refuses existing email without changing credentials or role; an older platform that lacks this tool refuses safely. `benmore users <app> list --all --env dev` includes inactive accounts for preflight. `benmore users <app> delete <email> --confirm --env dev` accepts one explicit dev/prod environment (also --env=dev), overriding the saved pin; `-y` is accepted in place of `--confirm`. Without --env the saved pin or server default still applies. Missing confirmation, malformed or duplicate environment flags, and extra positional emails refuse before dispatch. Deletion remains permanent; inspect the app marker and intended environment first. It erases the sign-in and the framework's data about the user; the app's own rows and the files the user uploaded stay (account_erasure), so remove those first. `benmore users <app> set-password <email> --password-stdin [--promote] [--no-change-required]` reads the new password from standard input with the same limits; the argument form `set-password <email> <new-password>` works and warns. set-password refuses an unknown option and a second password.
