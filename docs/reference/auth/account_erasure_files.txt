What an account deletion does with the files the account uploaded depends on whether an app flow runs.

`run: purge_current_user` removes no file. The step runs inside the app's own flow and that flow decides: the stored files stay, the app rows that reference them stay, and a signed URL already issued for one keeps working until its expiry or the object's deletion. Remove the person's own files in the flow before the purge step: select the account's file references with an owner-scoped SQL step, `run: delete_upload` each one (a public upload needs `record:` naming its row, and cached copies of it outlive the delete, api({at:'uploads'}) → public_deletion), delete or detach the rows, then `run: purge_current_user`. A flow that deletes many files, or must not call storage inside its transaction, writes the references to a table of its own and `run: enqueue`s a worker flow that deletes them after the commit. Files the person shared with others can be left in place on purpose. `benmore check`, and the check a file write runs, warn about a purge flow that has no `run: delete_upload` step and enqueues no flow; ignore the warning when the app stores no user uploads or keeps them deliberately.

The deletions that run no app flow remove the account's private files themselves, once the erasure has committed: operator deletion (`benmore users <app> delete`, MCP delete_app_user) always, and /settings/delete-account (and the hosted dashboard's Delete account) in an app that has no flow running `purge_current_user`. An app with such a flow has decided for itself what happens to a person's files, so /settings/delete-account there erases the account and removes no file, exactly as the flow's step would without a delete: its JSON answer carries `"private_files":"left to the app's erasure flow"` in place of the counts, and no audit row for a cleanup is written. The rule follows the flows the app has loaded, so adding or removing the flow changes it at the next reload. Every private file whose recorded uploader is the account (api({at:'uploads'}) → private_ownership) and that it did not upload as an admin is deleted from the app's storage, including one attached to another person's row or shared in a tenant, and a signed URL already issued for it stops working at once (404 on local storage, 403 on the media CDN). An app whose users share private files with each other, and that wants those to outlive the uploader's account, offers its own deletion flow with `run: purge_current_user`; the built-in page then leaves files alone, and `features.account_settings: false` turns it off altogether (api({at:'auth'}) → account_settings).

A private file the account uploaded while it was an admin is kept: it stays stored, a signed URL for it keeps working and the rows that reference it keep serving it, because a file staff attached to someone else's record is the app's record; remove one with an app flow (`run: delete_upload`). Also not removed: public files (remove one with an app flow: `run: delete_upload` with `record:` naming its row); private files with no recorded uploader (stored by a flow step, or before uploaders were recorded); and app rows, which keep their reference to the deleted file and the erased account's id, so delete or detach those rows yourself, before or after. On a dev instance only the dev instance's own files are removed: a file production stores that a copied row references stays (api({at:'uploads'}) → storage_backends, dev_instance_prefix).

The answer carries three counts: `private_files_removed`, `private_files_failed` and `private_files_kept_admin`. Operator deletion adds a `files` sentence. /settings/delete-account answers a request that asks for JSON (`Accept: application/json`) with 200 `{"ok":true,"deleted":true,"redirect":"<sign-in path>","private_files_removed":N,"private_files_failed":N,"private_files_kept_admin":N}`; a form post is redirected to the sign-in page as before. A file the storage did not delete is counted as failed, named in the app's log and stays stored; it never undoes the deletion, and the deletion cannot be repeated for the erased account, so delete such a file with a flow (`run: delete_upload`). A file that was already missing counts as removed. The cleanup has a time limit and counts what it had not reached as failed: about 15 seconds for /settings/delete-account, about two minutes for operator deletion.

A cleanup that found at least one private file writes one `_benmore_audit_log` row: action `account_upload_cleanup`, table_name `_benmore_users`, row_id the erased account's id, new_values `{"removed":N,"failed":N,"kept_admin":N}` and nothing else (no file name, no address). user_id and user_email name who asked: the account's own id with no address for a self-service deletion, the operator's address for operator deletion. It follows the `account_purge` row of the same erasure.

Operator deletion finds the account by its email whether it is active or deactivated, so an account can be cut off first and erased later without reactivating it. An account already erased has no email and is not found.
