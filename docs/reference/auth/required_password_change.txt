Trusted provisioning/reset flows can set _benmore_users.password_change_required=1 alongside the password hash and revoke existing credentials in the same transaction. The platform create_superuser tool does this by default when it resets an existing account. The flag is protected from profile, signup and generic CRUD writes. Pending accounts cannot authenticate normal sessions, API tokens or scheduled actions. Browser sessions are directed to GET /auth/change-password; APIs return 403 password_change_required with a redirect. POST /api/_auth/change-password accepts current_password, new_password, confirm_password and CSRF (form or JSON; bearer login sessions use normal CSRF exemption). Requires an unscoped login outside impersonation/act-as, a different valid password of at most 72 bytes, and invalidates all sessions, the support sessions the account started as an admin (`support_sessions`), API tokens, OAuth codes, MCP connector grants, passkeys and reset links atomically before clearing the flag. Sign in again afterward. Password-reset links can also complete the change. So does the claim of an UNVERIFIED pending account by its proven owner (a verified OAuth sign-in, or the emailed verification link of an account with no password): the claim replaces the password with a random one and revokes every credential, so the temporary password is gone and the flag is cleared with it. A verified or grandfathered pending account is not claimed and keeps both the temporary password and the flag. The password-only /api/_auth/token exchange refuses pending users; complete interactive login (including configured OTP) first. This gate does not prove who owns a shared bootstrap password; keep email verification/OTP or issue unique credentials.
