Admin-only management surfaces need an admin with an unscoped credential (admin = the users.role column or a global, unexpired admin grant in the role join table; the /_admin panel counts the grant too): the /_admin panel, GET /api/_audit, /api/_webhooks (create, and list/delete beyond your own), /api/_jobs, schema field and aggregate endpoints, analytics, metering, read audit, recorder, feedback and POST /api/_testing/reset, key rotation and blind-index backfill. A request with no valid credential (signed out, an expired or idle-ended session, a revoked token) gets 401 `{"error":"authentication required"}` there, as on every other route, and a signed-in caller who is not such an admin gets 403 (`admin required` on most of them). An admin's scoped API token (bmr_/bma_) or scoped Bearer session gets 403 there; row visibility is unchanged, so an admin's orders:read token still reads every order. The /_admin panel shows the credential tables and never writes them: _benmore_sessions, _benmore_api_tokens, _benmore_passkeys, _benmore_oauth_tokens, _benmore_oauth_codes, _benmore_oauth_clients, _benmore_email_changes, _benmore_password_resets, _benmore_otp, _benmore_signin_challenges and the connector's _benmore_mcp_grants, _benmore_mcp_credentials, _benmore_mcp_authorizations and _benmore_mcp_connection_credentials have no Create, Edit or Delete control there, and POST /_admin/api/<table>/create, /update/<id> and /delete/<id> answer 403 {error:"admin_table_read_only", table, message, docs} (the audit tables too: api(at:"audit") -> append_only). Sessions, tokens, passkeys and reset grants are created and revoked through the sign-in and account endpoints; to cut an account off, set deactivated_at on its _benmore_users row, which the panel does edit (admin_panel_accounts lists what it writes on that row and what it never does). Persistent API tokens (bmr_/bma_) cannot mint further tokens. Mint from a login session outside act-as/support impersonation; requested scopes must be a subset of current permissions. A token minted from a scoped session (explicit app scopes, or a dashboard embed) or from a POST /api/_auth/token exchange session expires no later than that session, even when `expires_in` is empty or longer (the response carries the resulting `expires_at`); a token minted from an interactive sign-in keeps the requested expiry, none when `expires_in` is empty. Explicit token scopes are intersected with current role grants on every request. Resource wildcards retain their action limit: *:read never grants write/delete/custom actions. A scoped credential (an API token, Bearer session or connector grant minted with explicit scopes; '' and '*' are unscoped) should reach a flow as its user only through the flow's `on.request.permissions:`; a flow that declares none is run by a notes:read token, writes included, as the full account. The rule is ADVISORY: such a call runs, and the app log names the flow once per app and flow every 10 minutes (`flow <name> [<app>]: a scoped API token or session (scopes ...) ran it as its full account ... declare on.request.permissions:`). Where the platform operator enforces the rule, an `auth: required` or `role:` flow that declares none answers 403 (`declare permissions: on the flow, or call it with an unscoped credential`) before any step, a public or `auth: optional` flow runs as for an anonymous caller (no user_id/user_email bound), scheduling refuses such a flow and /_internal/flows.json omits it. Declare permissions: on the flows your integrations call. A server-rendered page is outside a credential's scopes in the same way, with no setting that changes it: a scoped API token or scoped Bearer session passes a page's auth/role/require gates as its account, and the page's `<query>` tags and gotmpl queries (and GET /pdf/<page>, which renders the page) return what that account may read, tables the scopes do not name included. Scopes narrow the generated API (/api/<table> and its batch, ingest and transaction routes, /api/_query, `?include=`, version history, realtime events) and nothing else, so an integration that must not see what the account's pages show needs an account of its own. Minting, listing and revoking tokens: api_tokens. GET /api/_auth/users and /api/_auth/users/{id} need `_benmore_users:read` (or `*:read`) on a scoped credential, checked against the credential's own scopes like /api/_notifications' `_notifications:<action>`; the access: rule still decides whom it lists. Unscoped credentials and ordinary sign-ins need no such scope.  Account management needs an unscoped credential (a login session, or a session/API token whose own scopes are empty or '*'): PATCH /api/_auth/profile, POST /settings/profile, POST /settings/password, GET/DELETE /api/_auth/sessions, GET/DELETE /api/_auth/api-tokens (minting keeps its subset-of-current-scopes rule), MFA setup/verify/disable, and GET/DELETE /api/_auth/oauth-tokens return 403 for scoped tokens. GET /api/_auth/profile stays readable with any credential. An account holds at most 100 live API tokens, counting the ones it creates (bmr_) and the ones OAuth clients were issued for it (bma_), expired rows excluded: past that POST /api/_auth/api-tokens answers 409 {error:"api_token_limit", limit:100} and the OAuth code exchange answers 400 access_denied (the code is spent) until a token is revoked (DELETE /api/_auth/api-tokens/{id}) or expires. POST /api/_auth/token is never refused for volume, but an account keeps only its newest 200 live sessions from that exchange: each further exchange ends the oldest one, so a client must keep and reuse the token it was given rather than rely on one issued more than 200 exchanges ago. Interactive sign-ins, support sessions and dashboard embeds are not counted or ended.
