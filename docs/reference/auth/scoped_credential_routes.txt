A scoped credential (an API token, Bearer session or connector grant issued with explicit scopes; '' and '*' are unscoped) is held to its scopes on the routes beside the generated API that are about one table's rows. They ask it for that table's scope, `<table>:read` to read and `<table>:write` to change, and refuse with the 403 /api/<table> answers (`{"error":"scope denied: token does not have <table>:<action> permission","docs":"rbac.gotchas"}`): POST /api/_approvals and POST /api/_approvals/{id}/decide need write on the approval's table and GET /api/_approvals?table= needs read; POST /api/_scheduled with `table` and DELETE /api/_scheduled/{id} need write on the task's table and GET /api/_scheduled?table= needs read; saving or deleting a view at /api/_query/views needs write on the `table` of its spec; GET /api/_presence needs read, and POST /api/_presence/heartbeat write, on the membership table the slug's `ws_rooms` pattern names. A list that names no table (GET /api/_approvals, GET /api/_scheduled, GET /api/_query/views) holds, for a scoped credential, only the entries of tables its scopes read. An entry that names no table has no scope to ask for and is refused with the same 403 (`scope denied: ... names no table ...`): an approval on a free-form label, a reminder without `table`, a saved view whose spec has no `table`, a presence slug no `ws_rooms` pattern matches. Only a wildcard resource (`*:read`, `*:write`) covers those. A `kind: flow` task without `table` follows the flow rule (credential_limits). Private files need no rule of their own: /uploads/private/... and an image transform of a private file answer a signed link and no credential, and GET /api/_signed_url signs one only for a credential that reads the owning record. Unscoped credentials and ordinary sign-ins are answered on all of these as the account, whatever an app's `roles:` scopes name. The account's own routes (sessions, tokens, passkeys, billing) refuse a scoped credential whatever its scopes: credential_limits.
