A scoped credential (an API token, Bearer session or connector grant issued with explicit scopes; '' and '*' are unscoped) is held to its scopes on the routes beside the generated API that are about one table's rows. They ask it for that table's scope, `<table>:read` to read and `<table>:write` to change, and refuse with the 403 /api/<table> answers (`{"error":"scope denied: token does not have <table>:<action> permission","docs":"rbac.gotchas"}`): POST /api/_approvals and POST /api/_approvals/{id}/decide need write on the approval's table and GET /api/_approvals?table= needs read; POST /api/_scheduled with `table` and DELETE /api/_scheduled/{id} need write on the task's table and GET /api/_scheduled?table= needs read; saving or deleting a view at /api/_query/views needs write on the `table` of its spec; GET /api/_presence needs read, and POST /api/_presence/heartbeat write, on the membership table the slug's `ws_rooms` pattern names. A broadcast slug and a WebSocket room are room names too, held to the same membership table: POST /api/_broadcast/subscribe and GET /api/_broadcast/stats/{slug} need read, and POST /api/_broadcast/publish, /heartbeat and /stop write; on /ws a `join` needs read and a `broadcast` message write, and a refused join or send is answered with an `error` frame for the room whose `body` is the same sentence. POST /api/_upload and POST /api/_files store a file for a scoped credential only when the request names the app table the file is for in a `table` field (multipart field or query parameter, any letter case) and the credential holds that table's write scope; `table` changes nothing else, and an unscoped caller needs none. A list that names no table (GET /api/_approvals, GET /api/_scheduled, GET /api/_query/views) holds, for a scoped credential, only the entries of tables its scopes read. An entry that names no table has no scope to ask for and is refused with the same 403 (`scope denied: ... names no table ...`): an approval on a free-form label, a reminder without `table`, a saved view whose spec has no `table`, a presence slug, broadcast slug or WebSocket room no `ws_rooms` pattern matches, an upload whose `table` is missing or names no app table. Only a wildcard resource (`*:read`, `*:write`) covers those. A `kind: flow` task without `table` follows the flow rule (credential_limits). Private files need no rule of their own: /uploads/private/... and an image transform of a private file answer a signed link and no credential, and GET /api/_signed_url signs one only for a credential that reads the owning record. Unscoped credentials and ordinary sign-ins are answered on all of these as the account, whatever an app's `roles:` scopes name. The account's own routes (sessions, tokens, passkeys, billing) refuse a scoped credential whatever its scopes: credential_limits. So do the other routes that act for the account and name no table, with 403 `account management requires a full-access sign-in: ...`: POST and DELETE /api/_devices (a registered device receives the account's push notifications), GET /api/_usage, POST /api/_feedback and GET /api/_feedback/{id} (GET /api/_feedback answers it the empty list a caller without access gets), and GET /api/_webrtc/ice, except in an app with `features.ws_anonymous: true`, where signed-out callers are handed TURN credentials and a scoped credential gets that same anonymous answer. The two reporting routes open to signed-out visitors record a scoped credential as one: POST /api/_errors stores its report with no user id or address, and POST /api/_analytics does not tie the visitor to the account. A scoped credential still reads its own role and tenant (GET /api/_auth/profile, GET /api/_auth/act_as), and a scoped Bearer session may move itself to another of the account's tenants with POST /api/_switch_group: scopes name tables, never tenants, and an API token holds no tenant to switch.
