The /_admin panel gives every table a list page (/_admin/<table>) and a record page (/_admin/<table>/<id>), and writes through POST /_admin/api/<table>/create, /update/<id> and /delete/<id>. It creates, edits and deletes rows of the app's own tables and of _benmore_users; the other framework tables and version history are shown and never written (admin_panel_accounts). A search index is shown and never written either: the full-text index of a `@@fulltext` table (<table>_fts) and the tables SQLite keeps it in (<table>_fts_data, _idx, _docsize, _config), like every other virtual table and its shadow tables. SQLite updates them as the indexed table's rows change; their pages have no Create, Edit or Delete control, and the three write routes answer 403 {error:"admin_table_read_only", table, message, docs} and change nothing. An app table whose name only looks like an index table's is written like any other. A table admin.yaml hides (`tables: {<table>: {hidden: true}}`) is not in the panel at all: it is left out of the sidebar, of the dashboard's Total Records count and of the Related lists on other tables' record pages, /_admin/<table> and /_admin/<table>/<id> answer as an unknown page does, and POST /_admin/api/<table>/create, /update/<id> and /delete/<id> answer 404 and write nothing. Its stored versions (<table>_history) are hidden with it, in the same way. So are the rows the framework keeps about it: the dashboard's Recent Activity leaves them out, and so do the list, search and record pages of every framework table that names the table in a `table_name` column (the audit log, the read audit, record locks, custom fields, imports), whose record count is then the count of the rows listed. Hiding a framework table also removes what the panel shows from it elsewhere: `_benmore_users` takes away the Users tile, the Recent Users list, the accounts in the panel's search and the user count in the header; `_benmore_sessions` the Active Sessions tile and the session count in the header; `_benmore_usage` the Page Views and API Requests tiles; `_benmore_audit_log` the Audit Trail tile and Recent Activity; `_benmore_feedback` the Feedback link and /_admin/feedback. The name is matched without regard to letter case, in admin.yaml and in the URL. Hiding a table changes the panel only; /api/<table> and the table's access: rule are unaffected. The create and edit forms of every table offer an input for exactly the columns a create or an update stores from a request. They have none for the primary key, user_id, created_at, updated_at, deleted_at, a computed column, a workflow's state column, a command-owned column, a blind-index column, or the role column of the membership table (groups.role_field); the tenant key has an input on the create form of an admin who has not stepped into a tenant, and none on the edit form; on the membership table the edit form has none for the member column either. The record page shows those columns as read-only values, and has no Save button when no column of the row can be edited. A request that names one of them anyway is answered as on /api/<table>: the value is dropped and named in X-Stripped-Fields, or refused 403 `field_owned_by_command` for a command-owned column. The Tools page (/_admin/tools, linked in the sidebar when the app has one) lists the app's admin tools with a Run button each: every POST flow without a path parameter whose on.request.role names `admin`, alone or in a list (`role: admin`, `role: [admin, finance]`; letter case does not matter). A flow gated only on other roles is not listed there, though an admin may call it.
