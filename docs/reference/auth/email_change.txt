Changing an account's email is two-step. PATCH /api/_auth/profile with {email, current_password} (or POST /settings/profile) verifies the password, then emails a single-use, one-hour link to the NEW address and returns 202 {status:'pending_verification', pending_email} (other fields in the same PATCH still apply; the response then carries _email_change). The email changes only when the link is confirmed: GET /settings/confirm-email?token= shows a confirm form (opening the link changes nothing, so mail scanners and link previews can't confirm it) and its POST /settings/confirm-email {token, _csrf} applies the change. Confirming also takes proof of the account that asked for the change, because the link goes to an inbox the requester names and its reader could be talked into pressing a button: in a browser signed in to that account (a direct sign-in) the button is enough; anywhere else the form asks for that account's password (POST field `password`; wrong password 403, five wrong tries lock it for 15 minutes with 429, and the link is not spent). On success the address is marked verified and every session, API token, OAuth code and connector (MCP) grant for the account is revoked, and unused reset links for the old address are cancelled, so the user signs in again and re-creates any tokens. An address already used by another account returns 409. An address that was sent 3 confirmation links in the last 15 minutes (from any account of the app) returns 429 and the earlier link keeps working. One account can ask for 5 changes an hour: the sixth returns 429 whatever address it names, also with the earlier link kept. If the confirmation email cannot be sent, nothing changes. On the benmore.ai dashboard itself the email is also the platform account, so a change there is refused (403, or an error on the settings form) and pending links are not applied; support changes it. Email is an authorization input (tenant membership, record shares and invites resolve by it), which is why it must be proven.
