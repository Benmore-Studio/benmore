Password sign-in treats account state consistently. (1) A deactivated account (_benmore_users.deactivated_at holds anything but NULL) answers exactly as a wrong password does, with the right password too: POST /login says `Invalid credentials` (JSON 401), POST /api/_auth/token answers 401 `{"error":"invalid credentials"}`, the same bcrypt work runs and a failed attempt counts toward the per-account and per-IP locks; no session or token is issued. No other sign-in method issues one either: a social (OAuth) callback, managed or with your own client, returns to the login page with `Invalid credentials` and leaves the account as it is (not verified, not claimed, no provider token stored); a passkey answers its generic 401; an emailed-code or authenticator step already under way ends and the person is sent back to sign in. The sign-in never says an account is deactivated; tell the person through your own channel. To deactivate an account on a hosted app, run `benmore users <app> deactivate <email> [--env dev|prod]` (MCP deactivate_app_user; editor access): it sets `deactivated_at` on the account's `_benmore_users` row to the current time, and an account that is already deactivated keeps its timestamp. An app admin does the same in the /_admin panel: open `_benmore_users`, edit the row and enter a timestamp such as `2026-01-31 12:00:00` in Deactivated At. It takes effect on the account's next request: its sessions and API tokens answer 401 `authentication required` without being deleted. To reactivate, run `benmore users <app> reactivate <email> [--env dev|prod]` (MCP reactivate_app_user), or empty Deactivated At in the panel and save: both store NULL, the account signs in again and its unexpired sessions and tokens work again, so change the password or revoke the sessions as well when the person should sign in afresh. Each command answers JSON with the account's state `before` and `after` (`state`: `active` or `deactivated`, and the stored `deactivated_at`) and an `action` (`deactivated`, `already_deactivated`, `reactivated`, `already_active`), and writes an audit row (`app_user_deactivated` / `app_user_reactivated`; api(at:"audit") -> account_events). An account is active only while `deactivated_at` is NULL, and the framework reads the column that one way everywhere: every sign-in method, sessions and API tokens, the user directory (GET /api/_auth/users), the auto_memberships `all_users` filter, the account behind a queued job, a scheduled task, a webhook subscription or a support session, and the count of usable admins. A row that holds an empty string there is a deactivated account exactly like one with a timestamp, and is reactivated with the reactivate command or by emptying the field in the panel and saving. Write `deactivated_at IS NULL` in your own SQL for "active"; `COALESCE(deactivated_at, '') = ''` takes an empty-string row for active, which the framework does not. The panel refuses to deactivate the app's last usable admin (409). A deactivated admin is not a usable one and is not counted, so the last admin who can sign in cannot step down, be demoted or delete their account beside admins who are all deactivated; reactivate one of them first. If no admin can sign in at all, reactivate one with `benmore users <app> reactivate <email>`. The CLI command does not refuse it: the account is deactivated, the result carries a `warning` and the CLI prints it as a `WARNING:` line, because no account can manage the app until that one is reactivated or another admin is created (`benmore users <app> create <email> --password-stdin --role admin`). (2) With `auth.require_verified: true`, an account whose email is unverified gets no session or token. After the right password, POST /login and POST /signup answer 403 `{ok:false, error:"email_verification_required", message}` and POST /api/_auth/token answers 403 `{error:"email_verification_required", message}` (no `ok` field); signup adds `account_created: true` (the account exists and signs in once verified), and a browser form returns to the login page showing the message. bm.auth.signIn/signUp throw with err.code `email_verification_required` and the message. A wrong password still answers `Invalid credentials`. With `auth.verify_email` on, a refused sign-in also mails a fresh verification link (at most one per 5 minutes; the signup link lasts an hour). An `auth.otp` app (email identifier) is not stopped at the password, because its emailed code verifies the address. Because signup sets no session cookie here, opening the verification link in the same browser asks for the account's password once, as on another device. Passkey sign-in answers `email_verification_required` too. (3) A request carrying an existing session or token of such an account (issued before require_verified was turned on) gets 401 `{error:"email_verification_required", message}` from auto-CRUD, GET /api/_auth/profile and auth-required flows; an unknown or expired credential gets the generic `authentication required` 401 with the hint "Sign in again or use a current token".
