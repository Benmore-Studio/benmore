Password sign-in treats account state consistently. (1) A deactivated account (_benmore_users.deactivated_at set) answers exactly as a wrong password does, with the right password too: POST /login says `Invalid credentials` (JSON 401), POST /api/_auth/token answers 401 `{"error":"invalid credentials"}`, the same bcrypt work runs and a failed attempt counts toward the per-account and per-IP locks; no session or token is issued. The sign-in never says an account is deactivated; tell the person through your own channel. (2) With `auth.require_verified: true`, an account whose email is unverified gets no session or token. After the right password, POST /login and POST /signup answer 403 `{ok:false, error:"email_verification_required", message}` and POST /api/_auth/token answers 403 `{error:"email_verification_required", message}` (no `ok` field); signup adds `account_created: true` (the account exists and signs in once verified), and a browser form returns to the login page showing the message. bm.auth.signIn/signUp throw with err.code `email_verification_required` and the message. A wrong password still answers `Invalid credentials`. With `auth.verify_email` on, a refused sign-in also mails a fresh verification link (at most one per 5 minutes; the signup link lasts an hour). An `auth.otp` app (email identifier) is not stopped at the password, because its emailed code verifies the address. Because signup sets no session cookie here, opening the verification link in the same browser asks for the account's password once, as on another device. Passkey sign-in answers `email_verification_required` too. (3) A request carrying an existing session or token of such an account (issued before require_verified was turned on) gets 401 `{error:"email_verification_required", message}` from auto-CRUD, GET /api/_auth/profile and auth-required flows; an unknown or expired credential gets the generic `authentication required` 401 with the hint "Sign in again or use a current token".
