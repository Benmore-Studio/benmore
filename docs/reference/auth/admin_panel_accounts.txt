The /_admin panel lists, creates, edits and deletes _benmore_users rows with these limits. Never written through it, on create or update, whatever the request sends: role, password_hash, the password_change_required flag, totp_secret, backup_codes, mfa_last_totp, mfa_last_totp_at, mfa_setup_nonce, email_grandfathered and created_at (and id on an update). The create and edit forms have no input for them; the user page shows role, email_grandfathered, created_at and the password_change_required flag as read-only values and changes role with its own form (POST /_admin/set-role). POST /_admin/api/_benmore_users/create or /update/<id> naming one of them saves the other fields and lists the dropped names in the X-Stripped-Fields response header (an update also in `stripped_fields`); an update that names nothing else answers 400 `No fields to update`. So a password is set only by its account (sign-up, a reset link, POST /settings/password) and a TOTP factor is enrolled and removed only by its account (POST /api/_auth/mfa/setup, /verify, /disable): no admin gives another account a factor, replaces it or clears it from the panel, and a row created there starts with no password and no factor. Written through it: username, email, phone, first_name, last_name, avatar_url, verified, deactivated_at, last_login_at and the columns the app added to the table. A change to a sign-in identifier is an identity change: `email` on every app (it selects the account, receives its reset links and emailed sign-in codes, and is what a social sign-in is matched on), and `phone` or `username` when auth.identifier names it. On ANOTHER admin's account (role admin, or an unexpired global admin grant; a deactivated admin too) it is refused: 403 {error:"admin_identifier_protected", message, docs} and nothing in the request is saved; that admin changes their own address (email_change). On any other account, and on the admin's own, it is saved, and in the same transaction every session, API token, OAuth code and connector (MCP) grant of the account is revoked, unused reset links for the old address are cancelled and a pending email change is dropped, as when an email change is confirmed: the account signs in again under the new identifier and re-creates its tokens, and an admin who changes their own address is signed out. The password, the TOTP factor and `verified` are left as they are. An edit that sends the identifiers back unchanged (the edit form sends every field) revokes nothing. Deactivating, unverifying or deleting the app's last usable admin is refused 409 (api(at:"rbac") -> gotchas). To cut an account off, set deactivated_at; session_revocation ends a single session.
