The /_admin panel lists, creates, edits and deletes _benmore_users rows with these limits. Never written through it, on create or update, whatever the request sends: role, password_hash, the password_change_required flag, totp_secret, backup_codes, mfa_last_totp, mfa_last_totp_at, mfa_setup_nonce, email_grandfathered and created_at (and id on an update). The create and edit forms have no input for them; the user page shows role, email_grandfathered, created_at and the password_change_required flag as read-only values and changes role with its own form (POST /_admin/set-role). POST /_admin/api/_benmore_users/create or /update/<id> naming one of them saves the other fields and lists the dropped names in the X-Stripped-Fields response header (an update also in `stripped_fields`); an update that names nothing else answers 400 `No fields to update`. So a password is set only by its account (sign-up, a reset link, POST /settings/password) and a TOTP factor is enrolled and removed only by its account (POST /api/_auth/mfa/setup, /verify, /disable): no admin gives another account a factor, replaces it or clears it from the panel, and a row created there starts with no password and no factor. Written through it: username, email, phone, first_name, last_name, avatar_url, verified, deactivated_at, last_login_at and the columns the app added to the table. A change to a sign-in identifier is an identity change: `email` on every app (it selects the account, receives its reset links and emailed sign-in codes, and is what a social sign-in is matched on), and `phone` or `username` when auth.identifier names it. On ANOTHER admin's account (role admin, or an unexpired global admin grant; a deactivated admin too) it is refused: 403 {error:"admin_identifier_protected", message, docs} and nothing in the request is saved; that admin changes their own address (email_change). On any other account, and on the admin's own, it is saved, and in the same transaction every session, API token, OAuth code and connector (MCP) grant of the account is revoked, unused reset links for the old address are cancelled and a pending email change is dropped, as when an email change is confirmed: the account signs in again under the new identifier and re-creates its tokens, and an admin who changes their own address is signed out. The password, the TOTP factor and `verified` are left as they are. An edit that sends the identifiers back unchanged (the edit form sends every field) revokes nothing. No admin takes admin away from ANOTHER admin, by any route: POST /_admin/set-role to a non-admin role, and on the role API a DELETE of the global admin grant (also `?group_id=all`), a PATCH that gives it an expiry, or a POST that re-grants it with one, answer 403 {error:"admin_demotion_protected", message, docs} and change nothing, unless the account stays an admin through its other standing (the role column beside the grant, or a global admin grant with no expiry beside the role). An admin steps down from their own account. Role grants (_benmore_user_roles) are shown in the panel and never written there: POST /_admin/api/_benmore_user_roles/create, /update/<id> or /delete/<id> answers 403 {error:"admin_table_read_only"}; grant, extend and revoke roles with the role API (api(at:"rbac")). Granting admin to an account stays open. Deactivating, unverifying or deleting the app's last usable admin is refused 409 (api(at:"rbac") -> gotchas). To cut an account off, another admin's included, set deactivated_at: a deactivated admin keeps the admin role, so their address stays protected; session_revocation ends a single session. _benmore_users is the only framework table the panel writes. Every other table whose name starts with `_benmore_` is shown there and never written, whichever feature it belongs to: its list and record pages have no Create, Edit or Delete control (a row opens with View), and POST /_admin/api/<table>/create, /update/<id> and /delete/<id> answer 403 {error:"admin_table_read_only", table, message, docs} and change nothing. Change such a table through the endpoint of its feature, which applies that feature's checks: role grants (_benmore_user_roles) through the role API (api(at:"rbac")); record permissions (_benmore_permissions) with POST /api/<table>/<id>/share and DELETE /api/<table>/<id>/share/<permissionId> (api(at:"permissions")); record locks (_benmore_locks) with POST and DELETE /api/<table>/<id>/lock (api(at:"locks")); background jobs (_benmore_jobs) are queued by async flows and `run: enqueue`, retried with POST /api/_jobs/<id>/retry and removed with DELETE /api/_jobs/<id> (api(at:"async-flows")); scheduled tasks (_benmore_scheduled_tasks) with POST /api/_scheduled and DELETE /api/_scheduled/<id>, and approvals (_benmore_approvals) with POST /api/_approvals and POST /api/_approvals/<id>/decide (api(at:"scheduling")); webhook subscriptions (_benmore_webhooks) with POST /api/_webhooks and DELETE /api/_webhooks/<id> (api(at:"webhooks")); custom fields (_benmore_custom_fields) with POST /api/_schema/<table>/fields and DELETE /api/_schema/<table>/fields/<name> (api(at:"schema")); notifications (_benmore_notifications) through the notification endpoints (api(at:"notifications")); saved views (_benmore_saved_views) with POST /api/_query/views and DELETE /api/_query/views/<id> (api(at:"query")); push devices (_benmore_devices) with POST and DELETE /api/_devices; feedback (_benmore_feedback, _benmore_feedback_comments) with POST /api/_feedback, PATCH /api/_feedback/<id> and POST /api/_feedback/<id>/comment; analytics funnels (_benmore_funnels) with POST and DELETE /api/_analytics/funnel; imports (_benmore_imports) through /api/_import (api(at:"import")); sessions, tokens, passkeys and the other credential tables through the sign-in and account endpoints (credential_limits). The rest are kept by the framework as the app runs and are not edited by hand: the audit tables, the migrations ledger, usage, analytics and request records, upload owners, sign-in attempt and rate-limit state, idempotency keys, presence and broadcast state. The stored versions of a versioned table (<table>_history, also the history kept from a table that is no longer versioned) are shown and never written in the same way, with the same 403: they are recorded as the table's rows are replaced, read with GET /api/<table>/<id>/versions and restored with POST /api/<table>/<id>/revert/<version> (api(at:"versioning") -> history_table). The panel creates, edits and deletes rows of the app's own tables, one whose name only ends in _history included. Hidden tables, search index tables, what the create and edit forms offer and the Tools page: admin_panel_tables.
