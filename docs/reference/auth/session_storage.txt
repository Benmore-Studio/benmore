The session cookie / Bearer session token is the credential; _benmore_sessions.id stores only `sha256:` + hex SHA-256 of it (as reset links and API tokens are stored), so a backup, SQL console or query_db read of the table, of impersonation rows or of act-as audit entries yields no working login. A presented value already in stored form is refused. Raw ids stored by an older runtime are rekeyed at startup, so an upgrade signs no one out. Rolling back to a runtime without hashing signs everyone out. GET /api/_auth/sessions keeps listing the same 12-hex-digit id (the token's SHA-256 prefix) for DELETE /api/_auth/sessions/{id}; MCP revoke_session and the dashboard revoke accept the stored id or the token. App SQL that matched `_benmore_sessions.id` against a cookie value must hash it first. Ending support impersonation hands the admin a fresh session token for the same session row (the original cookie value is not recoverable from its hash); a second end of the same impersonation returns 409. Over HTTPS the session cookie is __Host-benmore_session (host-only, Secure, Path=/), so another app on a sibling subdomain cannot set or shadow it; plain-HTTP development uses _benmore_session, which HTTPS requests ignore. Upgrading from a release that used _benmore_session signs everyone in again once.
