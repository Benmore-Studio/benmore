Passkeys (WebAuthn: Face ID, Touch ID, Windows Hello, a phone) are on by default; `auth.passkeys: false` turns them off. In an `auth.oauth_only: true` app they are off unless app.yaml sets `auth.passkeys: true` (a passkey signs in without the identity provider). Browser: `await bm.auth.passkey.register('MacBook', { password })` while signed in adds one (direct sign-in + CSRF; not an API token, scoped session, impersonation or act-as). Adding a passkey re-confirms the account like MFA setup: pass `{ password }` (the current password) or `{ mfa_code }` (an authenticator code); the proof is optional within 10 minutes of a sign-in on this browser (password, OAuth such as Google, or passkey; not impersonation, act-as, a scoped token, an API token or a Bearer-presented token), so an OAuth-only account can add one by signing in again; otherwise the options call answers 400, and a password or code that is sent is always checked (wrong password 403), `await bm.auth.passkey.signIn()` signs in with any passkey saved for the site (discoverable credentials, no email needed), `bm.auth.passkey.list()` / `.remove(id)` manage them and `.supported()` is false where the browser lacks WebAuthn. Routes: POST /api/_auth/passkeys/register/options (body {password} or {mfa_code}) + /register, GET /api/_auth/passkeys, DELETE /api/_auth/passkeys/{id}, DELETE /api/_auth/passkeys (removes all of the caller's passkeys), POST /api/_auth/passkeys/login/options + /login. User verification (biometric or PIN) is required, so a passkey sign-in satisfies MFA (TOTP) for an account that has enrolled it; it does not enroll a factor, so under auth.require_mfa_for_roles an account of a listed role without one gets `{mfa_setup_required: true, redirect}` and the setup cookie instead of a session (see api(at:"mfa") existing_credentials); apps with auth.otp still send the emailed or SMS code before issuing the session (`bm.auth.passkey.signIn()` then takes the browser to the code page). Each challenge is single-use (a signed cookie plus a hashed database nonce). It still honors deactivation, auth.domain/allow_emails, the per-network lockout and the grandfathered-email check. The relying party is the host the page is served from, so a passkey made on the -dev URL, the prod URL or a custom domain works only there. Up to 20 per user; account deletion erases them; a password reset (reset link, operator set-password, or finishing a required password change), the OAuth claim of an unverified address and a verify-link claim delete them (a signed-in password change keeps them unless it sends revoke_passkeys=1); a database restore keeps the live set. Stored in _benmore_passkeys (public keys only); each passkey keeps the user handle it was registered with, so a changed server secret does not break signing in with it.
