`auth.idle_timeout: 15m` (a duration, at least 2m; "0" or absent = off) ends a session with no counted request for that long: the next request carries a dead credential (401 / redirect to sign-in) and the row is deleted. Counted: any request except the SSE/WebSocket re-checks of an open stream (they enforce the timeout but are not activity). Applies to cookie and Bearer sessions in `_benmore_sessions` (including connector consent pages), not to `bmr_` API tokens, which keep their own expiry. The row's `last_seen_at` (unix seconds; 0 reads as created_at) is touched at most once a minute, so the effective timeout is up to a minute shorter, never longer. Under `compliance: hipaa` the default is 15m and a longer value (or 0) is refused by the write gate, `benmore check` and the loader. The SDK's own timers do not count as activity: POST /api/_presence/heartbeat (bm.presence, every 18 s), POST /api/_broadcast/heartbeat and a record-lock acquire/renew (POST /api/{table}/{id}/lock) are authenticated and refused when idle but never touch last_seen_at. Every request carrying `X-Benmore-Background: 1` is treated the same way: bm.js sends it on requests made with nobody at the tab (a live query's refetch after a realtime event, bm.live.scoped refreshes, the heartbeats), so an open tab still times out. A timer in the app's own code (a custom setInterval fetch) must send the header too (`api.get(path, {background: true})`, or `bm.query.fetch(key, fn, {background: true})`), or it counts as a click and the page never times out. Sending it can only shorten the sender's own session. A malformed auth.idle_timeout (or one under 2m) is refused by the write gate, `benmore check` and the loader for every app. Ending a support session counts as the admin's activity: the session handed back is not idle (`support_sessions`).
