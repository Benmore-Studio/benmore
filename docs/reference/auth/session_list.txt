GET /api/_auth/sessions returns the caller's own live sign-ins as {sessions:[{id, created_at, expires_at, ip, user_agent, current}]} (id is a 12-hex-digit handle, never the credential) and DELETE /api/_auth/sessions/{id} ends one; both need an unscoped credential. The list holds only sessions the person started. A support impersonation session (POST /api/_auth/impersonate) and a session platform tooling minted to act as the user are rows under the same user id, but they carry the support admin's address and browser, so they are not listed and DELETE answers 404 for their ids. Support access is recorded in the audit log instead (action `impersonate`, and impersonator_user_id / impersonator_email on every row written through the session). A password change or reset still ends every session of the account, support sessions included. Through a support or delegated session both endpoints answer 403: the list is the owner's to see and end. Ending one of an admin's own sign-ins here also ends the support sessions started from it (`support_sessions`).
