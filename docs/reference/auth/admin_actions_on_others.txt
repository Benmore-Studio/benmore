Five admin-only actions need the admin's unscoped credential (a sign-in, or a session/API token whose own scopes are empty or '*'), like the surfaces in credential_limits: reading a published app's feedback (GET /api/_feedback and /api/_feedback/{id} with features.feedback on and testing off), the detailed GET /health report (checks, uptime), stopping another user's stream (POST /api/_broadcast/stop), releasing another user's lock (DELETE /api/<table>/<id>/lock) and deciding an approval assigned to someone else (POST /api/_approvals/{id}/decide). No scope names these, so an admin's scoped API token or scoped Bearer session (say notes:read, minted for an integration) gets what the same account would get without the admin role: the feedback list answers [] and the detail 403 `admin required`; /health answers 200 with status, version, instance_id and reload_generation but no checks or uptime (the status and ?deep=1 readiness are the same for every caller, so a monitor that reads only those needs no admin credential); stop answers 403 `not the publisher`; release answers 403 `only the lock owner can release this lock`; decide answers 403 `not the assigned approver`, for an unknown id too. It still stops its own stream, releases its own lock and decides the approvals assigned to it, and it sees the same rows. An integration that needs one of these calls it with an unscoped token or from a sign-in. Step-in (POST /api/_auth/act_as) and an admin's switch to any tenant (POST /api/_switch_group) accept an admin's scoped session: they choose the tenant of the caller's own session and reach nothing outside its scopes.
