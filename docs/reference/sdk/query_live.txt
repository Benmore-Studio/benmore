Render a cached read from a subscription. bm.query.tableKey(table, opts) is the key bm.query.table(table, opts) caches under for the same arguments: opts.key when you pass one, otherwise a key derived from the table and the request (select, where, group_by, aggregates, order_by, limit). staleTime, staleMs, force and live are not part of it, and the derived key is the default key of bm.query.read for the same request, so the two share one entry. bm.query.read(spec, {key}) caches under the key you name. bm.query.subscribe(key, fn) calls fn at once with the current {data, error, updatedAt, pending} (data is undefined before the first read), when a read of that key starts and when it settles, so a subscriber to the read's key renders the first read and every refetch; a subscriber to any other key stays at undefined without an error. Working example: api(at:"sdk.query_live_snippet"). bm.query.read/table register their keys for live invalidation unless live:false. Named change events refetch that table's registered keys. A tableless {action:'refresh'} hint (used for private/member-of changes) refetches all registered live keys, so another authorized member's edit reaches cached lists and summaries. Generic and named hints coalesce over the existing 50ms window; unrelated custom caches and keys never registered for live updates are untouched. Refetches use the current server access rules. Session changes cancel queued invalidations and clear the live-key registry; older pending reads cannot replace the refreshed data.
