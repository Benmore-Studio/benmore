Table events come from auto-CRUD writes AND from flow `run: sql` / `run: sql_dynamic` writes (after commit), so a bm.live() view of a table that only flows write refreshes by itself - no polling fallback needed. In a multi-instance cluster (BENMORE_CLUSTER=true) table, presence and notification events reach the streams of every instance, within about a second; room messages stay on the instance that sent them. A flow can also message a WebSocket room directly with `run: broadcast` (api({at:'flows'}) → broadcast_step).
