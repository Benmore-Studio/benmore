A transition's `role:` (each listed role, see role_lists) passes for a platform admin, for the _benmore_users.role hierarchy, for an exact role match on the caller's live membership row in their CURRENT effective tenant, or for a role grant in _benmore_user_roles counted as a `role:` access rule on the workflow's table counts it: a grant for the caller's current tenant only when the table carries the groups key, otherwise only a global grant (group_id NULL); expired grants never count. `admin` (any letter case, alone or in a list) is the exception to the membership-row match: on a table without the groups key that the app does not list in groups.shared, it passes only for a global admin (`_benmore_users.role` = admin or an admin grant with no group), never for a tenant member whose membership role is `admin`, because the table has no tenant column to keep one tenant's admin to its own rows; on a table with the groups key the tenant's admin passes for rows of its own tenant. A transition the tenant's own admins make on such a table names a tenant role with a name of its own (`org_admin`), or the table gets the groups key. `benmore check` and the post-write check warn about a transition that names `admin` there in an app whose tenant members can hold that role. Membership authorization reads groups.role_field when configured; only apps without that setting use the membership table's `role` column. A missing, NULL or empty configured field never falls back to that `role` column. Another tenant's role, a missing current tenant, and inactive or soft-deleted membership grant no membership authority; email-keyed membership requires a verified address. Approved MCP commands recheck the same configured field inside their commit transaction. SSR user.app_role, user_app_role and {{#role}} sections use this configured per-tenant role too (a `{{#role "admin"}}` section opens for a global admin only, api({at:'ssr'}) mustache).
