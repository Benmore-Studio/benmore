A state can only be retired while no live row holds it. Rows in a state workflows.yaml does not declare have no transition or timeout out of it and PATCH refuses the state column, so the hosted write gate (write_file, edit_file, `benmore push`) refuses a workflows.yaml that removes or renames a state live (not soft-deleted) rows hold, naming table, field, state and row count; an app that is not running is not checked. `benmore check` (check_app's checks against the running app) reports rows already stuck in an undeclared state however they got there (flow SQL, an import, an older file). There is no automatic state migration (a config-driven bulk UPDATE would skip audit, hooks and webhooks). `promote` runs the same count against PROD's rows for the workflows.yaml it would ship and refuses without `force` (dev may hold none of the rows prod does). Not covered: apply, feature_install, the legacy archive deploy and git_revert write workflows.yaml without this check (`benmore check` reports the result). The check is check-then-act: rows moved into a state between the count and the write or reload are stranded anyway, and it compares with the workflows the instance serves now (a failed or pending reload makes that stale). To retire a state: keep it declared with a transition to its replacement, move the rows through POST /api/<table>/<id>/transition, then remove it. An encrypted state column is not counted.
