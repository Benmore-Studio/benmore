A timeout transition is a full update. The state change, the on_transition hooks, the table's on_update hooks, webhook subscriptions and the audit row (`transition`, `_trigger: timeout`, system actor) commit in one transaction, shared with a user transition; on_update flows and realtime events run after the commit. A timeout has no caller, so hook context keys stay the row's own. The on_transition and on_update hooks of a timeout are queued as durable jobs in that transaction (as webhook subscriptions are), never run as inline SQL, and a hook whose `when:` cannot be evaluated is skipped: a hook that needs a session value or fails cannot roll the timeout back (it fails as a job, with the job worker's retries). If the transaction itself fails (audit, webhook queueing, the database), the whole timeout rolls back and the checker retries that row after 1m, then 2m, 4m ... up to an hour between attempts (each sweep takes at most 500 rows per state, oldest first, and re-checks the deadline inside the transaction, so a row edited after it was selected is left alone); before_update hooks do not run for a timeout. Hook context: `{{user_id}}` is the row's own user_id column (the owner, not who caused the move), and `user_email`/`user_role` are NULL.
