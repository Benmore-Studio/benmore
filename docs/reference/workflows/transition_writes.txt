User and timeout transitions advance updated_at as a PATCH does, with the same precision. Rapid state cycles invalidate prior edit tokens, and a clock behind the stored version never moves it backward. A transition is an update of the state column and passes the same gates as PATCH: update access mode, write scope, CSRF (cookie sessions), row scope, record locks (409 while another user holds the lock), before_update hooks, audit, on_update hooks/flows, webhook subscriptions and realtime broadcast. The write is conditioned on the state it was validated against: if the row changed meanwhile the response is 409 `state changed` and nothing is applied - re-read and retry. PATCH cannot set the state column directly (a PATCH that sends it names it in X-Stripped-Fields and answers a `hint` pointing at the transition route), and a create can set it only to `initial`. before_update hooks see the merged target row (the state column already holds the target state), as PATCH does, so a guard keyed on the new state fires.
