A YAML test reads a saved value back as `{{name}}`. The names: each `save:` entry of an earlier step; `{{user_id}}`, the id of the `as_user` account (also replaced in `setup:` SQL); and the session token of each of the test's accounts, `{{<local part>_token}}` (`{{bob_token}}` for bob@example.com, from `as_user` or `users:`; two emails with the same part before `@` share the name and the later one keeps it). `{{name}}` is replaced in a step's path, its `sql`, its `set_auth`, the values of its body (`data`, `json`, `json_array`, `ndjson`), the names and contents of `files`, and every text of `expect`: `redirect`, `contains`, `not_contains`, the paths and values of `json` and the values of `headers`. A value is written as it is and is not read for another variable. `save` on a request step takes a top-level field of a JSON object response; a field that is missing or null saves nothing. In `expect`, a `{{name}}` (letters, digits, `_`, `-`) that nothing saved fails the step before it runs, with a message that names the variable and the ones saved so far; so does a `contains`, `not_contains` or `redirect` whose text is a saved value that is empty. Compared as written, either would check nothing: `not_contains: "{{other_users_secret}}"` would pass on every response. Other braces in `expect` are compared as text (`{{`, `{{ name }}` with spaces, `{{user.email}}`, `{{#each}}`); to match the text `{{name}}` itself, leave the pair open (`{{name`). Outside `expect`, a `{{name}}` nothing saved is sent as written. Acting as another account: list its email under `users:` (the accounts are created with role `user` before `setup:` runs, so setup SQL can look an id up with `(SELECT id FROM _benmore_users WHERE email = 'bob@example.com')`), then `- set_auth: "bob_token"` (or `"{{bob_token}}"`). `set_auth: "alice_token"` returns to the `as_user` account alice@example.com and `set_auth: "none"` signs out. The steps after a `set_auth` send the token as a Bearer credential, so they send no CSRF token. A `set_auth` value that is not `none`, the name of a saved variable or a token is sent as the token itself, and every later step answers 401. Example: `isolation:` / `as_user: "alice@example.com"` / `users: ["bob@example.com"]` / `steps:` / `- api: "POST /api/notes"` with `json: {title: "alices-note"}` and `save: {note_id: id, note_title: title}` / `- set_auth: "bob_token"` / `- get: "/api/notes"` with `expect: {status: 200, not_contains: "{{note_title}}"}` / `- get: "/api/notes/{{note_id}}"` with `expect: {status: 404}`. Assert the status beside `not_contains`: a 401 body does not contain the text either. Test accounts are also created with the password `testpass123`, so where sign-in asks for no second factor a step can sign one in through the app (`api: "POST /api/_auth/token"`, `json: {email: "bob@example.com", password: "testpass123"}`, `save: {t: token}`, then `set_auth: "{{t}}"`). Under `compliance: hipaa` or `auth.require_mfa_for_roles` that exchange asks for a code the test does not have; use the saved token.
