Batch CRUD applies access and row scope, validators.yaml and `:validate` rules, before-hooks, record locks (409), computed-column protection, foreign-key target visibility and audit with real old/new values. Batch PATCH and DELETE skip IDs that are missing or outside the caller's edit/delete row scope; the updated/deleted count includes only processed rows, and a skipped ID does not abort an otherwise valid batch. Batch POST skips an object only when nothing would be written for it: it names no writable column and the table has no owner (`user_id`) or tenant column to fill from the session; a batch of only such objects answers 200 `{count: 0, ids: null}`. On a table with `user_id`, `{}` (or an object naming only unknown or protected keys) still inserts a row holding the caller's id and the column defaults, and when the model has a required field it fails the whole batch with 422 `<field> is required`. A validation, database-constraint or before-hook failure on an applicable row aborts the transaction and rolls back that batch's pending row/audit changes. Per-row after-effects still run for changed rows: PATCH includes SQL after-hooks and durable job intents in its transaction, while create/delete after-hooks and event flows run after commit. A failure in post-commit delivery cannot roll back committed rows. See api(at:"hooks") for submitted-field and hook timing contracts. A submitted foreign key must name a parent row the caller can read; a missing and a forbidden parent both answer 422. UNIQUE/FOREIGN KEY/NOT NULL/CHECK failures read as generic messages (`a record with the same unique value already exists`). POST /api/_transaction reports validation and foreign-key refusals as 422. Streaming NDJSON ingest has separate hook and partial-success semantics; see api(at:"ingest").
