Startup and reload reuse unchanged FTS tables and sync triggers without rebuilding their data. UPDATE synchronization runs only when the row id or an indexed value actually changes (including NULL transitions). Encryption, blind-index and timestamp updates on other columns do not touch FTS, so inserts remain safe when their storage triggers are recreated by checks or reloads. Existing unconditional update triggers are replaced and rebuilt on the next initialization. New indexes, changed indexed columns/tokenizers, and missing or changed sync triggers rebuild atomically from the source table after column migrations. A failed rebuild preserves the previous index and rejects initialization/reload instead of reporting success. An ordinary or content-owning table occupying the generated index name is refused rather than replaced. Removing @@fulltext does not automatically drop previously created indexes. For an explicit repair of a structurally unchanged index, use authorized SQLite maintenance to run the FTS5 rebuild command after a backup.
