Every lock endpoint checks the row's READ gate first (table read mode + token scope + row scope). A row the caller cannot read answers 404 on acquire, status AND release - whether or not it exists or is locked - so the endpoints never reveal which rows in another tenant are being edited. A table the caller cannot read answers exactly the unmatched-route 404 body. Only after that: acquire needs edit rights (403 otherwise), release of someone else's lock is 403 (an admin on an unscoped credential may release any; an admin's scoped API token or scoped session releases only its own, api({at:'auth'}) → admin_actions_on_others), and release with no active lock is 404. Writes check scope before the lock the same way: PATCH, DELETE, batch update/delete and /api/_transaction answer 409 for a locked row only when the caller may edit/delete it; a locked row outside the caller's scope is 404 (or skipped by batch), like an unlocked one.
