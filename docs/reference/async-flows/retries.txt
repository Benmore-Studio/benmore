A queued flow job runs ONCE by default: when a run fails, the job is marked failed with that run's error and each `on_error` handler has run once. This covers a `mode: async` request, a `run: enqueue` job (it takes the TARGET flow's setting) and a connector command's data-event flow; data-event flows otherwise run in the app process once and are never retried, and scheduled flows keep cron's rules. Opt in with `on.request.max_attempts: N` (1 to 5, counting the first run; refused outside that range) only when the whole flow is safe to run again: a retry re-runs the flow FROM STEP 1 with the same queued input, and what a failed run committed is repeated. Without `transaction: true` every SQL statement commits as it runs, so the statements before the failing step run again; with `transaction: true` the failed run's SQL and its `run: enqueue` jobs are rolled back, and its outbound effects (`api`, `webhook`, email, SMS, broadcasts) still repeat. Either way the failing step's `on_error` handler runs on every failed run (it writes outside the transaction), so a handler that journals failures writes one row per failed run. Only a failure a later run can change is retried: an `api` or `webhook` call that got no answer (timeout, refused or reset connection, temporary DNS failure), met an open circuit breaker, or was answered 408, 429, 500, 502, 503 or 504 (a 4xx listed in the step's `handled_statuses` is not a failure), and a busy or locked database. Every other failure fails the job on its first run even with max_attempts: a body that is not JSON, a value missing from scope, a refused or failing SQL statement (constraint, authorizer, expect_rows), another 4xx, `success_when`, an email or SMS failure, a caller who lost access before the job ran, and a `parallel` block in which any branch failed for another reason. Retries wait 30 s, then 60 s, 120 s, 240 s. While a retry waits, the status_url answers `status: "pending"` with `error` (the failed run's error) and `attempts` / `max_attempts`; keep polling until `completed` or `failed`. To retry one flaky call without re-running the rest, put `retry: N` (and `retry_delay:`) on that step: it re-runs only that step, inside the same run. Crash recovery is separate: top-level `idempotent: true` decides whether a job interrupted by a worker crash runs again. A job stored with a higher max_attempts than its flow declares follows the flow's current max_attempts, so it runs once unless the flow opts in. Webhook-subscription deliveries keep their own retries (3 attempts).
