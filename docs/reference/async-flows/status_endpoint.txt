GET /api/_jobs/{id}/status → { job_id, flow_name, status, attempts, max_attempts, error?, started_at?, completed_at?, run_at?, created_at? } (`error` redacted, see error_redaction). `pending` with an `error` means a failed run is waiting for its retry (`retries`); `failed` is final. `running` does not prove a worker is still on the job: one whose worker stopped mid-run (an app restart or a crash) keeps answering `running` until its lease ends, up to 5 minutes after the worker's last sign of life, and only then becomes `failed` (its `error` starts `worker died mid-execution`) or, for a flow that declares `idempotent: true`, `pending` again. Keep polling through it, and size a client-side timeout above that window plus the flow's own run time. The 202 response's `status_url` already carries a per-job capability token (`?token=...`) - **poll the returned status_url verbatim, do NOT reconstruct `/api/_jobs/{id}/status` yourself** (the bare id is rejected 404). The token is required because job ids are serial + the status/error can leak SQL/upstream detail across tenants; an admin session can poll without it. Full job rows + admin actions stay behind /api/_jobs (admin only).
