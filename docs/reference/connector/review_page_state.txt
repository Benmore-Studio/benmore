(1) The operation review page (GET /api/_mcp/operations/{id}) shows the state `_status` reports, from the same check `_commit` runs, and the latest attempt. When the approving session has ended (signing out ends it), `_status` says denied with reason approval_lapsed and `_commit` refuses; the page says the approval no longer holds and to ask the assistant to prepare the change again. An operation takes one approval, so the same one cannot be approved twice, and the person should stay signed in until the new one is applied. A role change the command reads (actor_changed) or a changed reviewed source (source_changed) shows the operation with that reason, and approving it is refused. A running, failed, conflicting or unknown attempt shows as such, not as "Approved. Your assistant can now apply this change." An `approval: grant` approval is described as coming from the connection's standing consent: only that connection can check the consent, so the page does not claim it still holds (`_status` does). The batch page lists the person's unexpired changes from that connection that can no longer be applied under "Can't be applied" with the same reason and no checkbox. (2) The JSON text content of connector tool results (commands, `_status`, `_commit`, reads, files, external reads, artifacts) keeps & < > as written, as the review page's Exact data does. (3) A command or read tool call whose input does not match its input_schema answers invalid_input naming the JSON path and the rule, e.g. `invalid_input: The input does not match the tool's input_schema at arguments.status: value is not in enum.` It never repeats the value, and names an undeclared key only when the key is a plain identifier.
