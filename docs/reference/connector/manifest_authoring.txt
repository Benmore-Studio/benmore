Read `benmore docs connector` (also help(topic:connector)) for the embedded offline guide and a complete native mcp.yaml, including pagination, top-level digest placement and hosted deployment. No framework source checkout or Go toolchain is required. `benmore mcp review <appdir> --reviewed` works on an authored manifest with missing or stale digests. Native reads use handler {kind: native, operation: table.list or table.read, table: <actual-table>}, not kind:table/operation:list. Digest generation is source attestation, not access approval. Reconcile the app project with deployed source, review exact declarations/source, check locally, then deploy the full reviewed project: dependency files are sent before mcp.yaml because upload validation hashes server source. Deploy and multi-file push send root schema.prisma/schema.sql/schema.yaml, then app.yaml, before flows and the other sources, preserving order within each tier and keeping mcp.yaml last, so a command can name a table added in that same batch without a second deploy. Then the owner runs `benmore mcp enable <app> --env dev` for exposure, adding --writes only after declaring approved commands (owner status and enable select the explicit instance), and app users connect their client to https://<app-host>/api/_mcp and consent to explicit scopes. Any later source change, a static image included, makes the review stale. The app then still reloads and serves the change from disk like an app without mcp.yaml, but its connector is off (no /api/_mcp, `benmore mcp status` names the problem, `enable` is refused) until the source is reviewed again and mcp.yaml is pushed; read exposure, export/publication switches, grants, the revision ledger and command flows are kept, so a review restores the connector's reads. Approved writes and auto-approve are not kept: every hot reload, including the one that applies the source change and the one that loads the new review, turns them off, forgets the digests they were approved under and ends users' auto-approve consent, because the reloaded generation may run different code. After the review is loaded the owner runs enable --writes (with --auto-approve if it was on) and users tick auto-approve again when they reconnect; `benmore mcp status` says so in approved_writes_off_reason until the owner changes a switch (a restart in between loses that note, not the rule). Delete mcp.yaml when the app serves no connector. Source write tools that reload (write_file, edit_file, delete_file, upload_static, upload_static_from_url, feature_install, git_revert) add the warning mcp_connector_withheld, and benmore push prints it; a batch write with reload:false is checked at the batch's final write. The digest can cover server files that `benmore pull` never writes (for a manifest without `execution_sources: runtime`, hidden directories outside static/ such as .sdd/), so a review made in a pulled workspace cannot match while they exist: the warning names them, and deploying mcp.yaml is blocked naming them until they are deleted on the server (`benmore delete-file <path>`) or the workspace holds identical copies. Deploy does not upload hidden directories outside static/, so the reverse case is blocked too: a workspace file the digest covers in such a directory (below flows/, emails/ or templates/, or anywhere for a manifest without `execution_sources: runtime`) that the server lacks or holds with other content is named, to be sent with `benmore push <file>` or moved to a plain directory and reviewed again; a manifest reviewed again binds only the files the runtime reads, which leaves most of them out. Any other mcp.yaml error (malformed manifest, broken bindings) still refuses the load. See the embedded guide before commands, files, artifacts, UI or external connections.
