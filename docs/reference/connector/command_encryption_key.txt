Approved commands seal their prepared operations, approvals and attempt history under the app's ENCRYPTION_KEY, so a load whose mcp.yaml binds a command flow refuses without a durable key (`operation lifecycle requires configured ENCRYPTION_KEY`; the reload keeps the previous handler, a start fails). Hosted: a push or deploy that adds an mcp.yaml with command flows to an instance whose environment holds no ENCRYPTION_KEY restarts the app instead of hot reloading it, and the restart pins a key in that instance's environment before the process starts, as for newly declared encrypted fields; `benmore restart <app> --env <env>` does the same. An existing key is never replaced. `benmore check`/check_app and the write response after an mcp.yaml or flow write warn (source mcp_connector) when commands are declared and the environment has no key, and `benmore mcp check`/`inspect` list it under `warnings`. `benmore test` and `benmore verify` load a disposable copy of the source and give it a random key for the run when none is set (api(at:"verification.test_workspace_copy")). Self-hosted and `benmore serve --mcp-local`: set ENCRYPTION_KEY (`openssl rand -hex 32`) in env.yaml or the environment before the first start and keep it; once commands have run, changing it needs the key-rotation workflow.
