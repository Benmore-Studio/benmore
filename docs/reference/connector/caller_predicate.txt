An approved command is not checked against its table's `access:` rule or row scope (`connector_hooks_effects`, 'Access rules are not applied'): which rows it may change is decided by its SQL alone. The source checks therefore point out a command whose SQL has no predicate tied to the caller. `benmore mcp review`, `benmore mcp check` and `benmore mcp inspect` list it under `warnings`, and `benmore check` and the check after a push of the command's file report it as a warning (source mcp_connector, on that file), starting `flows/<name>.yaml: command "<name>" has no predicate tied to the caller` and naming the statements. A command is named when its apply SQL updates or deletes rows, or inserts rows it selects from a table (INSERT ... SELECT ... FROM), and no SQL binding in its dependencies, prepare or apply names the actor: `${{ user.id }}`, `${{ user.group_id }}`, `${{ user.email }}`, `${{ user.role }}` or `${{ user.is_admin }}`. To fix it, add the owner or tenant predicate to the prepare SQL and the apply SQL, bound from the actor and never from an argument: `UPDATE orders SET status = 'cancelled' WHERE id = :id AND user_id = :actor` with `params: {id: '${{ params.id }}', actor: '${{ user.id }}'}`, and on a tenant-keyed table `AND org_id = :tenant` bound to `${{ user.group_id }}`. It is advice, never a refusal: the command loads, review binds it, and its digests and approvals are the same with or without the warning, so a command that is meant to let every holder of its permission change those rows needs no change. The check stays quiet when it cannot be sure. One actor binding anywhere in the command's dependencies, prepare or apply silences it for the whole command, so a quiet check does not prove that every statement is scoped; readback bindings do not count. It is also quiet for a write whose table has a before-hook for that action (before_update, before_delete, before_insert) that reads a caller key (user_id, user_email, user_role, user_roles, user_group_id), for an update that names the state column of a workflow whose every transition carries a `role` or a `when:` reading one of those keys, for a plain INSERT ... VALUES, and for an INSERT ... SELECT that reads no table (insert unless it exists).
