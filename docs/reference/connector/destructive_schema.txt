A reload or start that loads a reviewed mcp.yaml refuses a schema.prisma that removes a model the database still has (the last applied migration declares it): `mcp.yaml: destructive Prisma schema transition is unsupported`. The message names the tables and the recovery order, `benmore check`/check_app report it (source mcp_connector) before a reload does, and a write of mcp.yaml (write_file, edit_file, push, deploy) is refused while the server's schema.prisma removes such a model. What happens on a deploy (or a multi-file push): mcp.yaml is the batch's last write, the one that asks for the batch's single reload; when it is refused, the server reloads the files already written anyway, without that mcp.yaml (a write sent with reload:false is refused without a reload, and its answer says the next reload applies the change). The reload migrates the schema with no connector: a first connector has no mcp.yaml on the server, and one reviewed for the old schema is stale, so the connector stays off. Its command flows load but are not exposed: no /api/_mcp, no route, `benmore mcp enable` refused; the strict loaders behind review and inspect still require the binding (`flows: command ... requires an mcp.yaml binding`). The CLI waits for that reload, pulls the migrations/ file it wrote, and says what it applied; the deploy still exits non-zero because mcp.yaml was not written. Then run `benmore mcp review <dir> --reviewed` (it covers that migration) and deploy again, which writes mcp.yaml and turns the connector on. A deploy that fails records the files it did write in the sync base, so a following `delete-file` or push of one is not refused as remote_only. Manual recovery (any other order): apply the schema change with the connector off (a first connector has none on the server; a manifest reviewed for the old schema is stale and already keeps it off; delete one reviewed for the new schema with `benmore delete-file mcp.yaml --app <app> --env <env>`), wait for the reload to migrate, `benmore pull` the migrations/ file the server wrote (review covers it), `benmore mcp review <dir> --reviewed`, then deploy again. Only mcp.yaml has to come off; command flows can stay.
