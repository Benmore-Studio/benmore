A built-in route that fails on the server (auto-CRUD list, count, create, update, delete, batch and ingest, /api/_transaction, /api/_query, notifications, roles, ACLs, locks, versions, scheduling, import, signed URLs, OAuth, MFA, passkeys, page render, ...) and a failed flow keep their status, but the answer carries only the route's generic text and a request id, never the database's own text: every /api/ route answers JSON `{"error": "<text>", "request_id": "<id>"}` (a failed list: `{"error": "list failed", ...}`), an OAuth error code such as `server_error` stays as it is, a text route outside /api/ answers `<text> (request id: <id>)`, and a failed flow answers its flow_no_response JSON, whose `message` is `Internal error (request id: <id>)` and which has `request_id`, the failed step and a fixed `reason` (a signed-in app admin also gets the step's error, see api({at:'flows'}) step_failures). A page whose render fails (a gotmpl `queries:` or `<query>` tag error, a template error) answers a caller signed in to the app as an admin on a full-access credential with `Internal Server Error: <error> (request id: <id>)`, the request log's redacted text; anyone else, a scoped token included, gets only the id. Every such answer has an `X-Request-Id` header. This holds for every app, hosted `-dev` instances included. The detail is kept server-side under the same id: the request log row (`_benmore_request_log.error` and `request_id`; MCP `get_request_logs` with `request_id: <id>`, `benmore requests <app>`, which reads the prod instance when the app has one unless you pass `--env dev` or ran `benmore use dev`), and one journal line, `SERVER ERROR [<table or route>] <method> <path> (request <id>): <detail>` or `FLOW ERROR [<flow>] <error> (request <id>)` (`benmore logs <app>`). The stored detail is one line of at most 2 KiB with credential-shaped text (URL query strings, Bearer values, tokens, password=...) replaced by [redacted]. A failed flow's row names failed_step, failed_type, the error and the step hint. A single-record read (`GET /api/<table>/<id>`) whose query fails still answers 404 `{"error": "Not found"}`, with the failure recorded the same way. Show the request id to the user and look it up; do not parse the text of a 500.
