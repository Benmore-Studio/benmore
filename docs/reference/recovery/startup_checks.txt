A start copies and re-reads the database only when it must. The pre-migrate snapshot (.benmore/backups/pre-migrate-<ts>.db, a VACUUM INTO copy) is taken when the load will change the schema (a column to add, a deferred index/view/trigger that does not exist yet, a generated or adopted Prisma migration - its own snapshot is reused - a new table, a pending migrations/*.sql), on the first start of a new runtime build, and when the storage configuration changed since the last snapshot (encrypted, versioned, computed, aggregate or @@fulltext fields, or whether ENCRYPTION_KEY is set), because those starts rewrite stored data in later steps (history re-sealing, blind-index columns, full-text rebuilds, the framework's user-table and session steps). .benmore/db-boot-state.json records the build and configuration a snapshot covered; anything that cannot be determined snapshots. The app keeps the newest 3 (scheduled-* backups keep their own count). A new copy byte-identical to the newest pre-migrate snapshot (the database has not changed since; a checkpoint, quick_check or reopen does not count) is deleted and the newest is reused, so a failing migration retried by every restart, or any repeat start against an unchanged database, takes no retention slot. The reused snapshot keeps its name and timestamp, which is the age auto-recovery judges (auto_recovery); the log says `backup: the database is unchanged since <name>; reusing it`. PRAGMA integrity_check runs once per load, after the last schema-writing step, when the load changed the schema, when the open could not verify the file, when a table, index or migration changed since the last passing check on that file (.benmore/db-integrity.json, bound to the file's device and inode: DDL from a hot reload or `sql write:true` is checked at the next start), or 7-10 days after that check. A failed check runs REINDEX and checks again (index damage, no data loss), then restores the load's first snapshot (for a self-hosted `serve`, the one its boot check took). Validation loads (`check`, `benmore check`) check only columns they added and reuse a snapshot from the last 10 minutes. PRAGMA quick_check at open is skipped only when the previous serving process closed that exact file cleanly: after its pool closes, with data.db still the file it opened (device and inode), no background job cut off, no connection still open, no corruption or I/O error in SQLite's error log during the run (corruption is always logged; some I/O errors are not), an empty WAL and no rollback journal, and only if its own open was verified, it writes .benmore/db-clean-shutdown.json with the file's device, inode, size, mtime and ctime (stat only), stamped once the file has been unchanged for 1s. The next open removes the marker before SQLite opens the file and trusts it only if everything still matches. No marker (crash, kill -9, OOM, power loss, first start on this runtime), a replaced, restored or copied file (restore, PITR, refresh-dev and auto-recovery also delete all three records), a write by any process, WAL frames, or a marker more than 7-10 days past the last full check runs quick_check, with the REINDEX-then-restore recovery (auto_recovery). Log lines: `database: quick_check (<reason>)`, `database: quick_check skipped`, `database: no clean-shutdown marker (<reason>)`, `backup: pre-migrate snapshot (<reason>)` / `no pre-migrate snapshot needed`, `database: integrity_check (<reason>)` / `skipped`.
