restore_db / `benmore restore` checks the snapshot against the app's current code before installing it. If the restored app would drop data again when it starts - a table whose model schema.prisma no longer declares, or rows or populated columns a migrations/*.sql file the snapshot's ledger has not applied deletes (the file is run on the snapshot in a rolled-back transaction and measured as in api(at:"schema") migration_file_drops, so a rename then a drop or a rebuild that copies nothing counts) - it refuses, lists what would be dropped, and leaves the live database unchanged. Revert the code to the snapshot's version first (on prod: revert on dev and promote), or pass force (`--force`) to restore anyway. The same run also reports a migration that fails on the snapshot's data (the schema step, or a migrations/*.sql file the snapshot's ledger has not applied): the restored app would fail every start, or fail once, set the file aside as `<name>.sql.failed.sql` and run without it. restore_db refuses with the step, SQLite's error and the statement, live database unchanged, unless force. The check replays a start, so a file that uses a history table or blind column the start creates before it is not reported. Promote refuses the same condition on prod unless forced: api(at:"environments") promote_would_fail.
