A backup listing is complete or an error: one that cannot be read in full returns an error rather than a partial list. There are two kinds of backup. An instance's own backup files (.benmore/backups: pre-migrate, scheduled and before-restore copies) are what `benmore restore <app> [--env dev|prod]` (restore_db without `from`) lists under `backups` and what `--from <name>` restores; an instance that has taken none yet answers an empty list. Stored snapshots are kept in the platform's backup storage, outside the instance, for production only: the hourly ones (`<UTC date>-<hour>.db.gz`) and the pre-deploy ones (`pre-deploy-<UTC time>.db.gz`), among them the final backup `remove-production` takes. On the hosted platform the same restore listing of a production instance shows them under `stored_snapshots`, newest first, at most 50: `{name, size, modified, kind:'hourly'|'pre-deploy', where:'backup storage'}`, with `final_backup: true` on the one a removed production's `remove-production` took, plus `stored_snapshots_total`, `stored_snapshots_truncated` when there are more, and `stored_snapshots_note`. When the backup storage cannot be listed the instance's own backups are still answered and `stored_snapshots_error` says the stored ones could not be read. A stored snapshot is not a name `--from` takes, and no command restores one into an app: the dashboard's Backups view downloads it (a gzipped SQLite database; editor access, for a `compliance: hipaa` app the owner only). To go back to an earlier state of a running app use one of the instance's own backup files, or point-in-time recovery where it is enabled (wal_base_readiness). The dashboard's Backups view lists ordinary snapshots, the newest 1000, with count, total and truncated; PITR objects are not offered as downloads.
