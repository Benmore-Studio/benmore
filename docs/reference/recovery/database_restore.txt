restore_db and benmore restore need editor access and act on the requested dev/prod instance. List mode checks real SQLite integrity, not just the file header. A restore prepares and fully validates its snapshot before the app is stopped. The app's lifecycle lock is held throughout. The replaced database is retained under .benmore/backups/before-restore-<id>/data.db; this relative name can be selected in a later restore. Success includes recovery.verified:true after a full restart of the app. Failure returns an MCP error with recovery.stage, database_applied and previous_database. Preparation failures leave live data unchanged; later errors can leave the app stopped or the restored database installed but unverified. Never interpret an error as rollback: inspect the stage and preserved bundle before retrying. User data after the selected restore point is lost, but sign-in state is not rolled back: after writers stop and before installation, the restored copy takes the live database's credential state in one transaction (stage `credentials`; a failure installs nothing and leaves the live database in place). Accounts in both keep the live password hash, sealed TOTP secret, backup codes and MFA replay guard, deactivation, password_change_required, verification and login identifiers (email, phone, username). Sessions (compared by stored hashed key), API tokens (token hash), OAuth provider tokens, OAuth codes and clients, email-change, password-reset/verification and one-time-code grants survive only if the same credential exists live for the same account, refreshed to live values; nothing issued after the snapshot is added, so those users sign in again. Accounts deleted since the snapshot come back with their snapshot password but no sessions or tokens, and lose any login identifier a live account now holds; an account id reused since an earlier restore is matched by created_at and not merged. Login lockout state is the live one. When the live database is missing or unreadable, every restored session, token and grant is revoked and account credentials stay as in the snapshot. recovery.credentials reports the mode and counts, and one `restore_credentials` audit row records them (never a credential). The `_benmore_audit_log` rows of account, role and credential events recorded since the snapshot are copied from the live database in the same transaction, each once and marked in `restore_carried_at`; recovery.credentials.audit_rows gives the count: api(at:"recovery.restore_audit_rows"). Role grants and app tables roll back with the data. Boot auto-recovery applies the same carry-forward. Work that already ran is not queued again. In the same transaction, every job (`_benmore_jobs`: pending, running) and scheduled task (`_benmore_scheduled_tasks`: pending, blocked, running) the snapshot still has queued is settled against the live database. (1) The live database holds the same row (same id and created_at; an id handed out again after an earlier restore is a different row): the row takes its live status, attempts, error and timestamps, so finished work stays finished, a run the restore cut off is left to the worker's usual crash recovery, and a row still waiting live stays waiting. (2) The live database had the row and no longer does (completed jobs are cleaned up after 7 days; a job or an account's tasks can be deleted): it is held, never run: the job becomes `failed` and the task `cancelled`, with the reason in `error` / `last_error` (an admin can run a held job on purpose with POST /api/_jobs/{id}/retry). Only the id says so: a row from another timeline (dev restored to its own data after a refresh from production) is held too when the live table has passed its id and holds no row with it. (3) The live database never had the row (an id past its sequence, or the id is a different row's): it stays queued. With no readable live database (or one without the queue table), nothing says what ran: queued rows that are already due are held as in (2), and rows whose run_at is still ahead cannot have run and stay queued. Jobs and tasks created after the snapshot are gone with the rest of the newer data. Cron's last-run times (`_benmore_cron_state`) are the live ones, so an `every <interval>` schedule counts from its real last run instead of firing as soon as the restored app starts. recovery.credentials.queue gives per-table counts (`finished`, `held`, `waiting`, and `live_error` when only the queue could not be read); the `restore_credentials` audit row and the restore's log line carry the same counts (never a payload). Source/config files are not rolled back, and startup can apply current migrations to the restored database. A restore is not atomic across a power loss; keep other processes and direct file or database access away from the app while it runs. Stopping and starting the app are bounded at 25 seconds; preparing the snapshot takes additional time. On the hosted platform each step on the app's files is bounded at 31 minutes. If a step ends without saying whether the swap happened, nothing is rolled back and the failure says so. A restore's working copies (the selected backup, the candidate made from it, a PITR replay) are staged in .benmore/.restore-<id> and .benmore/.pitr-<id>, beside refresh-dev's .benmore/.refresh-<id>. A stage is never app source wherever it sits: one an unfinished restore left at the top of the app directory is not committed, copied between instances, listed in a source manifest or pull, or readable or writable through the file tools, and a history that already holds one is refused by history operations and the GitHub push like one that tracks data.db (an operator removes it from history). Stages a restore never cleaned up (a platform restart, a cancelled request) are removed at the start of the next restore of that instance, and at app start once nothing has changed in them for 2 hours; at the top of the app directory only a .restore-<digits> or .pitr-<digits> directory holding nothing but database copies is removed, so do not keep files of your own under such a name.
