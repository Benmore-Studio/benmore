When an app starts and its database file is unreadable, it auto-restores from the most recent valid pre-migrate-*.db or scheduled-*.db backup, and the corrupt original moves to .benmore/backups/data.db.corrupt-<timestamp>. A disk I/O error at open or during quick_check is retried with backoff (about 2s) before it counts as corruption. When quick_check runs at open (startup_checks) and fails, REINDEX is tried first (index corruption, no data loss), then the same restore. Only a snapshot younger than 24h is restored unattended (the timestamp in its name; the operator of the server can change the limit with BENMORE_AUTO_RESTORE_MAX_AGE, a Go duration such as 72h - a hosted app cannot set it). A snapshot whose name is dated more than 5 minutes in the future (clock skew) counts as of unknown age and is not restored either. With only older snapshots the original stays in place, the log says `DB AUTO-RECOVERY REFUSED: newest snapshot is <age> old; restore with benmore restore or PITR`, and the start fails, so the app shows as failed until someone chooses a restore. The refusal is recorded in .benmore/db-recovery-refused.json, bound to the file's device, inode, size, mtime and ctime, the age limit and the newest snapshot's name: while all of those are unchanged, a restart fails at once with the same message (`DB AUTO-RECOVERY REFUSED (unchanged since <time>)`) without reading or repairing the file, so the app fails fast instead of re-checking a large file on every start. A restore (`benmore restore`, PITR, refresh-dev), any change to the file, a newer snapshot or a different BENMORE_AUTO_RESTORE_MAX_AGE clears it. A restore logs the snapshot's age. With no usable backup at all the original is reopened degraded, and the integrity_check that follows fails the start unless REINDEX repairs it. Pre-migrate snapshots come from schema changes and new releases, not from every restart, and a start against an unchanged database reuses the newest one with its original timestamp; schedule backups (app.yaml backup:) for a recent local recovery point. Credential state is carried forward from the original as in database_restore; when the original cannot be read, every restored session, token and grant is revoked, so users sign in again. Look for `DB AUTO-RECOVERY` and `auto-restore:` lines in `benmore logs <app>` after a failed deploy (`benmore tail <app> --grep AUTO-RECOVERY`; the filter is case-sensitive).
