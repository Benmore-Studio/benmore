The migrations/ ledger is checked before taking its pre-migration snapshot. Already-applied files do not create another full database backup on startup or reload. Pending files take one snapshot before the batch; a required production backup failure prevents their execution and leaves them pending for retry. Startup rejects failed deferred schema DDL and user migrations; previously committed changes are not automatically undone. A failed SQL file is set aside as <name>.sql.failed.sql: inspect and fix it, then restore its .sql name to retry. A statement whose change this database already has is skipped with a log line (`migration: skipping ...`) and the rest of the file runs: an ADD COLUMN of a column that exists, a CREATE of a table or index that exists, a RENAME whose source is gone and whose target exists, and a statement that is exactly `ALTER TABLE t DROP COLUMN c`, `DROP TABLE t` or `DROP INDEX i` naming a column, table or index the database does not hold (a column of a table it does not hold counts). That is what lets a file written for a database that had the column run on one built later from the schema, which never had it. A misspelt name in such a drop is skipped too, so a write, a promote and a restore list every drop they skip under `migration_skipped_drops` (api(at:"schema") unapplied_changes). A statement that would take a framework control away (`PRAGMA writable_schema`, a trigger created under a `_benmore_` name, a framework trigger dropped from a framework table, an audit table of a `compliance: hipaa` app changed) fails with `a migration may not ...` and fails the file (api(at:"schema.framework_tables")). Nothing else is skipped: any other statement that fails, a drop that fails for another reason (a column a trigger, index or view still uses, a primary-key column) and a drop in another schema fail the file. Schema snapshots and integrity checks run when the load changes something (startup_checks). The log names each app load phase with its elapsed time; a completed load is not HTTP readiness. With a reviewed mcp.yaml, a database with no application tables and no applied migrations (first boot, a fresh deploy, --mcp-local; a first boot that failed partway and is retried stays on this path until one load completes) applies its schema and pending migrations first, including ALTER and DROP, and the manifest routes are then checked against the migrated schema; an existing database whose pending migration DDL could change routes under the live manifest is refused (pending route-changing migration DDL is unsupported), so apply such a migration in a separate reviewed step.
