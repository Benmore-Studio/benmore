The migrations/ ledger is checked before taking its pre-migration snapshot. Already-applied files do not create another full database backup on startup or reload. Pending files take one snapshot before the batch; a required production backup failure prevents their execution and leaves them pending for retry. Startup rejects failed deferred schema DDL and user migrations; previously committed changes are not automatically undone. A failed SQL file is set aside as <name>.sql.failed.sql: inspect and fix it, then restore its .sql name to retry. Schema snapshots and integrity checks run when the load changes something (startup_checks). The log names each app load phase with its elapsed time; a completed load is not HTTP readiness. With a reviewed mcp.yaml, a database with no application tables and no applied migrations (first boot, a fresh deploy, --mcp-local; a first boot that failed partway and is retried stays on this path until one load completes) applies its schema and pending migrations first, including ALTER and DROP, and the manifest routes are then checked against the migrated schema; an existing database whose pending migration DDL could change routes under the live manifest is refused (pending route-changing migration DDL is unsupported), so apply such a migration in a separate reviewed step.
