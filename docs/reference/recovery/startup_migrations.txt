The migrations/ ledger is checked before taking its pre-migration snapshot. Already-applied files do not create another full database backup on startup or reload. Pending files take one snapshot before the batch; a required production backup failure prevents their execution and leaves them pending for retry. Startup rejects failed deferred schema DDL and user migrations; previously committed changes are not automatically undone. A failed SQL file is set aside as <name>.sql.failed.sql: inspect and fix it, then restore its .sql name to retry. A statement whose change this database already has is skipped with a log line (`migration: skipping ...`) and the rest of the file runs: an ADD COLUMN of a column that exists, a CREATE of a table or index that exists, a RENAME whose source is gone and whose target exists, and a statement that is exactly `ALTER TABLE t DROP COLUMN c`, `DROP TABLE t` or `DROP INDEX i` naming a column, table or index the database does not hold (a column of a table it does not hold counts). That is what lets a file written for a database that had the column run on one built later from the schema, which never had it. A database that is new in this load skips more. New means that before the load built it from the current schema it held no application table and no applied migration: the copy `benmore test` runs on, a new instance, a dev database built again. A database stops being new once a load has built its tables, also when that load fails later. On a new database a statement is skipped, with a `WARNING` log line naming the file, the statement's number and what is missing, when it fails only with SQLite's `no such table`, `no such column` or `has no column named` for a table or column of the main schema that the statement itself names and that neither the current schema nor an earlier migration statement gave the database; the rest of the file runs and the file is recorded as applied. A statement that names a framework table (`_benmore_*`) or a SQLite one (`sqlite_*`) anywhere in it is never skipped, whatever is missing. The framework tables a migration file has a reason to name exist before the first file runs, on a start and on a reload, on a new database as on any other, so a file can put a trigger of its own on one, write its rows or read it. For every app: `_benmore_audit_log`, `_benmore_notifications`, `_benmore_jobs`, `_benmore_permissions`, `_benmore_upload_owners`, `_benmore_webhooks` and `_benmore_custom_fields`. For an app that has sign-in (an `auth:` block in app.yaml, or a page with `auth="required"`): `_benmore_users` with its MFA columns and the columns `auth.signup_fields` and page `require=` declare, `_benmore_user_roles`, `_benmore_password_resets`, `_benmore_sessions`, `_benmore_api_tokens` and `_benmore_login_attempts`. An app without sign-in never gets the sign-in tables, so a file of its that names one fails with `no such table` on every database (`_benmore_permissions` exists there, but its rows refer to users and a write to it fails the same way). Every other framework table (record locks, idempotency keys, the request log, analytics, devices, passkeys, OAuth tokens, scheduling, saved views and the like) holds the framework's working state and is created when the app's routes are registered or on first use: a file that names one fails with `no such table` on a database that does not hold it yet. A dry run (a write, a promote, a restore) has the same tables and columns in place, inside the transaction it rolls back, so its verdict on a file that names one is the start's: a file that fills a column `auth.signup_fields` declares passes before the app has reloaded with that app.yaml, and a statement further down such a file that fails is reported as a failure. Only when the dry run cannot prepare them is a file that fails for one of these tables alone reported as not verified, never as a failure. Still a failure there as well: a table or column the schema declares and an earlier statement removed, a statement that names nothing missing but fires a trigger that does, a column SQLite reports under an alias while a table the statement reads holds one of that name, and a missing view, trigger, index or function. A misspelt name is skipped like a removed one, so a write, a promote and a restore list every statement they skip under `migration_skipped_drops` (api(at:"schema") unapplied_changes). A statement that would take a framework control away (`PRAGMA writable_schema`, a trigger created under a `_benmore_` name, a framework trigger dropped from a framework table, an audit table of a `compliance: hipaa` app changed) fails with `a migration may not ...` and fails the file (api(at:"schema.framework_tables")). Nothing else is skipped: any other statement that fails (on a database that is not new, also one that names a missing table or column), a drop that fails for another reason (a column a trigger, index or view still uses, a primary-key column) and a drop in another schema fail the file. Schema snapshots and integrity checks run when the load changes something (startup_checks). The log names each app load phase with its elapsed time; a completed load is not HTTP readiness. With a reviewed mcp.yaml, a database with no application tables and no applied migrations (first boot, a fresh deploy, --mcp-local; a first boot that failed partway and is retried stays on this path until one load completes) applies its schema and pending migrations first, including ALTER and DROP, and the manifest routes are then checked against the migrated schema; an existing database whose pending migration DDL could change routes under the live manifest is refused (pending route-changing migration DDL is unsupported), so apply such a migration in a separate reviewed step.
