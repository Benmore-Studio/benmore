Legacy POST /platform/deploy?app=<name-or-subdomain> targets prod (env omitted or prod), requires ownership and an active hosting backend, and holds the app's lifecycle lock. Once the caller is authorized and holds a deploy slot, the archive (up to 500 MB) may take up to 5 minutes to arrive, and the deploy 300 s after that to answer. On the hosted platform Cloudflare's own limits apply in front. It applies the promote publish gate (api(at:"environments") `publishing`): a deploy that would put an app live for the first time (an app with a dev instance and no production instance yet, exactly as `promote` judges it, or a new app where new apps start on a dev instance, as on the hosted platform) needs a free live-app slot on the owner's plan and answers 402 with the way out otherwise (free: 0 live apps (1 app in total); Pro ($39/month): 5 live apps (10 apps in total); Scale ($149/month): 25 live apps (50 apps in total)); a deploy that publishes an existing app records the publish. Updating an app that is already live is unchanged. Existing apps resolve to their stored immutable subdomain. The complete bounded tar.gz is staged privately and checked for invalid paths, symlinks, protected metadata/secrets/databases, gzip corruption and malformed core configuration before source writes. It is also scanned for hardcoded provider secrets, the same high-confidence gate write_file applies: a file the archive adds or changes that carries one (Stripe sk_/rk_, AWS AKIA, GitHub, Google AIza, Slack, Resend, OpenAI/Anthropic keys, a PEM private key) fails the deploy with 400 (stage archive), nothing installed; a file already deployed with exactly the same bytes is not re-checked (`benmore doctor` lists those), so move the secret to `benmore env` before you next edit that file. New registration and quota checks must succeed before the app is created. Existing apps require a local database snapshot plus the platform's pre-deploy snapshot before installation; an app with no database needs none. HTTP 200 status:deployed includes verified:true: the restarted app answered healthy. Starting the app has a 25-second health deadline, which does not include upload, backup or source copy time. The app is not served until it is verified; a failed start keeps the app's registration for a retry. Failures identify stage and source_applied (none, partial, complete), with reservation_retained indicating a platform app record remains. Installation overlays submitted files and keeps omitted files; per-file replacement is atomic, the whole tree is not. A disk failure may partially install source; a startup failure may leave all source installed and the service stopped. Read the stage, repair the cause, inspect health/logs, then retry using the returned immutable subdomain. No automatic filesystem/database rollback or exact-source attestation is promised. Ordinary hosted app development goes through push/promote.
