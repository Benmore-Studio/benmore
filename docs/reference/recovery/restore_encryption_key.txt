A database and the ENCRYPTION_KEY its encrypted values were written under are a pair, and restore_db / `benmore restore` keeps them together. Before stopping anything it checks every encrypted value in the selected backup against the instance's current key. The current key decrypts them (or the backup has none): the restore proceeds. On a dev instance, a preserved key record decrypts them (`.benmore/backups/before-refresh-*/key.json`, written by refresh-dev, or `before-restore-*/key.json`): that key is set for dev first, then the data is installed, as refresh-dev installs a pair (`recovery.key_restored`, `recovery.encryption.key_from`). Otherwise the restore is refused with the live database unchanged, because every encrypted value would read as "[unavailable: decryption failed]"; force (`--force`) restores anyway and says so in `recovery.encryption.warning`. Prod never installs a preserved key (an editor's restore must not undo an owner's key rotation). On dev every restore also writes the replaced database's key, sealed, to `before-restore-*/key.json` next to it before anything changes (`recovery.previous_key_record`), so the restore can itself be undone as a pair; a failure before installation puts the previous key and environment back. The backup listing includes refresh-dev's `before-refresh-*/data.db` bundles and marks bundles that hold a key record (`key_record: true`).
