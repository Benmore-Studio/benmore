A served app (`benmore serve`, hosted or self-hosted) checks every 30 s that data.db is still the file its connection pool opened (same device and inode). Another file renamed over it, a deleted file, a symlink or a directory there logs `SECURITY ALERT: database file replaced|deleted|unverifiable` (once per change, then hourly), adds checks.db_file (status, opened, current, since, last_alert; admin sessions only) to /health and makes the overall status `degraded` (still HTTP 200; reloads, restarts and deploys still count the app as up). Nothing else changes: the app is not restarted and writes are not refused, but new connections open whatever is at the path now, or an empty database. On the hosted platform the alert reaches the platform owner. The process keeps the original file open, so a deleted database is still recoverable from it: do not restart the app; ask the platform owner, who saves it and restores it with restore_db. The framework's own replacements (boot auto-recovery, restore_db, PITR, refresh_dev) happen before the process opens the file and never alert; `benmore db rollback` against a running self-hosted app does, because that process keeps writing to the moved-aside file: stop the app first.
