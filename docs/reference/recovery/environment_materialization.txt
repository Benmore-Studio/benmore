An environment change is saved, then applied to each instance as one complete, checked set. Shared values are overlaid by the selected dev/prod scope. A value that cannot be read or decrypted, an invalid environment file or a key that cannot be saved fails the change explicitly. An existing server secret is never regenerated after a read or validation failure. Startup and reload reject a malformed or unreadable env.yaml before database migrations run. Environment names must be valid identifiers; values must be valid UTF-8 without NUL, BOM or Unicode noncharacters. Multiline values and quotes are preserved. Platform runtime metadata keys are reserved. Saving and applying are separate steps: an error can mean the value was saved while the previous runtime is still active. Success means every instance whose environment changed was restarted with it and answered healthy before the response returned. An instance whose snapshot did not change (a dev-only key for prod) is not restarted, and a stopped instance picks the snapshot up when it starts. Several instances or several key saves are not one transaction; a later failure may follow an earlier successful application. Fix the reported cause and retry; do not rotate encryption keys to work around an environment error.
