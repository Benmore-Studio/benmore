Owner-only delete_app requires confirm:true and removes both prod and dev. The HTTP route (DELETE /platform/apps/{name}, used by `benmore delete --confirm` and the dashboard) needs the same acknowledgment as ?confirm=true and answers 400 without it. The instances must be stopped and removed before the app name is released. On failure, read the reported stage, correct the reported problem, then retry deletion of the same immutable subdomain. Cleanup already completed is not rolled back: an error can leave an app stopped or partially removed. Failed create_app cleanup uses the same checks and reports a retained reservation if teardown fails. Deletion also removes the app's browser_check session recordings, shared replay links included, deauthorizes the app's Stripe Connect grants, clears their env keys and releases its dedicated SMS number; a provider call that fails is logged and queued for retry while the local rows are freed. External domain/object cleanup remains best-effort; deletion is not a backup or a transaction across concurrent lifecycle operations. On the hosted platform, once the delete succeeds, the app's uploads on the platform media storage are deleted in the background - every object under `public/<sub>/` and `private/<sub>/`, which prod and dev both write (media is keyed by the app's subdomain, not the instance), using the subdomain the app had before deletion. Only objects written before the delete are removed, so an app later created at the freed subdomain keeps its files. A storage failure is logged on the platform and never blocks or fails the delete. After the purge the platform asks the media CDN to drop its cached copies of `/public/<sub>/*` (public uploads are stored with `max-age=31536000, immutable`); where the operator has not configured that, cached copies can keep loading until the cache drops them. The app's dashboard media library (image library, brand assets, `upload_media`) is deleted with it. Files in an app's own S3_BUCKET are the owner's and are not touched.
