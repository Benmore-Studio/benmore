benmore restart <app> [--env dev|prod], restart_app, and POST /platform/app-restart require editor access and target the selected instance. Success includes verified:true and runtime with status, version, instance_id and reload_generation. Verification waits up to 25 seconds, within the CLI request timeout, for a healthy response with a different process ID from the pre-restart baseline (or a first healthy identity when the previous process was unreachable). Command failure, missing identity or an unchanged process returns an error, not success. A restart command that succeeded but was not verified before the deadline returns HTTP 202 / ok:true with verified:false (not 503): the restart happened and is not rolled back; large apps routinely boot slower than the deadline, so poll /health until instance_id changes before retrying. `benmore restart` prints that 202 body and exits 1, as deploy and promote do for an app that is not healthy. Source writes (write_file/edit_file) acknowledge persistence and run only source-file validators; app-load and schema-drift checks run on demand via `check`, never against the live database from the write path. write_file accepts reload:false so a batch (`benmore deploy`) schedules one debounced reload after its last file. A hosted reload that takes a second or more spaces the next reload of the same instance until three times its duration after it ended (at most 2 minutes). A large app (about 400 flows) reloads in about 20 s, so pushing one file every 40 s keeps it reloading half the time. Writes during the wait coalesce into one trailing reload; batch with `benmore deploy` to see changes sooner. A reload also logs one `flows: N HTTP routes and M cron flows registered` line (the full route list prints once per start). A push to an app that is down after a crash loop (5 crashes in 5 minutes take it out of service) restarts it, verified, and serves it again, so pushing the fix brings the app back without `benmore restart`. `benmore deploy` then waits up to 30 seconds for the app to answer healthy and exits 1 with a pointer to `benmore logs` when it does not. /health uses no-store and exposes only an opaque process nonce plus a reload counter alongside basic status/version; detailed checks stay admin-only. The counter advances only after a successful hot-handler swap. Debounced source writes acknowledge persistence/queueing, not completed reload. Rejected configuration never advances the counter or forces a restart merely to satisfy verification. These receipts do not attest exact source bytes, every migration, future health, or serialization with concurrent lifecycle operations. While an instance is out of service after repeated start failures, its address answers 503 `App unavailable` with Retry-After and the owner's `benmore logs`/`benmore restart` commands.
