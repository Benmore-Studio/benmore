On the hosted platform a schema.prisma or migrations/*.sql write (write_file, edit_file, `benmore push`, `benmore deploy`, the save hook) dry-runs the migration the app would apply on its next reload, against the target instance's database: the Prisma migration, the schema's tables, added columns, indexes and triggers, then every pending migrations/*.sql file, in the load's order. All of it runs in one transaction that is always rolled back; a file's COMMIT, END, BEGIN or plain ROLLBACK is refused (it would fail at a real load too), and nothing is written, snapshotted or recorded. If the file being written fails, the write is refused with SQLite's error and the statement (`UNIQUE constraint failed: contacts.company` for `@unique` over duplicates). Fix the data first with a migrations/ file or `benmore sql`: the schema's migration runs before migration files, so a dedupe has to be applied by an earlier push. The write is accepted, answering `migration_not_verified` (the CLI prints it), when the run reaches no verdict: over its 8 s bound, the write lock held by another writer for 2 s, a trigger needing the encryption key, or a failure in a pending file other than the one being written (the warning names that file; the reload will fail on it). During the run readers carry on and writers wait: up to 8 s on a large index build, under the 10 s writers queue for, and an edit that changes no schema never takes the lock. Not replayed: triggers from computed.yaml, encrypted.yaml and versioning, full-text tables, and deferred foreign keys checked at commit. The same run measures what a migrations/*.sql file deletes, the drop guard's verdict (api(at:"schema") migration_file_drops).
