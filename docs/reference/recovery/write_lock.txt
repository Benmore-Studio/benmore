SQLite has one writer per database, and app pools begin every transaction with the write lock. Read-only transactions neither take nor wait for the write lock. The app log names who holds the lock: when a request, flow, cron, job or statement fails with `database is locked`, the log line `db: database is locked: <victim> ... ; write lock held <duration> by <holder>` names the write transaction holding it (flows `flow:<name>`, cron `cron:<id>`, jobs `job:<flow>`, ingest `ingest:<table>`, otherwise the framework operation that began it), or says no tracked transaction of the app holds it (another process such as `benmore sql`, a single write statement or a manual BEGIN). Contention lines are rate-limited to one per database per 5 s with a suppressed count. A write transaction that held the lock longer than `BENMORE_DB_WRITE_TX_WARN` (default 2s; read from the same place as the limit below) is logged with its holder when it ends. A write transaction has a time limit, `BENMORE_DB_WRITE_TX_LIMIT` (a hosted app's env var; for self-hosted `benmore serve` the process environment, env.yaml is not read for it; Go duration, default 60s; 0 or off disables): past it the runtime rolls the transaction back and frees the lock even while its owner is still busy (a slow outbound `run: api` inside a `transaction: true` flow, a slow upload into streaming ingest, a leaked transaction), logs `db: write transaction by <holder> held the write lock ... rolling it back`, and every later statement and the commit of that transaction fail, so none of its writes are kept. Any external call it already made (a payment, an email) is not undone: keep outbound calls out of `transaction: true` flows, or call first and write after. Schema migrations, table rebuilds, user migrations, imports, encryption key rotation, trigger/index installs and other startup maintenance have no limit. Reset/seed and connector reads are not limited either. The error text is `database is locked` after the connection's busy timeout (10 s for app pools), and a waiting writer holds a pool connection. The caller of a request that fails this way gets 503 `{"error":"database_busy","message":"the database is busy, retry shortly","request_id":"<id>","docs":"recovery.write_lock"}` with `Retry-After: 1` from every built-in route and from a flow (outside /api/ a page, a form post or the admin panel answers the same status and header with one line of text; see api({at:'errors'}) common_envelopes); nothing the request tried to write is kept, so the same request can be sent again. The journal has one `DATABASE BUSY [<table or route>] <method> <path> (request <id>)` line per such answer, next to the `db: database is locked: ...` line that names the holder. A busy answer that keeps coming back means a writer holds the lock too long: find the holder in the log and shorten its transaction.
