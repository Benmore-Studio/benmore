Hosted apps: each app's database is capped at its owner's plan storage (free 100 MB, pro 1 GB, scale and the operator's own staff/admin plans 10 GB; dev and prod instances each get the limit, and add-ons do not change it) or at an operator override in platform_apps.storage_limit_bytes (NULL = plan, 0 = no limit, N = bytes). Two layers: at the plan limit, pre-flight checks on auto-CRUD creates, tenant bootstrap and imports refuse new data (507). Past it, SQLite enforces a hard ceiling of the limit plus headroom (a quarter of the limit, at least 64 MiB): a write through any path (auto-CRUD, flows, hooks, jobs, sql(write:true), imports, logins) that would grow the file past the ceiling fails with SQLITE_FULL. The headroom keeps sign-ins, sessions, jobs and migrations working at the plan limit. The failing statement or transaction is rolled back and the file stays consistent. Auto-CRUD, batch, transactions, ingest, tenant bootstrap and HTTP flows answer 507 {error:'storage cap reached', code:'storage_limit', limit_bytes, detail}; sql(write:true) and failed imports carry the same message. Pre-flight checks on creates, bootstrap and imports refuse on data.db + WAL/SHM before any work. Reads, deletes, and writes that fit in pages freed by deletes keep working; the file does not shrink (apps cannot VACUUM), freed pages are reused. A database already larger than its ceiling is frozen at its current size: it cannot grow but keeps serving reads, deletes and writes into freed space. At or over the limit, a deploy whose schema change needs new pages (an index over existing rows, a table rebuild, a data migration) fails during startup or reload with the storage error: a reload keeps the previous handler serving, a cold start does not come up. Free space first, or have an operator raise the limit. A plan change or override reaches a running app at its next restart or environment refresh. `benmore health <app> [--env dev|prod]` shows where an instance stands: `db_bytes` (data.db + WAL/SHM, what the pre-flight checks measure) and `storage_limit_bytes`, the limit that instance enforces (null with `storage_unlimited` true when it has none); `benmore billing` shows the plan's per-app limit. The platform app and apps with no platform row have no limit; self-hosted, `benmore serve` and framework-edition databases are never capped. A hosted app process whose environment predates the limit enforces its owner plan, or the largest tier when no plan is present. The WAL is not counted by the ceiling, so disk use can briefly exceed the limit by the size of in-flight transactions. App SQL (flow and hook SQL, sql write:true) cannot move the ceiling: on a capped database, setting PRAGMA max_page_count, page_size, temp_store or temp_store_directory fails with `not authorized` (reading them still works), and TEMP tables are limited to 64 MiB per connection (SQLITE_FULL past it).
