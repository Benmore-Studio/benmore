The body is read only as fast as rows are inserted, so ingest does not use the server's ordinary 15 s read and 30 s answer deadlines. Once the caller is authenticated and within the rate limit, the body may take up to 5 minutes, and the answer 30 s after that; the hosted platform gives /api/<table>/ingest the same read time. The app's MAX_REQUEST_BODY_BYTES (10 MB by default) does not cut an ingest body; the 100 MB cap is ingest's own. On the hosted platform Cloudflare still ends a request whose answer has not started about 100 s after it was sent (a 524), so one request must finish well inside that: the measured hosted rate was about 2,800 simple rows per second (100,000 rows in roughly 35 s); before-hooks, validators and wide rows are slower. The audit entry written per row adds server time (on a laptop 50,000 simple rows take about 2.1 s), so treat the hosted rate above as an upper bound. Split larger loads or use api(at:"import"). If the hosted platform answers instead of the app, check `X-Benmore-Outcome` (or `outcome` in the JSON): `not_delivered` (503) means nothing ran and a retry is safe; `unknown` (500) means the app received the request and rows may have committed, so count before you resend.
