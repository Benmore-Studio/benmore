GET /api/<table>/<id>/permissions and bm.permissions.list return {resource_type,resource_id,permissions:[{id,grantee_id,permission,granted_at,expires_at}]}; permissions is an empty array when no grants exist. grantee_id is the stored recipient: the email of a user share (a row written by SQL with another grant_type is listed with its stored id and gives no access). There is no email response field. Generated RecordPermissionGrant declarations match these wire fields, including nullable expires_at. For user shares created with bm.permissions.share, display grantee_id and pass it to bm.permissions.revoke; the permission-ID DELETE route handles an individual grant. Listing still requires the existing row-sharing authority and read scope; no recipient directory lookup or new fields are exposed.
