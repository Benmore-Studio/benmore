Record sharing is on for every table unless app.yaml turns it off. `features.sharing: false` turns it off for the whole app; `access.<table>.share: off` turns it off for one table (and `share: on` keeps a table shared in an app that set `features.sharing: false`). The value is read as a switch: on/off, true/false, yes/no and 1/0 mean the same. Order: the table's own `share`, then `access.default.share`, then `features.sharing`, then on. `share` is a switch, not an access mode: who may share a row stays its owner or an admin, and `all:` does not set it. The write gate and `benmore check` refuse a misspelled key (`features.sharng`, `access.docs.sharing`) and a value that is neither on nor off.

While sharing is off for a table:
- POST /api/<table>/<id>/share answers 403 `{"error":"sharing_disabled","message":"record sharing is turned off for <table> ...","docs":"permissions.sharing_switch"}` and stores nothing, for a new grant and for a change to an existing one. `bm.permissions.share` throws with `err.code` `sharing_disabled`. A caller who may not read the table gets the same 404 as on an unknown /api path.
- Grants already stored give no access: a grantee no longer reads, lists, updates, deletes, restores, locks or signs a file of the row, no longer reads its version history, and no longer gets it through `?include=`. An admin grant no longer lets its holder list or revoke the row's shares. Owners, tenant members, role holders and admins reach the row exactly as the table's access rule says.
- GET /api/<table>/<id>/permissions still answers the owner or an admin, with `"sharing":"off"` beside the list and `"active":false` on every grant. Neither field is present while sharing is on.
- Both DELETE routes still revoke, so stored grants can be removed before sharing is turned on again.
- GET /api/_schema reports the switch for every table it lists as `capabilities.sharing` (true or false, always present), so a client can leave its share control out without a request per row.
- sdui.ShareDialog shows "Sharing is turned off for this table." in place of its form and sends no share request. To the owner or an admin it still lists the stored grants, each marked as giving no access, with Revoke. A signed-in account that may not list the row's grants sees the same sentence and no grants. A dialog that learns of the switch only from a refused share (`sharing_disabled`) replaces its form with the same state.

Turning the switch back on puts every grant still stored (and not expired) in force again; nothing is deleted when it is turned off. A table in `group` mode gives every tenant member the row already, so the switch matters for the owner-scoped modes (`self`, `owner_or_role`, `member-of`) and for a signed-in account outside the row's tenant.
