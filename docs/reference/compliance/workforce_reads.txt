For a compliance: hipaa app, reading rows through MCP query_db, the `sql` tool's read path (`benmore sql <app> "SELECT..." --reason "..."`) and the dashboard SQL console is limited to the app OWNER and needs a stated `reason` (1-500 characters; the console prompts for it). The app writes a `data_sql_read` row to _benmore_audit_log (platform user, role, surface, reason, statement SHA-256, row count; never the statement text) before any row is returned, and a failed audit write refuses the read. The platform decides from its own hipaa record or either app.yaml, so deleting the key lifts nothing; an app whose compliance cannot be checked is refused. Editors and viewers keep schema, counts and the observability surfaces (with viewer redaction); the channel's table_rows read is closed for such apps. Writes (sql write:true) stay editor-level and are audited as data_sql_write. Dashboard backup downloads (GET /platform/app-backup-download, a copy of every row) are owner-only for such an app too; they need no reason and write no data_sql_read row (the download is logged by the platform). The owner reads through a direct dashboard sign-in or the CLI: the desktop app's embedded Dashboard session acts as an editor on the console's POST (delegated-session policy) and is refused. Not covered yet: get_audit_log detailed old/new values, probe_route / browser `as:` sessions (audited as the end user), and an editor authoring a flow or page that returns rows; this gate stops casual console reads, not a determined editor.
