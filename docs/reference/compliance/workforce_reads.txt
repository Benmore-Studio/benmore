For a compliance: hipaa app, reading rows through MCP query_db, the `sql` tool's read path (`benmore sql <app> "SELECT..." --reason "..."`) and the dashboard SQL console is limited to the app OWNER and needs a stated `reason` (1-500 characters; the console prompts for it). The app writes a `data_sql_read` row to _benmore_audit_log (platform user, role, surface, reason, statement SHA-256, row count; never the statement text) before any row is returned, and a failed audit write refuses the read. The platform decides from its own hipaa record or either app.yaml, so deleting the key lifts nothing; an app whose compliance cannot be checked is refused. Editors and viewers keep schema, counts and the observability surfaces (with viewer redaction); the channel's table_rows read is closed for such apps. Writes (sql write:true) stay editor-level and are audited as data_sql_write. Dashboard backup downloads (GET /platform/app-backup-download, a copy of every row) are owner-only for such an app too; they need no reason and write no data_sql_read row (the download is logged by the platform). The owner reads through a direct dashboard sign-in or the CLI: the desktop app's embedded Dashboard session acts as an editor on the console's POST (delegated-session policy) and is refused. Not covered yet: get_audit_log detailed old/new values, headless-browser `as:` sessions, and an editor authoring a flow or page that returns rows; this gate stops casual console reads, not a determined editor. A probe as an app user (`benmore probe <app> GET /api/patients --as <user> --reason "..."`, probe_route with `as` and `reason`) needs editor access and a stated `reason` (1-500 characters). Without one it is refused before anything is sent to the app: `this app is compliance: hipaa: state why you are acting as this user (reason, 1-500 characters; CLI: --reason "why"); the reason is written to the app's audit log with the session it opens` (the CLI exits with `Error 400` and that text). A probe without `--as` needs no reason. A headless-browser session as a user (browser_check or browser_batch with `as`) needs editor access and no reason. Neither is held for the user's second factor: it answers what that user would read, encrypted columns unmasked where the user's own would be. Both are audited in two places: the app's _benmore_audit_log gets a `data_delegated_session` row before the session is used (user_email = the platform account, row_id = the app user's id, new_values with the caller's role, the surface, `purpose` `probe` or `browser`, and the probe's `reason`) and a `data_delegated_session_end` row when it ends, and each read it makes is a read-audit event under the app user's own name. rotate_encryption_key and blind_index_backfill (`benmore rotate-key`, `benmore blind-backfill`) open their admin session the same way; they ask for no reason and record the tool's name as the `reason`.
