Mode A: an admin session (a stepped-in act-as admin does NOT count) OR an owner token, PLUS the normal per-table write scope and access: rules - an owner token already proves the stronger authority and skips that second check. Mode B: an owner token, always, no exceptions - it is a multi-statement, multi-table write with no per-table gate downstream. `benmore import` obtains the owner token for you: hosted apps mint one from the platform automatically (needs `benmore login` + the owner role on the app). A self-hosted `benmore serve` target needs BENMORE_SERVER_SECRET set in the CLI environment to the running process's value plus --dir PATH matching the EXACT directory `benmore serve` was given; the CLI does not read a secret file. The token is reusable until its short expiry, not single-use. A client calling the endpoints itself sends the owner token in the `X-Benmore-Import-Token` header. Every session's `created_by_subject` (surfaced in the `_benmore_audit_log` row's `user_email` column) carries the human-identifiable actor behind it - an admin session's real email, a hosted owner token's platform-user email, or for a self-hosted mint, a BEST-EFFORT LOCAL identity suffixed `@self-hosted` (e.g. `alice@self-hosted`) rather than a verified email: it identifies the operator's local machine account, not an authenticated person, and should be read accordingly when auditing who ran an import.
