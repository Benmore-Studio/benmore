32 MiB per chunk. No row cap. Bounded by free disk, the plan's storage cap, and BENMORE_MAX_IMPORT_BYTES (default 50 GB). New sessions are limited to 10 per minute per app and caller (all owner-token imports of one app count as one caller): the next create answers 429 `too many import sessions; try again shortly`. A script that imports many files in a row must pause between them. Resuming a session still in staging does not count. These are separate projections. PLAN: current data.db + WAL/SHM plus 2x the projected loaded-data footprint (data pages + transient WAL), against the app's storage limit (the owner plan or an operator override; empty or unknown plans default to free; see api({at:'recovery'}) storage_limit). The database ceiling also applies during the load, so a load that outgrows the limit anyway fails and rolls back with the storage message. Staging is not database usage and is NOT charged to the plan cap. FREE DISK: at create, the staged copy sits on the same filesystem for the entire load, so a non-gzip import needs roughly 3x declared `bytes` free (1x staging + 2x data/WAL); at commit, staging is already reflected in current free disk, so only the 2x data/WAL term remains, calculated from the ACTUALLY staged bytes. For gzip, the data/WAL term uses the same conservative decompressed bound as the runtime bomb guard, not compressed `bytes`; the CLI supplies an ISIZE hint from an already-gzipped input but never gzips the file itself. Both gates run at create and commit. The runtime loader also counts decompressed bytes and aborts atomically past the bound.
