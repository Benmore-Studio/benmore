Mode A fills the owner column (`user_id`) like an auto-CRUD create; the file can never set it (protected). An admin session owns the rows it imports. An owner token (`benmore import`) has no user in the app, so it passes `owner` on the create request (CLI: `--owner EMAIL`): the email of an existing, active user of the SAME app instance (matched case-insensitively; another app's or environment's accounts never resolve), and every imported row gets that user's id. The owner is part of the resume identity, re-checked inside the load transaction (deleted or deactivated since create: the load fails, zero rows), and recorded in the import's audit entry (`owner_user_id`, `owner_email`) next to the token's subject. Refused with 400: an unknown, deactivated or ambiguous email; a table without `user_id`; `format: "sql"` (a restore keeps the dump's own values). An admin session passing `owner` gets 403. Without `owner`, an owner-token import leaves rows unowned, and a table whose `user_id` is NOT NULL with no default (the scaffold's Note) is refused at create, before any upload, with a message naming --owner, instead of failing row 1 with a NOT NULL error.
