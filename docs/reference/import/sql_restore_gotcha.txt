Mode B accepts only INSERT/UPDATE/DELETE/REPLACE/WITH as a statement's first verb - every DDL spelling, BEGIN/COMMIT/ROLLBACK, PRAGMA, VACUUM and ANALYZE are rejected by construction, so a raw sqlite3 db .dump fails immediately on its "PRAGMA foreign_keys=OFF; BEGIN TRANSACTION;" prologue. This is a SEPARATE mechanism from what's below: DDL/transaction-control rejection is the verb allowlist alone, a first-token match against the stripped, normalised statement - it is not raw-scanned.

On top of that allowlist, ATTACH/DETACH/PRAGMA are matched with a raw, case-insensitive, \b-word-anchored check against the UNTOUCHED statement text, and load_extension is matched with a raw, case-insensitive SUBSTRING check (deliberately not word-anchored - broader on purpose, since it's the one check that survived every bypass probe in review). Either way, a row value like 'please attach a receipt', or even a comment mentioning one of those words, aborts the WHOLE restore - and a substring like "myload_extension_call" trips the load_extension check too. That failure is loud and atomic (zero rows land), but a user hitting it deserves to know why immediately: it is not a bug in the data, it's the guard. Mode A (CSV/NDJSON) does none of this scanning and is the right choice for ordinary data - reach for Mode B only for a genuine whole-database SQL restore.
