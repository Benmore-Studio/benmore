MCP query_db is app database inspection for owners and accepted collaborators with editor access or higher (viewers are refused, as on the dashboard SQL console); it is separate from the session-scoped /api/_query API below. For a `compliance: hipaa` app, query_db, the `sql` read path and the SQL console are owner-only and need a `reason` (1-500 characters), which is written to the app's audit log as `data_sql_read`: see api({at:'compliance'}) workforce_reads. It accepts one SELECT/WITH statement and enforces read-only execution in SQLite. Writes, schema changes, PRAGMA, database attachment, extension loading and transaction control are refused. limit defaults to and cannot exceed 1000; iteration stops after one extra row to report truncated accurately. Queries stop after eight seconds or request cancellation. Narrow expensive joins/aggregates with WHERE/LIMIT. Credential columns in framework tables read as NULL (the session id in _benmore_sessions and the admin session an impersonation row names, a broadcast's publisher SFU session, and _benmore_* columns named like password, secret, token, hash, code, otp, totp, backup, key, nonce - so the emailed sign-in code, reset and email-change tokens, OAuth and MCP authorization codes and API token hashes; also `_benmore_idempotency.response`, a stored create response holding the row as its creator saw it), in the select list and in a filter alike, because collaborators can run this tool; app tables are unaffected. Other MCP tools that return application data need editor too: list_app_users (and describe kind:users), describe_jobs (queued payloads), get_audit_log with response_format:detailed (before/after row values) and read_file under uploads/; a viewer keeps concise audit rows, schema, source and health. Ordinary app mutations still use the guarded CRUD/flow APIs. query_db, sql (read and write:true), list_tables and get_counts are answered by the running app instance, with the same gates, caps and timeouts; sql write:true records a `data_sql_write` row in the app's audit log (platform user email, role, surface, verb, rows_affected and the statement's SHA-256, never its text) in the statement's own transaction; the row names the table the statement writes, a WITH-prefixed or quoted target included, and `last_insert_id` is reported only for an INSERT/REPLACE that added rows, 0 otherwise, and its live refresh reaches connected browsers. The other MCP tools that read or change app data (audit and read-audit trails, recent activity, health, analytics, request logs, client errors, describe, the context graph, visitor feedback, app users and sessions, create_superuser/create_app_user, delete_app_user, reset_and_seed, api discovery and the probe/browser `as` sessions) are answered the same way; the ones that change data leave `data_*` audit rows (or their existing actions) naming the platform user, never a password or statement text. The dashboard's SQL console and data tabs (schema, users, feedback, requests, analytics, graph, reset-and-seed, security scan history) are answered the same way. An instance that is not running (stopped) answers that the app is not running and must be started or restarted (restart_app); the platform never opens its database instead.
