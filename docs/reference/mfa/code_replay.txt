Each 30-second TOTP step is accepted once per account: after a code verifies, a code for that step or any earlier one is refused, including an earlier code still inside the ±1-step drift window. Enrollment activation records its accepted step atomically with factor activation/session issuance, and disabling MFA consumes a fresh TOTP step atomically with factor removal. A code already used for enrollment or sign-in cannot disable the factor; wait for the authenticator to show a new code. Failed activation/session/removal writes roll back the consumed step. Disabling still requires TOTP, not a recovery code; a replacement factor establishes a new watermark. Concurrent submissions of one code can't both pass. On auth.otp apps a password sign-in that completes TOTP on the separate MFA page continues to the emailed code, exactly as when the code is sent with the login form; social sign-ins go straight to a session after MFA. `benmore_totp_valid()` in app SQL checks a code but records no use; gate one-time actions on something the flow itself spends.
