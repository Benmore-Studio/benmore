`auth.require_mfa_for_roles` binds every credential of an account that holds a listed role and has no active TOTP factor, not only the next sign-in. Such a session or token resolves to no identity on every route (the change applies on the next request after a role grant or an app.yaml push): APIs, JSON and Bearer callers get 403 {error: "mfa_enrollment_required", message, redirect: <auth.mfa_setup_redirect, default /mfa-setup>}, page navigation is redirected to that page (HTMX: HX-Redirect), and minting an API token is refused. The realtime handshakes GET /sse/events and GET /ws answer the same 403 and open no stream. It can still load the setup page, GET /api/_csrf, sign out, reach the sign-in pages, and enroll: POST /api/_auth/mfa/setup with { password: <current password> } and CSRF (as any signed-in enrollment; also allowed when features.account_settings is off), then /api/_auth/mfa/verify. Once the factor is active the same session and tokens work again. Only a full sign-in session can enroll: for a held API token (or a scoped or act-as session) the 403's `message` says to sign in with the account's password instead, and POST /api/_auth/mfa/setup and /verify answer such a credential 403 `MFA enrollment requires a full-access login session outside act-as mode...` (401 when the request carries no credential at all). An account with no password (OAuth-only) signs in again instead, which issues the setup token. The sign-in pages are the login, sign-up, forgot-password, reset-password, verify-email and OTP/MFA step paths; login, sign-up and forgot-password are also reachable under their static file names (/login.html, /signup.html, /forgot-password.html), which scaffolds link to, and /signup itself is reachable; no other .html path is. The scaffold's setup page serves this case: when bm.mfa.enroll() answers 400 it shows a password form, calls bm.mfa.enroll(password), and offers sign-out. A setup page from an earlier scaffold only shows the 400's message (`password required to enable MFA`); there the person follows its "Back to log in" link and signs in again, which issues the setup cookie that page needs, or the app copies static/mfa-setup.html and lib/auth.ts initMFASetup from a new scaffold. Accounts this reaches: every signed-in account when the rule (or compliance: hipaa) is turned on, one granted a listed role (by an admin, or by a hook after sign-up), and one that turns its factor off. The roles that count are the ones sign-in checks: the users.role column and global grants (a role held only inside one tenant is not consulted). A pending enrollment (setup started, not verified) is not a factor. Not held: a support impersonation session (the admin's authority) and the session platform tooling mints for probe_route/browser_check `as`. `benmore test` gives its test users of a listed role a factor, so `as_role:` tests keep their session. Only accounts holding a listed role pay an extra lookup per request. MCP connector grants and scheduled tasks created earlier are not re-checked by this gate.
