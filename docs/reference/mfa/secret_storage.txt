_benmore_users.totp_secret is encrypted at rest with the app's ENCRYPTION_KEY (AES-256-GCM `enc:v2:` bound to _benmore_users.totp_secret; a pending enrollment is `pending:` + that ciphertext), so a database copy, backup or SQL read does not yield the secret. Only a durable key seals: ENCRYPTION_KEY set in the environment, env store (`benmore env set`, owner-only) or env.yaml, or auto-generated and persisted because encrypted.yaml declares fields. An app with none runs on a key generated for the process: the first enrollment (or the next successful use of an unencrypted factor) saves that key to env.yaml, the rule webhook subscription secrets follow (api(at:"encryption") secret_durability), and seals only once the environment the next start reads resolves it - so apps without ENCRYPTION_KEY encrypt TOTP secrets too, and env.yaml gains an ENCRYPTION_KEY line: keep it with the app's data. Where the key cannot be saved (env.yaml unwritable, or the environment sets a different or empty ENCRYPTION_KEY) the secret stays unencrypted - never sealed under a key a restart loses - enrollment still works, and startup logs a warning while any such enrollment exists: set ENCRYPTION_KEY and restart to encrypt them. Existing plaintext secrets are encrypted at startup once a durable key is present, and on their next successful use; reads accept both forms, so no one re-enrolls. rotate_encryption_key re-encrypts TOTP secrets in one transaction (also for apps whose only encrypted data is TOTP). Changing or losing ENCRYPTION_KEY without rotation leaves sealed factors unreadable: MFA then fails closed for those users (backup codes still work). App SQL keeps using `benmore_totp_valid(totp_secret, :code)`, which decrypts inside the engine; SQL that compares totp_secret to a known value directly does not match.
