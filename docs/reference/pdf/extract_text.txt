`run: extract_text` returns the text of a private PDF (an upload under uploads/private, or the app's own private CDN/S3 URL) through the same isolated Poppler/Tesseract extractor the MCP connector uses. `with: { source_path, record: {table, id}, ocr: true|false (default true) }`. Output under the step id: `{source_path, source_sha256, parser_version, complete, quality_flags, page_count, pages: [{page, text}], truncated}`; text is capped at about 1 MiB in total (`truncated: true`), blocks and boxes are not returned, so persist what you need with a following `run: sql`. `ocr: false` skips rasterizing and OCR for pages with no native text: they come back with empty text, `complete: false` and the quality flag `native_text_only_pages`; with OCR on, such pages are read by Tesseract (English only, `quality_flags` holds `ocr`). OCR text is evidence for human review, not exact. Limits are fixed: input up to 25 MiB (the connector's file limit), 200 pages, 40 MP a page, 60 s a page, 10 minutes in all, one extraction at a time per app (others wait for the slot, up to 10 minutes, then fail `limit_exceeded`), so the step runs only in a job, scheduled or data-event run (never an HTTP request or the /_admin/tools runner) and refuses a synchronous request flow when the flow is written (write gate and `benmore check`) and at run time: use `mode: async` under `on: request:`, or put the step in an async or scheduled flow and `run: enqueue` that flow (a synchronous request flow is refused even when it is only an enqueue target). It is also refused in a `transaction: true` flow (write gate and run time; an `on_error` handler, which runs after the rollback, may use it): a job or schedule transaction holds the app's write lock, and the step could hold it for 20 minutes. Extract in a flow without a transaction and write the text with a following `run: sql`. A failed step has one of these fixed messages, never parser text: `extract_text: unavailable_provider` (tools, language data or the sandbox are missing on the host, or the build is not Linux), `encrypted_pdf`, `limit_exceeded`, `unsupported_file` (not a PDF, corrupt, missing, or a tool failure), `timeout`. Authorization: the reference must be this app's private upload (public, foreign and encoded references are refused), and `record: {table, id}` is required (write gate and run time) and names the row that stores it, as for serve_file: the row must reference the file and its owner or tenant must be the uploader's, so a schedule that reads a user-editable reference column cannot extract a file another user uploaded. A `source_path` that reads request input (including a value an earlier step looked up with request input, or an enqueued payload value) also needs the signed-in caller (the actor the job restored) to be able to read that row through the table's access rules, all three of them: the table's `read:` mode (`admin`, `role:`, `perm:` and `off` decide here even on a table with no owner or tenant column, where there is no per-row rule; `read: off` refuses every caller, an admin included), the credential's `<table>:read` scope (an API token or scoped session without it is refused on its owner's rows too), and the per-row scope (the row's owner, tenant or membership, a record share, or an admin; it applies on an `everyone`/`anon` table too, so with an owner column only the owner, a share or an admin passes). A caller who fails any of them gets the error "extract_text refused: the signed-in caller cannot read the `record:` row"; a job with no actor refuses it too. The flow's own `auth:`/`role:` gate is not a substitute: the step checks the row whoever was let into the flow. For a `read: off` table, or callers the access rules do not cover, extract from a scheduled flow (below), which has no request-chosen reference. A data-event flow cannot pass the triggering row's own columns: they are caller-written (request input) and an event run has no signed-in caller to check; extract from a scheduled flow that picks pending rows up instead (`SELECT id, file_url FROM documents WHERE extract_complete = '' LIMIT 5` with `for_each`). Read and storage failures (a missing file, a refused reference) answer `unsupported_file`. Cost: results are cached in the app process by the file's SHA-256 and the `ocr` setting for an hour (a repeat of the same bytes reads the file and extracts nothing), and each signed-in user may use 15 minutes of extractor time an hour (a step that starts within the budget may finish past it); past that the step fails `limit_exceeded` until the hour is over. Runs without a signed-in user (schedules, jobs with no actor) are not counted. Extraction holds the app's single job worker for as long as it runs (up to 10 minutes), so other queued jobs wait; add `rate_limit` to a request flow that queues it. The step's output is treated as request input, so it cannot be spliced into `run: sql_dynamic` text; bind it with `:name` in `run: sql`. Extraction is not retried by the framework and holds a CPU-heavy child for up to 10 minutes: keep the flow's other work idempotent. Host prerequisite: an operator installs the tools with scripts/install-doc-tools.sh; until then the code is `unavailable_provider`.
