`pwa:` keys: `name`, `short_name`, `icon`, `theme_color`, `background_color`, `start_url`, `display`, `offline`, `offline_page`, `service_worker`. Any other key under `pwa:` is not read; a write of app.yaml and `benmore check` warn about it and name the nearest of these keys. The app serves `/manifest.json`, `/sw.js`, `/_internal/pwa.js` (registers `/sw.js`) and `/_internal/offline.html`. With a `pwa:` section every page carries the manifest link, the home-screen meta tags, `<meta name="theme-color">` (`pwa.theme_color`, else the brand color) and `<script src="/_internal/pwa.js" defer>`: SSR pages through the layout shell, static/*.html pages (the default TSX stack) added at serve time. The script is same-origin, so it runs under the page CSP's `script-src 'self'`. A page that declares its own manifest link, theme-color meta or `serviceWorker.register` call keeps it and gets no second one. An app with only a site name or brand color still serves the manifest and SSR pages link it, but its static pages register no worker. The manifest types the icon by extension: an SVG is one `image/svg+xml` icon with `sizes: "any"`; PNG/WebP/JPEG are declared 192x192 and 512x512, so use a 512x512 PNG. The manifest lists `icon`, else `seo.favicon`, else `/static/icon-512.png`, and when that is a /static/ file the app does not have, the next of them it does have, ending with `/static/favicon.svg` (the scaffold ships it), so a `pwa:` section without `icon` and a new app both list an icon that loads. A URL outside /static/ is listed as written; when the app has none of these files the configured (or default) path stays. `benmore check` and a write of app.yaml warn when a `pwa:` app's `icon` (or `seo.favicon`) names a file missing from static/, or when it has no icon file at all. The favicon fallback is one SVG entry: for home-screen installs add a 512x512 PNG and set `icon` (the iOS `apple-touch-icon` link is written only when `icon` or `seo.favicon` is set). `offline: true` is an offline fallback, not an offline app: navigations always go to the network, and when it fails the worker answers with `/_internal/offline.html`, precached at install without cookies. That page is generated (app name, theme color, `background_color` if `#rgb`/`#rrggbb`, a Try again link, no script, no CSRF token), or is the static/ .html file `offline_page: /static/offline.html` names, served as written (keep it self-contained; with a reviewed `mcp.yaml` from the reviewed source). No page is ever stored: pages are no-store and may be rendered for the signed-in visitor, and the worker's cache outlives the session. /static/ files are stored when the response is shareable (not no-store or private, no Set-Cookie, no Vary on Cookie, not a signed URL): a versioned `?v=` URL, which served HTML carries, is answered from the cache and replaces its older versions; an unversioned one comes from the network first and from the cache only offline. API calls, uploads and real-time are not handled. To open the app itself offline, ship your own worker (`pwa_service_worker`).
